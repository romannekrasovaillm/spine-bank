# Задание: форк spine-bank — «гейт, который нельзя тихо ослабить, и поставка, которой можно верить»

> Положи файл в корень форка рядом с `AGENTS.md` и начни сессию словами:
> «Прочитай `TASK.md` и действуй по нему. Сначала план, потом код».
> Основа: ревью `romannekrasovaillm/spine-bank` на коммите `7dbf13f` (v0.3.11, 2026-09-27) через призму
> эшелонированной защиты: разработчик → CI → мерж → реестр артефактов → вход в рантайм → после деплоя.

## 0. Суть в одном абзаце

Слои CI и гейта у проекта образцовые: fmt/clippy/test, `hermetic`, MSRV, `cargo audit`, SBOM, `dogfood`,
eval-сьют, ночные fuzz и mutants, единый `arch-be gate` с `rule_weakened` и `delta guard`. Поэтому задание
не про «добавить проверок», а про четыре вещи, найденные чтением кода: (1) исполнитель, которого проверяет
гейт, может **сам узаконить ослабление гейта** — override принимает любой непустой номер ADR, дельту
пишет тот же агент, а файлы контрольной плоскости (Stop-хук, `arch-harness.toml`, пороги рубрик) вне защиты;
(2) релиз публикуется без зависимости от CI, а SBOM и хэши описывают **другую сборку**, чем опубликованные
бинари; (3) входы рантайма агента (плагины, окружение исполнителя) не проверяются на целостность;
(4) слоёв после гейта — аналогов admission и пост-деплойной проверки — в продукте почти нет.
Цель форка — закрыть (1)–(3) и спроектировать (4).

**Критерий успеха:** сквозная репродукция «самоузаконивание» из раздела 3 даёт `exit 1` после фикса
(до фикса — зелёный гейт); релиз по тегу на красном коммите не публикуется; опубликованные бинари
сопровождаются SBOM, хэшами и provenance именно этой сборки.

## 1. Правила работы

1. **Сначала воспроизведи.** Репродукции ниже подготовлены по коду, но **не выполнялись** (см. приложение).
   Для каждой находки — падающий тест или shell-репродукция. Не воспроизводится — запиши в
   `docs/experiments/fork-repro-0.3.12.md`, что пробовал, и не чини.
2. **Соглашения репозитория** — `AGENTS.md`, `docs/RUST_CONVENTIONS.md`. Находки — по-русски, в формате
   `[error] <код> — <что> → <fix_hint>`.
3. **Без новых зависимостей** в `[dependencies]` (`[dev-dependencies]` и CI-инструменты — можно).
4. **Обратная совместимость:** `gate-verdict/v1`, exit-коды `0/1/2/3`, формат `CONSTRAINTS.yaml` не меняют смысла.
   Ужесточение, способное покраснить чужой пайплайн, — по схеме «warn → error по флагу» с ADR.
5. **Один пункт — один коммит** (`fix(A1): …`, `ci(B2): …`), тесты в том же коммите. Перед коммитом:
   `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test && cargo test --no-default-features --features core`.
6. **Ешь свою еду:** правки спайна и реестра — через `arch-be delta new …`, правила не ослаблять, решения —
   новыми ADR начиная с **ADR-055**.
7. **Не трогай:** лицензионную границу (`banking/`, `LICENSE.banking`), матрицу моделей (AD-BE2),
   границу ядра C-34 (новый код волн A и C — внутри будущего `spine-core`, без сетевых/TUI-крейтов).
8. **Стоп-условия:** нужно сломать `gate-verdict/v1`; нужно изменить смысл exit-кода; пункт помечен
   **[РЕШЕНИЕ ЧЕЛОВЕКА]**.

## 3. Волна A — P0: проверяемый не управляет проверкой

Общий принцип волны: исполнитель, которому гейт мешает, не должен иметь возможности сделать гейт зелёным,
не исправив код. Сейчас такая возможность есть на трёх путях.

### Сквозная репродукция «самоузаконивание»  ← главная

Подготовлена по коду, **не выполнялась**: ожидание до фикса — секция `rule_weakened` зелёная.

```bash
mkdir /tmp/sw && cd /tmp/sw && git init -q
cat > CONSTRAINTS.yaml <<'EOF'
rules:
  - id: X-1
    name: no_pan_in_logs
    type: must_not_contain
    glob: "src/**/*.go"
    pattern: "PAN="
    severity: critical
EOF
mkdir -p src && echo 'log("ok")' > src/a.go
git add -A && git commit -qm base

# «Исполнитель» под красным гейтом: удаляет правило, узаконивает выдуманным ADR, пишет себе дельту.
echo 'log("PAN=4111...")' > src/a.go
cat > CONSTRAINTS.yaml <<'EOF'
rules: []
overrides:
  - rule: X-1
    adr: ADR-999          # такого ADR нет
    until: "2099-12"      # горизонт не ограничен
EOF
mkdir -p changes/relax && printf '# Дельта\n\nПравка CONSTRAINTS.yaml.\n' > changes/relax/DELTA.md
arch-be gate --repo . --base HEAD
# Ожидание до фикса: rule_weakened PASS (override «активен»), delta_guard PASS (файл упомянут в дельте).
```

**Причины (по коду):** `active_override_keys` проверяет только, что `adr` непустой, а `until` не истёк —
существование и статус ADR не проверяются; `delta::guard` засчитывает любое упоминание файла в теле
активной дельты, не важно, кто и когда её создал.

### A1. `rule_weakened` видит изменение тела правила

Сейчас `RuleSnapshot` содержит только `id`, `exclude_glob` и `severity`. Не ловятся: замена `command`
у `command_succeeds` на `true`, сужение `glob`, правка `pattern` на никогда не срабатывающий, рост
`timeout_secs`, снижение числовых порогов.

**Сделать:**
- Добавить в снимок нормализованный хэш тела правила (все поля, кроме `rationale`/`fix_hint`/`skill`/`ad`,
  с канонической сериализацией). Изменение хэша без активного override — новая разновидность
  `WeakenedKind::BodyChanged` с перечислением изменённых полей.
- Ужесточение (новое правило, расширение `glob`, повышение severity) ослаблением не считается —
  сохранить поведение теста `rule_weakened_clean_when_unchanged_or_strengthened`; для `glob`/`pattern`
  без формальной семантики сравнения любое изменение — находка (лучше ложная тревога, чем тихое ослабление).
- Тесты: `cargo test` → `true`; `src/**` → `src/none/**`; `pattern` → `x^`; правки только `rationale` — чисто.

**Приёмка:** четыре теста выше; находка `BodyChanged` по умолчанию `warn`, по флагу
`[gate.rule_weakened] body = "error"` — `error` (схема warn → error из правила 4).

### A2. Override узаконивает только настоящим принятым ADR

**Сделать:**
- `active_override_keys` получает каталог ADR: override активен, если файл ADR с этим номером существует
  в `docs/adr/` (или в каталоге из конфига) и имеет статус `accepted`/«принято». Иначе — находка
  `override_adr_missing` / `override_adr_not_accepted`, ослабление не узаконено.
- Горизонт `until` ограничен: дальше `[gate.overrides] max_horizon_months` (дефолт 12) — находка
  `override_horizon_exceeded`.
- `arch-be control report --level corp` показывает эти находки в блоке overrides.

**Приёмка:** сквозная репродукция даёт `rule_weakened` FAIL с `override_adr_missing`; существующий тест
`rule_weakened_active_override_legalizes_weakening` переписан на реальный файл ADR и остаётся зелёным.

### A3. Пины контрольной плоскости: находка `control_plane_tampered`

Файлы, которые решают, работает ли гейт, сейчас вне `rule_weakened` и `delta guard`.

**Сначала аудит (без кода)** в `docs/experiments/control-plane-0.3.12.md`: полный перечень таких файлов
и путей к ним. Минимум: `.claude/settings.json` (Stop-хук и PostToolUse), блоки `spine-connect` в git-хуках
и CI-файлах, `arch-harness.toml` в корне репозитория (`[policy]`, `[gate.required]`,
`require_qualified_judge`, пороги), `.arch-handoff/RUBRIC.yaml`, `.arch-handoff/CONSTRAINTS.yaml`.
Отдельно проверить, защищает ли `DEFAULT_PROTECTED` копию реестра в `.arch-handoff/` — сравнение идёт
по префиксу пути, и `.arch-handoff/CONSTRAINTS.yaml` может не попадать под `CONSTRAINTS.yaml`.

**Сделать:**
- `handoff_create` записывает в `MANIFEST.json` поле `control_plane` — sha256 каждого файла из перечня.
- Новая составляющая гейта `control_plane`: сверка текущих файлов с пинами; расхождение без активной дельты —
  `[error] control_plane_tampered — <файл> изменён после выдачи пакета → вернуть файл или оформить дельту`.
  Нет `MANIFEST.json` — честный SKIP.
- Удаление Stop-хука из `.claude/settings.json` — отдельный тест.

**Приёмка:** исполнитель, удаливший Stop-хук или понизивший порог рубрики, получает `exit 1` от гейта.

### A4. `harness_run` перепроверяет результат сам

Stop-хук работает внутри песочницы исполнителя и в режиме fail-soft (нет `arch-be` в PATH — пропуск).
Доверять ему как последней линии нельзя.

**Сделать:**
- После завершения исполнителя (и после авто-коммита) `run_harness` сам запускает `arch-be gate`
  по рабочему дереву с базой `baseline_commit`, вне окружения исполнителя, и кладёт вердикт в итог прогона.
- Красный пост-гейт в CLI — код выхода 1 (сейчас `status=complete` у исполнителя ничего не говорит о
  гейте); в TUI — карточка с находками.
- Отключение — только явным флагом адаптера `post_gate = false` с предупреждением в журнале.

**Приёмка:** прогон, в котором заглушка-исполнитель удаляет Stop-хук и пишет нарушающий код, завершается
красным итогом с `control_plane_tampered` и находкой fitness.

### A5. Одобрение извне агентского диапазона  **[РЕШЕНИЕ ЧЕЛОВЕКА]**

A2 закрывает выдуманный ADR, но агент в режиме `--rw` может создать настоящий ADR со статусом `accepted`
(`adr_new`) и дельту (`delta_propose`). Нужен признак, что одобрение дал не проверяемый.

**Предложить (ADR-055) один из вариантов и дождаться решения:**
- (а) *по авторству коммита*: ADR, override и дельта, впервые появившиеся в диапазоне `base..HEAD` в коммитах
  с идентичностью исполнителя (`spine-harness` авто-коммита, трейлер `Co-Authored-By` агента) или
  в агентской сессии, не узаконивают ослабление — находка `self_approved`;
- (б) *по списку владельцев*: поле `approved_by` в ADR/дельте сверяется с `owners` из конфига репозитория;
- (в) *по подписи*: одобрение — подписанный коммит или тег ключом из списка владельцев (ssh-signing).

В любом варианте `self_approved` видна в паспорте вердикта.

## 4. Волна B — P1: поставка, которой можно верить

### B1. Релиз зависит от зелёного CI

`release.yml` по тегу `v*` собирает и публикует, не проверяя статус CI коммита: тег на красном коммите
выпустит релиз.

**Сделать:** первым джобом release — проверка, что для `github.sha` все обязательные джобы `ci.yml` зелёные
(через API check-runs), или прямой прогон `cargo test`, `dogfood` и `eval run` в release. Плюс документ
о защите тегов `v*` (кто может создавать).

**Приёмка:** тестовый тег на коммите с красной джобой не создаёт GitHub Release.

### B2. SBOM и хэши — от тех же бинарей, что опубликованы

Сейчас джоба `supply-chain` в `ci.yml` собирает только full-редакцию, без `--locked`, отдельно от
`release.yml`; SBOM живёт 90 дней как артефакт CI и к релизу не прикладывается.

**Сделать:** в матрице `release.yml` — `cargo sbom` для каждой редакции; в публикацию — `sbom-<edition>.cyclonedx.json`
и их хэши в общем `SHA256SUMS`. Джобу `supply-chain` в CI оставить как проверку, но собирать с `--locked`.
Обновить `docs/supply-chain.md` (таблица «что поставляется»).

### B3. Provenance и подпись  **[РЕШЕНИЕ ЧЕЛОВЕКА]** (выбор механизма для контура заказчика)

Открытый GAP из `docs/threat-model.md` §5 и `docs/supply-chain.md`.

**Предложить (ADR-056):** `actions/attest-build-provenance` (SLSA build provenance, `id-token: write`,
`attestations: write`) плюс keyless `cosign sign-blob` для `SHA256SUMS` — или GPG/ГОСТ-подпись, если
keyless-инфраструктура недоступна в контуре банка. Инструкция проверки — в `docs/supply-chain.md`.

### B4. Гигиена workflows

- Все `uses:` — по полному SHA с комментарием версии (сейчас по тегам: `@v2`, `@v4`, `@v7`, `@stable`,
  `@master`, `@nightly`), выровнять `actions/checkout` (сейчас `v7` и `v4` вперемешку). Обновления — через
  Dependabot/Renovate для actions.
- `permissions: contents: read` на уровне workflow в `ci.yml` и `nightly.yml` (сейчас блок есть только у
  публикации в `release.yml`).
- `cargo deny check` (licenses, bans, sources) как джоба CI с `deny.toml`; проверку лицензий из
  `docs/supply-chain.md` (ручной `jq`) заменить ссылкой на джобу.
- Фитнес-правила в корневой `CONSTRAINTS.yaml`: `uses:` без 40-символьного SHA запрещён;
  workflow без `permissions:` запрещён; джоба `cargo deny` существует (по образцу `C-04`).

### B5. `CODEOWNERS` в репозитории Spine

Добавить `.github/CODEOWNERS` на `CONSTRAINTS.yaml`, `ARCHITECTURE-SPINE.md`, `.github/workflows/`,

## 5. Волна C — P1: входы рантайма агента

### C1. Целостность плагинов

Скилл — инструкции агенту, то есть поверхность prompt-инъекции; `src/plugin.rs` загружает их без проверки.

**Сделать:**
- `plugins.lock` в каталоге плагинов: sha256 каждого файла плагина; пишется `arch-be init` и
  `arch-be plugins lock`.
- При загрузке расхождение — плагин не загружается, предупреждение в чате и журнале
  (`plugin_tampered`); `arch-be doctor` — отдельная проверка.
- Встроенные плагины сверяются с хэшами из бинаря.
- Подпись сторонних плагинов для bank-profile — вне объёма, карточка в ROADMAP.

### C2. Чистое окружение исполнителя по умолчанию на Critical

Окружение хоста по умолчанию протекает в процесс кодового харнесса; при запуске с отключёнными
разрешениями это путь утечки ключей в код и логи.

**Сделать:** на маршруте Critical и в bank-profile `env_allow` по умолчанию —
`["PATH", "HOME", "LANG", "TERM", "TMPDIR"]` плюс явные имена из адаптера; полное окружение —
только явным `env_inherit = true` с предупреждением в журнале.
Ужесточение для Standard — по схеме warn → error.

### C3. Секреты как составляющая гейта для целевых репозиториев

`src/secrets.rs` защищает вывод Spine, правила `C-05`/`C-06` — только код самого Spine.

**Сделать:** составляющая гейта `secrets` (детекторы из `src/secrets.rs`, область `changed`/`all` как у
`semantic_quality`), по умолчанию `warn`; шаблон правила в плагине `arch-governance`.
**Приёмка:** исполнитель, записавший ключ провайдера в код, получает находку `secret_literal` в пост-гейте A4.

### C4. Подписанная аттестация вердикта  **[РЕШЕНИЕ ЧЕЛОВЕКА]**

`compute_attestation` — sha256: защищает от порчи, но не от подделки (переписавший отчёт пересчитает хэш).
**Предложить (ADR-057):** подпись вердикта и Evidence Bundle идентичностью CI (keyless) или ключом
контура; `evidence verify` на маршруте Critical требует подписи не локальной идентичности.

## 6. Волна D — P2: слои после гейта (сначала дизайн)

Пункты волны D — ADR и прототип за флагом; в дефолтное поведение не входят.

### D1. `connect ci --provider bitbucket` (Core)

Вердикт гейта как отчёт Bitbucket Code Insights (`--format bitbucket-insights` и публикация через
`/rest/insights/1.0/…`) плюс Jenkinsfile-блок, отправляющий статус сборки новым build-status API —
под merge checks «Required builds» и «Code Insights» Bitbucket Data Center.

### D2. Теневой гейт для новых версий правил (канарейка реестра)

`arch-be gate --shadow-constraints <файл>`: вердикт по текущему и новому реестру, разница — отдельным блоком
(какие находки появятся). По флоту — через `control report --level corp`. Цель — заменить ручной раздел
«что может покраснеть» измерением до поднятия пина `extends`.

### D3. Экспорт инвариантов в политики кластера (Core)

По аналогии с мостом в ArchUnit (ADR-039): `arch-be policy export kyverno|rego` из `CONSTRAINTS.yaml` для
правил развёртывания (образы только из внутреннего реестра и подписанные, non-root, лимиты ресурсов,
тех-радар `deny_dependency` для образов). Новый тип правила или секция — **[РЕШЕНИЕ ЧЕЛОВЕКА]** (формат
`CONSTRAINTS.yaml`, правило 4).

### D4. Runtime fitness для NFR (исследование)

`arch-be nfr verify --metrics <источник>`: сравнение бюджетов p99 и SLA из модели (`nfr budget`,
`availability`) с фактическими метриками; расхождение — находка. Плюс генерация шаблона канареечного
анализа из сущностей `QAS-*`/`NFR-*` в handoff-пакете. Результат пункта — `docs/experiments/runtime-fitness.md`
