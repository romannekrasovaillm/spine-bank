# Задание: форк spine-bank — «таймаут, которому можно верить, и ядро, которое можно разделить»

> Положи файл в корень форка рядом с `AGENTS.md` и начни сессию словами:
> «Прочитай `TASK.md` и действуй по нему. Сначала план, потом код».
> Основа: ревью `romannekrasovaillm/spine-bank` на коммите `c5f94ea` (v0.3.6, 2026-09-19).

## 0. Суть в одном абзаце

Проект зрелый: clippy pedantic с `-D warnings`, `unsafe_code = "forbid"`, ~1555 тестов, в продовом коде
практически нет `unwrap/expect`, CI с audit/SBOM/MSRV/dogfood. Поэтому задание не про «навести порядок», а про
четыре вещи, которые ревью нашло механически: (1) таймаут `command_succeeds` не работает, если команда
порождает дочерние процессы — **воспроизведено**; (2) тесты и `bootstrap` молча зависят от установленного
`pytest`; (3) правила реестра исполняют произвольный `bash` из репозитория без модели доверия; (4) два
продукта (`spine-bank` и `spine-aiml`) держат 84 общих модуля, из которых идентичны 19, а синхронизация
делается руками — фиксы теряются (см. раздел 5). Цель форка — закрыть (1)–(3) и подготовить выделение
общего ядра в отдельный crate.

**Критерий успеха:** все пункты волны A закрыты тестами, которые падают на `c5f94ea` и проходят после
фикса; `cargo test` проходит на машине без Python; ни один продовый `.rs`-файл не длиннее 3000 строк.

## 1. Правила работы

1. **Сначала воспроизведи.** Для каждой находки — падающий тест или shell-репродукция. Не воспроизводится —
   запиши в `docs/experiments/fork-repro.md`, что пробовал, и не чини.
2. **Соглашения репозитория** — `AGENTS.md`, `docs/RUST_CONVENTIONS.md`. Находки — по-русски, в формате
   `[error] <код> — <что> → <fix_hint>`.
3. **Без новых зависимостей** в `[dependencies]`, кроме оговорённых ниже (`[dev-dependencies]` и CI-инструменты — можно).
4. **Обратная совместимость:** `gate-verdict/v1`, exit-коды `0/1/3`, формат `CONSTRAINTS.yaml` не меняют смысла.
   Ужесточение, способное покраснить чужой пайплайн, — по схеме «warn → error по флагу» с ADR.
5. **Один пункт — один коммит** (`fix(A1): …`, `refactor(B2): …`), тесты в том же коммите. Перед коммитом:
   `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test && cargo test --no-default-features --features core`.
6. **Ешь свою еду:** правки спайна и реестра — через `arch-be delta new …`, правила не ослаблять, решения —
   новыми ADR начиная с **ADR-053**.
7. **Не трогай:** лицензионную границу (`banking/`, `LICENSE.banking`), матрицу моделей (AD-BE2).
8. **Стоп-условия:** нужно сломать `gate-verdict/v1`; нужно изменить смысл exit-кода; пункт помечен
   **[РЕШЕНИЕ ЧЕЛОВЕКА]**.

## 3. Волна A — P0: баги с репродукцией

### A1. Таймаут `command_succeeds` не убивает потомков  ← главная

**Репродукция (выполнена на `c5f94ea`):**

```bash
mkdir /tmp/tt && cd /tmp/tt && git init -q
cat > CONSTRAINTS.yaml <<'EOF'
rules:
  - id: T-1
    name: slow
    type: command_succeeds
    command: "sleep 15; true"
    timeout_secs: 2
    severity: critical
EOF
time arch-be control check . --constraints CONSTRAINTS.yaml
# Факт: «превысила таймаут 2s и была убита», но реальное время — 15 с.
```

**Причина:** `run_with_timeout` делает `child.kill()` только для `bash`. Внук (`sleep`, `pytest` с воркерами,
`mvn`, `./gradlew`, любой `server &`) держит stdout/stderr, и `drain_tail`-потоки в `join()` ждут EOF до его
завершения. С фоновым процессом гейт висит **бесконечно** — хуже, чем без таймаута: CI убьёт джобу без отчёта.

**Сделать:**
- Вынести общий хелпер `src/proc.rs` — синхронный близнец `kill_process_group` из `harness.rs`, который уже решает
  эту задачу правильно: `CommandExt::process_group(0)` на unix, на таймауте `kill -TERM -- -<pgid>`, пауза, затем
  `kill -KILL -- -<pgid>`. `unsafe`/`libc` не использовать — запрещены линтом; разделитель `--` обязателен
  (комментарий в `harness.rs` объясняет, почему). Async-версию из `harness.rs` перенести туда же, чтобы логика была одна.
- `join()` читателей — с дедлайном: после kill ждать не дольше 1 с, дальше отчитываться тем, что успели прочитать.
- Все места с `Command::new("bash")`/`"sh"` и таймаутом (их ~70 — `grep -rn '"bash"\|"sh"' src`) перевести на хелпер.
- Тесты: `sleep 15; true` c таймаутом 1 с укладывается в < 3 с; `(sleep 30 &); sleep 30` — тоже; после
  таймаута в системе нет процесса-сироты (проверка через `kill -0` по pid, записанному командой в файл).

**Приёмка:** репродукция выше — FAIL за ≤ 3 с. Фитнес-правило в `CONSTRAINTS.yaml`: `Command::new("bash")`
вне `src/proc.rs` запрещён (`must_not_contain` по `src/**`, исключения — явным списком с owner/expiry).

### A2. Скрытая зависимость от `pytest`

**Репродукция:** на чистой машине без `pytest` `cargo test --no-default-features --features core` даёт
`1088 passed; 3 failed`: `bootstrap_creates_a_red_skeleton_with_a_next_step`,
`bootstrap_walks_to_green_when_artifacts_are_written`, `rules_report_prints_teeth_section_from_lock`.
С `pip install pytest` — все зелёные. CI это прячет, потому что ставит pytest в каждую джобу.

Это баг не только тестов. Сообщение самого теста: «иначе первым шагом было бы "почините то, что создал
проводник"» — именно это и видит пользователь без pytest: `bootstrap` выдаёт `rules ✗` на свежем каркасе.

**Сделать:**
- Отсутствие интерпретатора/раннера для шаблона правила = `SKIP` с причиной («pytest не найден → `pip install pytest`»),
  а не `✗`. Каркас `bootstrap` без pytest — `INCOMPLETE` (exit 3) с первым шагом «установите pytest», а не FAIL.
- `arch-be doctor` проверяет наличие `python3`, `pytest`, `java`/`mvn` для применённых шаблонов.
- Тесты, которым реально нужен pytest, — явный guard с сообщением «skipped: no pytest» (см. как это уже
  сделано для прогонщика в коммите `7a7501a`).
- CI: новая джоба `hermetic` — `cargo test` на образе **без** Python. Она обязана быть зелёной.

### A3. Правила реестра исполняют произвольный код без модели доверия  **[РЕШЕНИЕ ЧЕЛОВЕКА]**

`command_succeeds` запускает `bash -c <command>` из `CONSTRAINTS.yaml` проверяемого репозитория. Это
нормально для своего репо и опасно для чужого: `arch-be gate` на PR из форка, запуск через MCP агентом,
который склонировал незнакомый репозиторий, `control check` по кейсу коллеги. Для инструмента, чья
ценность — «зелёному можно верить», это та же дыра, что `direnv` без `direnv allow`.

**Сначала аудит (без кода):** составь в `docs/experiments/command-trust.md` таблицу — какие CLI-команды,
хуки и MCP-инструменты транзитивно доходят до `run_with_timeout`, и в каких из них репозиторий может быть
не своим.

**Затем предложить (ADR-053) один из вариантов и дождаться решения:**
- (а) *allow-файл по хэшу*: `arch-be rules allow` пишет в `~/.arch-harness/trusted.json` SHA-256 набора команд
  реестра; при несовпадении — `SKIP` с находкой `command_untrusted` и подсказкой;
- (б) флаг `--no-exec` / переменная `ARCH_NO_EXEC=1`, по умолчанию выключенный, плюс автоматическое включение
  в MCP-режиме;
- (в) оба.

В любом варианте — находка `command_untrusted` видна в паспорте вердикта в блоке «что не проверено».

## 4. Волна B — P1: код, который можно сопровождать

### B1. Декомпозиция крупных модулей

**Приёмка:** фитнес-правило «продовый `.rs` ≤ 3000 строк» (скрипт в `scripts/`, запуск через `command_succeeds`).

### B2. Подготовка общего ядра `spine-core`

Цифры сравнения с `spine-aiml` (оба на `main`, сентябрь 2026):

- общих файлов в `src/` — 84, идентичных — 19, похожих > 95 % — 20;
- сильнее всего разошлись `control.rs`, `contract_diff.rs` (3775 vs 830 строк), `evidence.rs`, `mcp_server.rs`, `gate.rs`;
- фиксы 0.3.5 (`CD-009/010`, `registry_diverged`, разбор базы диффа T-03) в `spine-aiml` отсутствуют;
- номера ADR с 040 означают **разные** решения в двух репо.

**Сделать** (в этом форке — только подготовка, без поломки сборки):
1. Превратить репо в cargo workspace: `crates/spine-core` (модель, `control`, `contract_diff`, `gate`, `evidence`,
   `rubric`, `mcp_server`-протокол, `hash`, `proc`) и `crates/arch-be` (бинарь, TUI, LLM, banking-профиль).
2. Граница: `spine-core` не зависит от `reqwest/ratatui/crossterm` — это уже почти так благодаря фиче `core`;
   сделай это проверяемым (`cargo tree -p spine-core` без этих крейтов — фитнес-правило).
3. Документ `docs/SPINE-CORE-API.md`: что стабильно, что внутреннее. Точки расширения доменов (banking/aiml)
   — через трейты (набор правил, триггеры значимости, шаблоны), а не через правку `control.rs`.
4. Схема ADR: префикс редакции для новых решений (`ADR-CORE-NNN` для ядра, `ADR-BE-NNN` для продукта) —
   **[РЕШЕНИЕ ЧЕЛОВЕКА]**.

**Приёмка:** `cargo build -p spine-core` собирается отдельно; `spine-aiml` может подключить его как git-зависимость
(проверь локально через `[patch]`).
