# Spec

## Требование: Хранение денежных сумм в minor units
Система ДОЛЖНА хранить и вычислять денежные суммы (суммы, комиссии, лимиты, остатки) только в minor units как целые значения (`i64`) либо через десятичный тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денег.

## Требование: Ключ идемпотентности на mutating-операциях
Каждая операция, изменяющая состояние (списание, зачисление, возврат, обновление статуса, запись в журнал), ДОЛЖНА принимать обязательный ключ идемпотентности (`idempotency_key`). Повторный вызов с тем же ключом ДОЛЖЕН возвращать сохранённый результат без повторного изменения состояния.

## Требование: Отсутствие unwrap/expect/panic в продуктовом коде
Продуктовый код НЕ ДОЛЖНА содержать `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Обработка ошибок ДОЛЖНА выполняться только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие персональных данных и PAN в логах
Система НЕ ДОЛЖНА записывать в логи и журналы полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Допустима только маска карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки
Ошибки ДОЛЖНЫ быть представлены типизированными перечислениями (enum ошибок с вариантом на каждый класс сбоя, реализацией `Display` + `Error`). Возврат ошибок строками (`Err("...")`, `String`, `Box<dyn Error>`) в продуктовом коде НЕ ДОЛЖЕН применяться.

## Требование: Отсутствие глобального мутабельного состояния
Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с состоянием домена. Состояние ДОЛЖНО передаваться явно (владение, параметры, конструктор).

## Требование: Таймауты на сетевых вызовах
Любой сетевой вызов (HTTP, TCP, очередь) ДОЛЖЕН выполняться с явно заданным таймаутом. Блокирующие вызовы без таймаута НЕ ДОЛЖНЫ применяться.

## Требование: Секреты из окружения
Ключи, пароли и токены ДОЛЖНЫ читаться только из переменных окружения (`std::env::var`). Секреты литералами в коде НЕ ДОЛЖНЫ присутствовать.

## Требование: Журналирование денежных событий
Каждое денежное событие ДОЛЖНО журналироваться с указанием ключа идемпотентности, суммы в minor units, валюты и результата. Журнал ДОЛЖЕН подчиняться требованию отсутствия персональных данных и PAN в логах.

## Требование: Контракт ошибок у публичных функций
Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

# Design

Обработчик колбэка платёжной системы лежит в платёжном домене и касается денег напрямую, поэтому архитектура строится вокруг трёх осей: точность вычислений, повторяемость операций и наблюдаемость без утечек данных.

Денежные суммы фиксируются в minor units (`i64`), потому что двоичная плавающая точка неспособна точно представить десятичные дроби — накопление ошибок округления в платёжных операциях недопустимо. Колбэк несёт сумму платежа, и весь путь её обработки — от парсинга входа до журнала — проходит в целых копейках.

Колбэк платёжной системы может быть доставлен более одного раза (ретраи шлюза, дубли сетевых сообщений). Обновление статуса и запись в журнал — mutating-операции, поэтому обработка каждого колбэка обязана начинаться с проверки ключа идемпотентности: при повторе возвращается сохранённый результат, состояние не меняется второй раз. Это защищает домен от двойных событий в журнале и рассинхронизации статуса.

Состояние хранилища платежей передаётся явно (владением или ссылкой через конструктор обработчика), а не через глобальные `static`-конструкции: это делает зависимости видимыми в сигнатурах, упрощает тестирование изолированными экземплярами и исключает скрытые гонки на глобальных лок-объектах.

Обработка ошибок построена на типизированном enum (`DomainError`: платёж не найден, неверная маска карты, ошибка хранилища и т.д.) с `Result`-контрактом у публичных функций. Паники в обработчике колбэка означали бы падение процесса на некорректном входе; вместо этого каждый сбой — предсказуемый вариант ошибки, который вызывающая сторона может классифицировать. Отсюда же запрет `unwrap/expect/panic`: обработчик должен пережить любой неожиданный вход.

Логирование денежного события (обновление статуса платежа) обязано фиксировать ключ идемпотентности, сумму, валюту и результат — это минимальный набор для сверки и разбора инцидентов. Номер карты из колбэка в журнал попадает только маской BIN + последние 4 цифры: журнал может читаться широким кругом лиц и выгружаться во внешние системы, поэтому ПДн и PAN в нём недопустимы.

В рамках задачи обработчик не выполняет сетевых вызовов и не читает секретов, однако стандарты домена действуют на весь код: если при реализации появятся HTTP-запросы или токены, они подчиняются правилам явных таймаутов и чтения секретов из окружения.

# Rules

- Все денежные суммы — только `i64` (minor units) или Decimal; `f64`/`f32` для денег запрещены.
- Любая mutating-операция (обновление статуса, запись в журнал) — только с ключом идемпотентности; повтор с тем же ключом возвращает сохранённый результат.
- Запрещены `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`; только `Result` с `?` или явной обработкой.
- В логах и журналах: без PAN, ФИО, паспортных данных, телефонов, адресов; карта — только маска BIN + последние 4 цифры.
- Ошибки — только типизированный enum с `Display` + `Error`; строковые ошибки (`Err("...")`, `String`, `Box<dyn Error>`) запрещены.
- Без `static mut`, `lazy_static!`, `static ref`, глобальных `static Mutex/RwLock` с доменным состоянием; состояние передаётся явно.
- Любой сетевой вызов — только с явно заданным таймаутом.
- Секреты — только из `std::env::var`; литералы секретов в коде запрещены.
- Каждое денежное событие журналируется: ключ идемпотентности, сумма в minor units, валюта, результат — без ПДн/PAN.
- Публичные функции домена возвращают `Result<T, DomainError>`; набор вариантов ошибки — часть контракта.
