# Spec

## Требование: Денежные суммы без плавающей точки

Система ДОЛЖНА представлять сумму операции в minor units (целые копейки, `i64`) или через десятичный тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для сумм, порогов и результатов скоринга, связанных с деньгами.

## Требование: Идемпотентность скоринговых операций

Система ДОЛЖНА принимать обязательный ключ идемпотентности (`idempotency_key`) для каждой операции, изменяющей состояние (запись решения в журнал). Повторный вызов с тем же ключом ДОЛЖЕН возвращать сохранённый результат без повторного изменения состояния.

## Требование: Запрет паник в прод-коде

Система НЕ ДОЛЖНА содержать `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` в продуктовом коде. Обработка ошибок ДОЛЖНА выполняться только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие ПДн и PAN в логах

Система НЕ ДОЛЖНА записывать в журнал полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны и адреса. Допустима только маска карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки

Система ДОЛЖНА представлять ошибки в виде типизированного перечисления (enum с вариантом на каждый класс сбоя, реализация `Display` + `Error`). Возврат ошибок строками (`Err("...")`, `String`, `Box<dyn Error>`) в продуктовом коде НЕ ДОЛЖЕН применяться.

## Требование: Отсутствие глобального мутабельного состояния

Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с состоянием домена. Состояние (стоп-лист, журнал решений, пороги) ДОЛЖНО передаваться явно: через владение, параметры или конструктор.

## Требование: Сетевые вызовы только с таймаутом

Система ДОЛЖНА выполнять любой сетевой вызов (HTTP, TCP, очередь) с явно заданным таймаутом. Блокирующие вызовы без таймаута НЕ ДОЛЖНЫ применяться.

## Требование: Секреты только из окружения

Система ДОЛЖНА читать ключи, пароли и токены только из переменных окружения (`std::env::var`). Секреты литералами в коде НЕ ДОЛЖНЫ присутствовать.

## Требование: Журналирование денежных событий

Система ДОЛЖНА журналировать каждое скоринговое решение: ключ идемпотентности, сумма в minor units, валюта, вердикт (pass/review/block) и результат. Журнал ДОЛЖЕН подчиняться требованиям по отсутствию ПДн/PAN.

## Требование: Контракт ошибок публичных функций

Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

## Требование: Функциональность антифрод-префильтра

Система ДОЛЖНА принимать на вход операцию (карта, сумма, страна, время). Система ДОЛЖНА применять правила: сумма выше порога, ночное время, страна из стоп-листа. Система ДОЛЖНА вычислять скоринг и выносить вердикт (pass/review/block), после чего логировать решение с данными операции.

# Design

Антифрод-префильтр — часть платёжного домена, поэтому применяется весь пакет организационных стандартов, а не их подмножество.

Суммы и пороги хранятся в `i64` (minor units): плавающая точка недопустима для денег, а порог скоринга сравнивается с денежной суммой, следовательно, тоже целочисленный. Скоринг — целочисленный вес, поскольку он выводится из денежных и категориальных признаков операции.

Решения журналируются, то есть мутируют состояние, поэтому оценка принимает `idempotency_key`: повторная отправка операции (частый случай в платёжных шинах при ретраях) не должна приводить к дублированным записям и расхождению результатов.

Ошибка при разборе входных данных, некорректной маске карты или при записи в журнал — это классы сбоев, различимые вызывающей стороной, поэтому они оформлены как варианты `DomainError` (thiserror-стиль), а публичная функция оценки возвращает `Result<Verdict, DomainError>`. Это делает контракт публичного API явным и проверяемым.

Стоп-лист стран, порог суммы, интервал «ночного времени» и журнал решений сгруппированы в структуре конфигурации, создаваемой в `main` и передаваемой по ссылке. Это исключает глобальное мутабельное состояние: правила и хранилище решений живут в одном явно передаваемом объекте, что упрощает тестирование и исключает гонки на глобальных статиках.

Карта при логировании приводится к маске (BIN + последние 4 цифры) до любой записи в журнал — сам входной PAN нигде не сохраняется дольше, чем нужно для маскирования. Время операции хранится как явное значение (час/минуты UTC), а не берётся из системных часов внутри правил, что делает скоринг детерминированным.

Файл самодостаточен (`src/main.rs`), сетевые вызовы отсутствуют, секретов нет — но стандарты S-07 и S-08 зафиксированы как ограничения: любое расширение префильтра внешними вызовами ( enrichment, внешние списки) обязано получить таймаут и чтение credentials из окружения.

# Rules

- Деньги, пороги и остатки — только `i64`/Decimal; `f64`/`f32` запрещены.
- Каждая mutating-операция (запись в журнал) принимает `idempotency_key`; повтор — сохранённый результат.
- Никаких `.unwrap()`, `.expect`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` — только `Result` и `?`.
- В логах: только маска карты (BIN + последние 4), никаких PAN/ФИО/паспортов/телефонов/адресов.
- Ошибки — только типизированный enum (`DomainError`) с `Display` + `Error`; строковые ошибки запрещены.
- Никаких `static mut`, `lazy_static!`, `static ref`, глобальных `static Mutex/RwLock`; состояние — через конструктор/параметры.
- Любой сетевой вызов — только с явным таймаутом.
- Секреты — только через `std::env::var`, литералов в коде нет.
- Каждое решение логируется: ключ идемпотентности, сумма в minor units, валюта, вердикт, результат.
- Публичные функции возвращают `Result<T, DomainError>`; варианты ошибки — часть контракта.
- Один самодостаточный файл `src/main.rs`; ответ — только код, без пояснений.
- Не добавлять требований и возможностей сверх зафиксированных стандартов и постановки задачи.
