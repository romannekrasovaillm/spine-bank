# Spec

## Требование: Денежные суммы без плавающей точки
Система ДОЛЖНА хранить и вычислять денежные суммы (суммы событий, балансы, комиссии, лимиты, остатки) только в minor units как целые числа (`i64`) либо через тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денежных величин.

## Требование: Идемпотентность дубликатов
Система ДОЛЖНА принимать ключ идемпотентности (id события) на каждой операции, изменяющей состояние (применение события к балансу, запись в журнал). Система ДОЛЖНА при повторном вызове с тем же ключом возвращать сохранённый результат без повторного изменения состояния, тем самым отбрасывая дубликаты уже обработанных событий.

## Требование: Отсутствие unwrap/panic в продуктовом коде
Система НЕ ДОЛЖНА содержать в продуктовом коде `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Система ДОЛЖНА обрабатывать ошибки только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие персональных данных и PAN в логах
Система НЕ ДОЛЖНА записывать в логи и журналы полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Система ДОЛЖНА допустить в логи только маску карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки
Система ДОЛЖНА представлять ошибки типизированными перечислениями (enum ошибок с вариантом на каждый класс сбоя и реализацией `Display` + `Error`, в стиле thiserror). Система НЕ ДОЛЖНА возвращать ошибки строками (`Err("...")`, `String`, `Box<dyn Error>`) в продуктовом коде.

## Требование: Отсутствие глобального мутабельного состояния
Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref`, глобальные `static Mutex/RwLock` с состоянием домена. Система ДОЛЖНА передавать состояние явно (владением, параметрами, через конструктор).

## Требование: Таймауты на сетевых вызовах
Система ДОЛЖНА выполнять любой сетевой вызов (HTTP, TCP, очередь) с явно заданным таймаутом. Система НЕ ДОЛЖНА выполнять блокирующие вызовы без таймаута.

## Требование: Секреты из окружения
Система ДОЛЖНА читать ключи, пароли и токены только из переменных окружения (`std::env::var`). Система НЕ ДОЛЖНА содержать секреты литералами в коде.

## Требование: Журналирование денежных событий
Система ДОЛЖНА журналировать каждое денежное событие с указанием: ключа идемпотентности, суммы в minor units, валюты, результата. Журнал ДОЛЖЕН подчиняться требованию отсутствия персональных данных и PAN в логах.

## Требование: Контракт ошибок публичных функций
Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

# Design

Обработчик очереди платежных событий — точка входа в платёжный домен, поэтому все орг-стандарты применяются к нему в полном объёме.

Деньги представляются `i64` в minor units: целочисленная арифметика исключает ошибки округления, свойственные `f64`, что критично при накоплении баланса из потока событий. Баланс счёта и сумма события — один тип, один масштаб.

Отбрасывание дубликатов реализуется через хранилище обработанных ключей идемпотентности (id события). Это соответствует стандарту S-02: повторная доставка сообщения из очереди не должна приводить к повторному изменению баланса. Перед применением события система проверяет ключ; при совпадении возвращается сохранённый результат без мутаций. Хранилище и балансы инкапсулируются в структуре процессора, создаваемой явно и получаемой через владение/параметры, — так исключается глобальное мутабельное состояние (S-06) и код остаётся тестируемым.

Обработка ошибок построена на `Result` без единого `unwrap`/`expect`/`panic` (S-03): ошибки парсинга, неизвестные типы событий, некорректные суммы типизированы в enum `DomainError` с `Display` и `Error` (S-05), а публичные функции возвращают `Result<T, DomainError>`, делая множество отказов частью контракта (S-10).

Журналирование денежного события содержит ключ идемпотентности, сумму в minor units, валюту и результат (S-09); карта попадает в журнал исключительно маской BIN + последние 4 цифры (S-04). Логгер передаётся явно, а не через глобальный реестр.

Если обработчик читает из очереди или совершает сетевые вызовы, каждый такой вызов выполняется с явным таймаутом (S-07). Параметры подключения и секреты берутся из `std::env::var` (S-08). Всё это упаковано в один самодостаточный `src/main.rs`, не добавляющий требований сверх зафиксированных стандартов.

# Rules

- `no-floating-point-money`: денежные величины только `i64` (minor units) или Decimal; `f64`/`f32` для денег запрещены.
- `require-idempotency-key`: каждая мутация (применение события, запись в журнал) идёт через ключ идемпотентности; повторный ключ — сохранённый результат без мутаций.
- `no-unwrap-panic`: запрет `.unwrap()`, `.expect`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` в продуктовом коде; ошибки только через `Result`/`?`.
- `no-pan-pii-in-logs`: в логах только маска карты (BIN + последние 4 цифры); PAN, ФИО, паспорт, телефон, адрес — запрещены.
- `typed-errors`: ошибки — enum в стиле thiserror с `Display` + `Error`; строковые ошибки и `Box<dyn Error>` запрещены.
- `no-global-mutable-state`: запрет `static mut`, `lazy_static!`, `static ref`, глобальных `static Mutex/RwLock`; состояние передаётся явно.
- `network-timeouts`: все сетевые вызовы (HTTP, TCP, очередь) — с явным таймаутом.
- `secrets-from-env`: секреты только из `std::env::var`; литералы в коде запрещены.
- `log-money-events`: каждое денежное событие журналируется с ключом идемпотентности, суммой в minor units, валютой, результатом.
- `result-domain-error-contract`: публичные функции возвращают `Result<T, DomainError>`; варианты ошибки — часть контракта.
