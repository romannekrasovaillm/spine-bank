# Spec

## Требование: Денежные суммы без плавающей точки
Система ДОЛЖНА хранить и вычислять денежные суммы (суммы платежей, расхождения) только в minor units (целые `i64`) либо через десятичный тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денег, комиссий, лимитов и остатков.

## Требование: Идемпотентность mutating-операций
Каждая операция, изменяющая состояние (включая запись в журнал и формирование отчёта как журнал результата), ДОЛЖНА принимать обязательный ключ идемпотентности (`idempotency_key`). Повторный вызов с тем же ключом ДОЛЖЕН возвращать сохранённый результат без повторного изменения состояния.

## Требование: Отсутствие unwrap/expect/panic в продуктовом коде
Продуктовый код НЕ ДОЛЖЕН содержать `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Обработка ошибок ДОЛЖНА выполняться только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие ПДн и PAN в логах
В логи и журналы НЕ ДОЛЖНЫ попадать: полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Допустима только маска карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки
Ошибки ДОЛЖНЫ быть представлены типизированными перечислениями (enum ошибок в стиле thiserror: вариант на каждый класс сбоя, реализация `Display` + `Error`). Возврат ошибок строками (`Err("...")`, `String`, `Box<dyn Error>`) в продуктовом коде НЕ ДОЛЖЕН применяться.

## Требование: Отсутствие глобального мутабельного состояния
Код НЕ ДОЛЖЕН использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с состоянием домена. Состояние ДОЛЖНО передаваться явно (владение, параметры, конструктор).

## Требование: Таймауты на сетевых вызовах
Любой сетевой вызов (HTTP, TCP, очередь) ДОЛЖЕН выполняться с явно заданным таймаутом. Блокирующие вызовы без таймаута НЕ ДОЛЖНЫ применяться.

## Требование: Секреты только из окружения
Ключи, пароли, токены ДОЛЖНЫ читаться только из переменных окружения (`std::env::var`). Секреты литералами в коде НЕ ДОЛЖНЫ присутствовать.

## Требование: Журналирование денежных событий
Каждое денежное событие ДОЛЖНО журналироваться с указанием: ключ идемпотентности, сумма в minor units, валюта, результат. Журнал ДОЛЖЕН подчиняться правилу отсутствия ПДн/PAN.

## Требование: Контракт ошибок публичных функций
Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

## Требование: Функциональность сверки реестров
Система ДОЛЖНА принимать на вход два списка записей (id платежа, сумма, карта) — внутренний реестр и реестр банка-эквайера. Система ДОЛЖНА находить расхождения: платеж отсутствует с одной из сторон, суммы не совпали. Система ДОЛЖНА формировать отчёт и залогировать каждое расхождение. Результат ДОЛЖЕН быть оформлен как один самодостаточный файл `src/main.rs`.

# Design

Задача сверки реестров относится к платёжному домену, поэтому к ней применяется полный набор организационных стандартов. Архитектура строится вокруг следующих решений.

Суммы платежей и расхождений представляются в minor units (`i64`), поскольку сверка — чисто денежная операция: сравнение `f64` на равенство ненадёжно, а накопление погрешности при конвертациях недопустимо для отчётности перед банком. Использование целочисленных minor units исключает целый класс ошибок на этапе типа.

Сверка реализуется как чистая доменная функция сравнения двух реестров, состояние которой передаётся явно через параметры. Никакого глобального мутабельного состояния: реестры, журнал и отчёт — обычные значения, которыми функция владеет или которые получает по ссылкам. Это упрощает тестирование и соответствует запрету глобальных синглтонов.

Хотя сверка двух переданных списков — операция чтения, формирование отчёта и записи журнала являются изменяющими действиями (запись в журнал явно упомянута в стандарте идемпотентности). Поэтому сведение реестров инициируется с ключом идемпотентности, который попадает в каждую запись журнала вместе с суммой, валютой и результатом — это требование журналирования денежных событий и защита от дублирования отчётов при повторных запусках.

Каждое расхождение журналируется с маской карты: BIN и последние 4 цифры, остальное замаскировано звёздочками. Даже если входные данные содержат PAN, в журнал он не попадает.

Обработка ошибок — через типизированный `enum` ошибок домена с реализацией `Display` и `Error`. Разбор входных записей и любые преобразования возвращают `Result`, который пробрасывается через `?` до `main`. В коде отсутствуют `unwrap`, `expect`, `panic!` — сбой на некорректных данных выражается вариантом ошибки, а не падением процесса.

Публичные функции сверки возвращают `Result<T, DomainError>`, где набор вариантов — часть контракта: вызывающая сторона может различать ошибки формата входных данных и ошибки журналирования.

Так как решение — один самодостаточный файл `src/main.rs` без внешних сетевых вызовов и без секретов, требования о таймаутах и чтении секретов из окружения применяются условно: при появлении сетевого взаимодействия оно обязано быть с таймаутом, а любые ключи — только из `std::env::var`.

# Rules

- Использовать только `i64` (minor units) или Decimal для денежных сумм; `f64`/`f32` для денег запрещены.
- Mutating-операции (включая запись в журнал и формирование отчёта) принимают `idempotency_key`; повторный вызов возвращает сохранённый результат без изменения состояния.
- Запрещены `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`; ошибки — через `Result` с `?` или обработкой.
- В логи не попадают PAN, ФИО, паспортные данные, телефоны, адреса; карта — только маска (BIN + последние 4 цифры).
- Ошибки — типизированный enum (стиль thiserror) с `Display` + `Error`; строковые ошибки запрещены.
- Запрещены `static mut`, `lazy_static!`, `static ref`, глобальные `static Mutex/RwLock`; состояние передаётся явно.
- Сетевые вызовы только с явным таймаутом; блокирующие вызовы без таймаута запрещены.
- Секреты только из `std::env::var`; литералы секретов в коде запрещены.
- Каждое денежное событие журналируется: idempotency_key, сумма в minor units, валюта, результат — без ПДн/PAN.
- Публичные функции возвращают `Result<T, DomainError>`; варианты ошибки — часть контракта.
- Результат — один самодостаточный файл `src/main.rs` без внешних пояснений.
