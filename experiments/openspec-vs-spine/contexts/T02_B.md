# Spec

## Требование: Денежные суммы как целые
Система ДОЛЖНА хранить и вычислять денежные суммы (баланс, суммы операций) только в minor units (`i64`) или через десятичный тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денег, комиссий, лимитов и остатков.

## Требование: Ключ идемпотентности на операциях изменения состояния
Система ДОЛЖНА требовать обязательный ключ идемпотентности (`idempotency_key`) у каждой операции, изменяющей состояние (списание, зачисление, обновление статуса, запись в журнал). Повторный вызов с тем же ключом ДОЛЖЕН возвращать сохранённый результат без повторного изменения состояния.

## Требование: Запрет паникующих конструкций
Продуктовый код НЕ ДОЛЖЕН содержать `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Обработка ошибок ДОЛЖНА выполняться только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие ПДн и PAN в логах и выписке
Система НЕ ДОЛЖНА выводить в логи и журналы (включая выписку) полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Допустима только маска карты: BIN + последние 4 цифры, остальное — `*`.

## Требование: Типизированные ошибки
Ошибки ДОЛЖНЫ быть представлены типизированными перечислениями (enum ошибок с вариантом на каждый класс сбоя, реализация `Display` + `Error`). Продуктовый код НЕ ДОЛЖНЕН возвращать ошибки строками (`Err("...")`, `String`, `Box<dyn Error>`).

## Требование: Запрет глобального мутабельного состояния
Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с состоянием домена. Состояние ДОЛЖНО передаваться явно (владение, параметры, конструктор).

## Требование: Сетевые вызовы с таймаутом
Система ДОЛЖНА выполнять любой сетевой вызов с явно заданным таймаутом. Блокирующие сетевые вызовы без таймаута НЕ ДОЛЖНЫ применяться.

## Требование: Секреты из окружения
Ключи, пароли и токены ДОЛЖНЫ читаться только из переменных окружения (`std::env::var`). Секреты литералами в коде НЕ ДОЛЖНЫ присутствовать.

## Требование: Журналирование денежных событий
Система ДОЛЖНА журналировать каждое денежное событие с указанием: ключа идемпотентности, суммы в minor units, валюты и результата. Журнал ДОЛЖЕН подчиняться требованию отсутствия ПДн/PAN.

## Требование: Контракт ошибок публичных функций
Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

# Design

Архитектура строится вокруг того, что модуль хранения банковского счёта и выдачи выписки относится к платёжному домену, где цена ошибки — некорректный баланс или утечка персональных данных.

Состояние счёта (баланс и история операций) инкапсулируется в структуре, создаваемой явно и передаваемой через владение или ссылки. Это прямое следствие запрета глобального мутабельного состояния: отсутствие `static mut` и глобальных `Mutex` делает поток управления изменениями состояния очевидным и тестируемым, а также исключает скрытые гонки на глобальном уровне.

Деньги представлены `i64` в minor units. Целочисленная арифметика исключает ошибки округления, присущие плавающей точке, и делает баланс детерминированным. Для арифметики с потенциальным переполнением используются проверяемые операции с возвратом ошибки, что согласуется с запретом паникующих конструкций.

Зачисление и списание — операции, изменяющие состояние, поэтому обе принимают обязательный ключ идемпотентности. Хранение результата по ключу позволяет повторному вызову вернуть сохранённый результат без повторного изменения баланса и истории, что критично при ретраях со стороны вызывающих систем.

История операций одновременно служит журналом денежных событий: каждая запись содержит ключ идемпотентности, сумму в minor units, валюту и результат операции. Контрагент хранится с номером карты, но при печати выписки выводится только маска (BIN + последние 4 цифры), так как выписка попадает в журналируемый вывод и подпадает под требование защиты ПДн.

Все сбои (недостаточно средств, некорректная сумма, ошибка маскировки карты и т.д.) выражаются через типизированный enum ошибок с реализацией `Display` и `Error`. Публичные функции возвращают `Result<T, DomainError>`, что делает контракт ошибок частью публичного API и заставляет вызывающего обрабатывать отказы явно. Отсутствие `unwrap`/`expect`/`panic` гарантирует, что ни один сбой не завершит процесс аварийно.

Модуль не выполняет сетевых вызовов и не хранит секретов; если такие зависимости появятся, таймауты для сети и чтение секретов из `std::env::var` применяются без исключений.

# Rules

- Денежные суммы — только `i64` (minor units) или Decimal; `f64`/`f32` для денег запрещены.
- Зачисление и списание принимают обязательный `idempotency_key`; повторный вызов с тем же ключом возвращает сохранённый результат без изменения состояния.
- Запрещены `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`; ошибки — только через `Result`.
- В выписке и логах контрагент выводится только маской карты: BIN + последние 4 цифры, остальное `*`; PAN, ФИО, паспорт, телефон, адрес — запрещены.
- Ошибки — типизированный enum (`thiserror`-стиль) с `Display` + `Error`; строковые ошибки (`String`, `Box<dyn Error>`) запрещены.
- Запрещены `static mut`, `lazy_static!`, `static ref`, глобальные `static Mutex/RwLock` с доменным состоянием; состояние передаётся явно.
- Сетевые вызовы (если появятся) — только с явным таймаутом.
- Секреты (если появятся) — только через `std::env::var`, без литералов в коде.
- Каждое денежное событие журналируется: ключ идемпотентности, сумма в minor units, валюта, результат.
- Публичные функции домена возвращают `Result<T, DomainError>`; набор вариантов ошибки — часть контракта.
