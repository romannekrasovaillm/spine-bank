# Spec

## Требование: Деньги без плавающей точки
Система ДОЛЖНА хранить и вычислять денежные суммы (суммы платежа, комиссии, лимиты, остатки) только в minor units (`i64`) или через тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денежных величин.

## Требование: Идемпотентность mutating-операций
Система ДОЛЖНА принимать обязательный ключ идемпотентности (`idempotency_key`) в каждой операции, изменяющей состояние (списание, зачисление, возврат, обновление статуса, запись в журнал). Система ДОЛЖНА при повторном вызове с тем же ключом возвращать сохранённый результат без повторного изменения состояния.

## Требование: Запрет unwrap/expect/panic
Система НЕ ДОЛЖНА содержать в продуктовом коде `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Система ДОЛЖНА обрабатывать ошибки только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие ПДн и PAN в логах
Система НЕ ДОЛЖНА записывать в логи и журналы полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Система ДОЛЖНА допускать в логах только маску карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки
Система ДОЛЖНА представлять ошибки типизированными перечислениями (enum с вариантом на каждый класс сбоя, реализация `Display` + `Error`, в стиле thiserror). Система НЕ ДОЛЖНА возвращать ошибки строками (`Err("...")`, `String`, `Box<dyn Error>`) в продуктовом коде.

## Требование: Запрет глобального мутабельного состояния
Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с состоянием домена. Система ДОЛЖНА передавать состояние явно (владение, параметры, конструктор).

## Требование: Таймауты на сетевых вызовах
Система ДОЛЖНА выполнять любой сетевой вызов (HTTP, TCP, очередь) с явно заданным таймаутом. Система НЕ ДОЛЖНА выполнять блокирующие вызовы без таймаута.

## Требование: Секреты из окружения
Система ДОЛЖНА читать ключи, пароли и токены только из переменных окружения (`std::env::var`). Система НЕ ДОЛЖНА содержать секреты литералами в коде.

## Требование: Журналирование денежных событий
Система ДОЛЖНА журналировать каждое денежное событие с указанием: ключа идемпотентности, суммы в minor units, валюты, результата. Система ДОЛЖНА подчинять журнал требованиям отсутствия ПДн/PAN.

## Требование: Контракт ошибок публичных функций
Система ДОЛЖНА возвращать публичными функциями домена `Result<T, DomainError>`, где набор вариантов ошибки является частью контракта функции.

## Требование: Реализация authorize
Система ДОЛЖНА реализовать функцию authorize p2p-платежа между картами с входными данными: сумма платежа, номер карты отправителя, номер карты получателя. Система ДОЛЖНА рассчитывать комиссию 1%, логировать операцию и возвращать структуру платежа со статусом authorized.

# Design

Платёжное ядро — домен с повышенными требованиями к корректности, поэтому стандарты выстроены вокруг трёх осей: точность денег, повторяемость операций и наблюдаемость без утечек данных.

Деньги как `f64` — исторически главный источник дефектов в платёжных системах: двоичная плавающая точка неспособна точно представить большинство десятичных дробей, и накопленные ошибки на комиссиях и остатках приводят к расхождению балансов. Отсюда жёсткий выбор в пользу целых minor units (`i64`) или Decimal — и это особенно критично для расчёта комиссии 1% в задаче authorize: операция обязана быть детерминированной и воспроизводимой в копейках.

Платёжные системы ретраят по своей природе: сеть мертва, клиент повторил запрос, брокер доставил сообщение дважды. Без сквозного ключа идемпотентности повтор списания удваивает деньги клиентов. Поэтому mutating-операция без `idempotency_key` невозможна по контракту, а не по соглашению — тип сигнатуры заставляет вызывающего думать о повторах.

Запрет `unwrap`/`panic` в прод-коде вытекает из стоимости простоя: паника в потоке обработки платежа — это прерванная транзакция и разбирательство. Ошибки должны быть управляемым потоком данных. Связка с типизированными enum-ошибками и контрактом `Result<T, DomainError>` делает множество классов сбоев видимым на уровне сигнатуры: компилятор и ревьюер видят, что может пойти не так, а обработка вариантов проверяется исчерпывающим `match`.

Маскирование PAN и ПДн в логах — комплаенс-требование (PCI DSS по сути). Журналирование денежных событий при этом обязательно: без журнала с ключом идемпотентности, суммой и результатом невозможен разбор инцидентов и сверка. Эти два правила применяются совместно — журнал детален по деньгам и слеп по персональным данным.

Запрет глобального мутабельного состояния защищает тестируемость и потокобезопасность: доменное состояние передаётся явно, значит его можно изолировать в тесте и проследить владение. Таймауты на сетевых вызовах и секреты из окружения — операционная гигиена: зависший без таймаута вызов внешней системы блокирует пул потоков, а секрет в коде — компрометация при каждой утечке репозитория.

В задаче authorize эти правила конкретизируются так: сумма приходит в minor units, комиссия 1% считается в целых, операция принимает `idempotency_key`, карты логируются только масками, функция возвращает `Result<Payment, DomainError>`, структура платежа несёт статус `authorized`. Код размещается в одном самодостаточном `src/main.rs`, так как задача локальна и не требует декомпозиции.

# Rules

- Денежные суммы, комиссии, лимиты, остатки — только `i64` (minor units) или Decimal; `f64`/`f32` запрещены.
- Каждая mutating-операция принимает `idempotency_key`; повтор с тем же ключом возвращает сохранённый результат без изменения состояния.
- Запрещены `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`; ошибки — через `Result` с `?` или обработкой.
- В логи не попадают PAN, ФИО, паспортные данные, телефоны, адреса; допустима только маска карты (BIN + последние 4 цифры).
- Ошибки — типизированные enum (thiserror-стиль) с `Display` + `Error`; строковые ошибки (`Err("...")`, `String`, `Box<dyn Error>`) запрещены.
- Запрещены `static mut`, `lazy_static!`, `static ref`, глобальные `static Mutex/RwLock` с доменным состоянием; состояние передаётся явно.
- Любой сетевой вызов выполняется с явным таймаутом.
- Секреты читаются только из `std::env::var`; литералы секретов в коде запрещены.
- Каждое денежное событие журналируется: ключ идемпотентности, сумма в minor units, валюта, результат.
- Публичные функции домена возвращают `Result<T, DomainError>`; набор вариантов ошибки — часть контракта.
- Результат — один самодостаточный файл `src/main.rs`; функция `authorize` p2p-платежа: вход — сумма, номер карты отправителя, номер карты получателя; комиссия 1%; логирование операции; возврат структуры платежа со статусом `authorized`; ответ — только код без пояснений.
