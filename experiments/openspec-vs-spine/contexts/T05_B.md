# Spec

## Требование: Представление денежных сумм
Система ДОЛЖНА хранить и вычислять все денежные суммы (суммы операций, лимиты, накопленные траты) только в minor units как целые `i64` либо через десятичный тип Decimal. Система НЕ ДОЛЖНА использовать `f64`/`f32` для денег, комиссий, лимитов и остатков.

## Требование: Ключ идемпотентности
Каждая mutating-операция (в т.ч. обновление статуса и запись в журнал) ДОЛЖНА принимать обязательный `idempotency_key`. Повторный вызов с тем же ключом ДОЛЖЕН возвращать сохранённый результат без повторного изменения состояния.

## Требование: Отсутствие паник в прод-коде
Продуктовый код НЕ ДОЛЖНА содержать `.unwrap()`, `.expect(...)`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`. Обработка ошибок ДОЛЖНА выполняться только через `Result` с явным пробросом (`?`) или обработкой.

## Требование: Отсутствие ПДн и PAN в логах
Система НЕ ДОЛЖНА записывать в логи и журналы полный номер карты (PAN), ФИО держателя, паспортные данные, телефоны, адреса. Допустима только маска карты (BIN + последние 4 цифры, остальное — `*`).

## Требование: Типизированные ошибки
Ошибки ДОЛЖНЫ быть представлены типизированными перечислениями (enum, вариант на каждый класс сбоя, реализация `Display` + `Error`). Продуктовый код НЕ ДОЛЖНА возвращать ошибки строками (`Err("...")`, `String`, `Box<dyn Error>`).

## Требование: Отсутствие глобального мутабельного состояния
Система НЕ ДОЛЖНА использовать `static mut`, `lazy_static!`, `static ref` и глобальные `static Mutex/RwLock` с доменным состоянием. Состояние ДОЛЖНО передаваться явно (владение, параметры, конструктор).

## Требование: Таймауты на сетевых вызовах
Любой сетевой вызов (HTTP, TCP, очередь) ДОЛЖЕН выполняться с явно заданным таймаутом. Блокирующие вызовы без таймаута НЕ ДОЛЖНЫ применяться.

## Требование: Секреты из окружения
Ключи, пароли, токены ДОЛЖНЫ читаться только из переменных окружения (`std::env::var`). Секреты литералами в коде НЕ ДОЛЖНЫ встречаться.

## Требование: Журналирование денежных событий
Каждое денежное событие ДОЛЖНО журналироваться с указанием: ключа идемпотентности, суммы в minor units, валюты, результата. Журнал ДОЛЖЕН подчиняться запрету на ПДн/PAN.

## Требование: Контракт ошибок публичных функций
Публичные функции домена ДОЛЖНЫ возвращать `Result<T, DomainError>`; набор вариантов ошибки ДОЛЖЕН являться частью контракта функции.

# Design

Движок проверки лимитов — часть платёжного домена, поэтому все организационные стандарты применяются к нему без исключений.

Деньги представлены в minor units (`i64`), поскольку операции сравнения с лимитами и суммирования трат за период требуют точной арифметики; плавающая точка недопустима по стандарту и опасна накоплением погрешности при агрегации трат за день и месяц.

Проверка лимитов — mutating-операция: она пишет результат в журнал и при allow обновляет накопленные траты. Поэтому вход операции включает обязательный `idempotency_key`; движок хранит результаты по ключу, чтобы повторная доставка запроса (типичная для платёжных шин) не приводила к двойному учёту трат и не нарушала корректность лимитов.

Уже потраченное за период хранится явно в структуре состояния движка (конструктор, владение, передача параметрами) — глобальное мутабельное состояние запрещено, а явная передача делает поведение детерминированным и тестируемым без порядка инициализации.

Решение allow/deny с причиной оформлено как типизированный результат: причины отказа — отдельные варианты enum ошибок/причин, а не строки, что делает контракт публичной функции `Result<T, DomainError>` стабильным и машиночитаемым для вызывающей стороны.

Ни одна точка кода не паникует: все разыменования опций и ошибки обрабатываются через `Result` и `?`, так как паника в платёжном ядре — недоступность сервиса.

Журналирование решения включает ключ идемпотентности, сумму в minor units, валюту и результат; карта логируется только маской (BIN + последние 4 цифры) — PAN и прочие ПДн не могут попасть в логи по построению.

Если движок обращается к внешним сервисам (например, за профилем лимитов), каждый вызов снабжён явным таймаутом; секреты для таких вызовов читаются только из `std::env::var`.

Вся логика размещается в одном самодостаточном файле `src/main.rs` на Rust, что соответствует постановке задачи и не противоречит стандартам: инкапсуляция состояния, типизированные ошибки и журнал реализуются внутри файла.

# Rules

- Все суммы — только `i64` (minor units) или Decimal; никаких `f64`/`f32`.
- Mutating-операции принимают обязательный `idempotency_key`; повтор — возврат сохранённого результата без изменения состояния.
- Запрещены `.unwrap()`, `.expect()`, `panic!`, `unreachable!`, `todo!`, `unimplemented!`; только `Result` и `?`.
- В логах: без PAN, ФИО, паспорта, телефона, адреса; карта — только маска BIN + последние 4 цифры.
- Ошибки — типизированный enum (Display + Error); никаких `Err("...")`, `String`, `Box<dyn Error>`.
- Без `static mut`, `lazy_static!`, `static ref`, глобальных `static Mutex/RwLock` с доменным состоянием; состояние — явно.
- Сетевые вызовы — только с явным таймаутом.
- Секреты — только из `std::env::var`, без литералов.
- Каждое денежное событие журналируется: idempotency_key, сумма в minor units, валюта, результат.
- Публичные функции домена возвращают `Result<T, DomainError>`; варианты ошибок — часть контракта.
- Результат — один самодостаточный файл `src/main.rs` на Rust.
