# Spine для агента GigaCode — рабочая инструкция

**Кому:** агенту GigaCode CLI (форк Qwen Code), запущенному в корне проекта
пользователя. Документ написан тебе, агенту: выполняй разделы по порядку и
докладывай человеку по-русски.

**Сверено с:** Spine **v0.4.17** (`releases/latest`, 2026-10-18). Подключение
к qwen-code проверено живыми прогонами на 0.0.5 и 0.24.0; GigaCode CLI
наследует от него `mcpServers`, скиллы и формат `settings.json`.

**Что такое Spine для тебя.** Детерминированный контур архитектурного
контроля без своей LLM: думаешь ты, Spine проверяет. Он даёт MCP-сервер
`spine` (45 инструментов в режиме только чтения), 79 скиллов (из них 12
плейбуков `spine-*`) и CLI `arch-be`. Вердикт контура — код возврата
`arch-be`, а не твоя оценка.

---

## 0. Правила, которые действуют всё время

1. **Ничего не коммить и не пушь** в git проекта, если человек не попросил
   явно. Секреты, ключи и токены не выводи.
2. **SKIP — не PASS.** `INCOMPLETE` (exit 3), `untrusted_skipped`,
   `command_untrusted`, `binding_not_measured` означают «не проверено». Так
   и докладывай; не называй это зелёным.
3. **Не ослабляй контур, чтобы позеленеть.** Не удаляй и не смягчай правила
   `CONSTRAINTS.yaml` (новый `exclude_glob`, пониженный `severity`), не правь
   рубрики, `bound_rules`/`binding_mode`, `ARCHITECTURE-SPINE.md` и файлы
   `.arch-handoff/` ради прохождения гейта. Гейт это ловит (`rule_weakened`,
   `self_approved`, `control_plane_tampered`). Чини код или решение.
4. **Решения человека — только человеку.** Ты не выполняешь
   `arch-be rubric promote` (подпись связки) и `arch-be rubric accept`, не
   пишешь файлы в `reports/human/` и не создаёшь override или ADR, которые
   узаконивают ослабление правила. Ты готовишь всё к решению и называешь,
   что осталось решить человеку.
5. **Если ты автор, ты не независимый судья.** Когда оцениваешь рубрикой код
   или документ, который сам написал в этой сессии, передавай свою модель в
   `author_model` — отчёт пометит `judge_is_author`. Не скрывай это.

## 1. Установка `arch-be`

### 1.1. Платформа и файл релиза

Определи ОС и архитектуру и доложи результат:

```bash
uname -sm                       # Linux/macOS
```

```powershell
$env:PROCESSOR_ARCHITECTURE     # Windows: AMD64
```

Тебе нужна редакция **Core**: MCP-сервер и CLI без собственной LLM и TUI.
Полную редакцию бери, только если человек попросил TUI.

| `uname -sm` / Windows | Core (берёшь это) | Полная (только по просьбе) |
|---|---|---|
| `Linux x86_64` | `arch-be-core-linux-x86_64` (21 МБ) | `arch-be-linux-x86_64` |
| `Linux aarch64` / `arm64` | `arch-be-core-linux-aarch64` (18 МБ) | `arch-be-linux-aarch64` |
| `Darwin arm64` | `arch-be-core-macos-arm64` (18 МБ) | `arch-be-macos-arm64` |
| Windows `AMD64` | `arch-be-core-windows-x86_64.exe` (25 МБ) | `arch-be-windows-x86_64.exe` |

Готового файла нет (Intel-Mac, Windows arm64, *BSD) — **не выдумывай имя
файла**: иди вариантом Б или В ниже.

### 1.2. Бинарь

Если `command -v arch-be` находит бинарь и `arch-be --version` ≥ 0.4.17 —
используй его. Версия ниже 0.4.17 — обнови тем же способом: связки
«критерий ↔ правило» (раздел 6) появились в 0.4.17.

**Вариант А — готовый бинарь из релиза** (подставь имя файла из 1.1):

```bash
F=arch-be-core-linux-x86_64
BASE=https://github.com/romannekrasovaillm/spine-bank/releases/latest/download
curl -LO "$BASE/$F" && curl -LO "$BASE/SHA256SUMS"
sha256sum --check --ignore-missing SHA256SUMS      # macOS: shasum -a 256 "$F"; grep "$F" SHA256SUMS
chmod +x "$F" && mkdir -p ~/.local/bin && mv "$F" ~/.local/bin/arch-be
```

Windows (PowerShell): `curl.exe -LO <BASE>/arch-be-core-windows-x86_64.exe`
и `SHA256SUMS`, сверь `Get-FileHash arch-be-core-windows-x86_64.exe
-Algorithm SHA256` со строкой файла в `SHA256SUMS`, переименуй в
`arch-be.exe` и положи в каталог из `PATH`. **Хэш не сходится — стоп**: не
запускай бинарь, доложи человеку.

**Вариант Б — сборка из локального клона Spine** (путь спроси у человека,
если он не назван):

```bash
cd <ПУТЬ_К_КЛОНУ> && cargo build --release --no-default-features --features core
cp target/release/arch-be ~/.local/bin/
```

Тулчейн закреплён `rust-toolchain.toml`, rustup подтянет его сам.

**Вариант В — закрытый контур, офлайн-бандл.** Если человек дал
`spine-offline-*.tar.gz`:

```bash
tar xzf spine-offline-*.tar.gz && cd spine-offline-* && ./install.sh
```

Внутри бинарь, движок Archify и `SHA256SUMS`; ассеты встроены в бинарь, сеть
не нужна.

Проверка: `arch-be --version` → `arch-be 0.4.17` (или новее).

## 2. Подключение к GigaCode

### 2.1. MCP-сервер и скиллы

В корне проекта:

```bash
arch-be connect gigacode --rw=reports
```

Что делает команда (сливает с существующими настройками, ничего не
затирает):

- выбирает каталог настроек: существующий `.gigacode/`, иначе существующий
  `.qwen/`, иначе создаёт `.gigacode/`;
- пишет в `<каталог>/settings.json` сервер
  `"spine": {"command": "arch-be", "args": ["mcp", "serve", "--rw=reports"]}`;
- раскладывает 79 скиллов в `<каталог>/skills/`;
- пишет провенанс в `.arch-handoff/connect-manifest.json`.

Хуки команда **не пишет**: у GigaCode нет подтверждённой схемы
блокирующих хуков (раздел 3). Посмотреть план без записи —
`arch-be connect gigacode --rw=reports --dry-run`.

**Режим записи MCP** — выбирай осознанно и доложи, какой записал:

| Флаг | Что доступно | Когда |
|---|---|---|
| без флага | 45 инструментов, только чтение | разбор и проверки без сохранения отчётов |
| `--rw=reports` (рекомендуется) | те же 45 + сохранение отчётов `rubric_verify` в `reports/rubric/` и архив в `~/.arch-harness/reports/` | смысловые рубрики, которые должен увидеть гейт |
| `--rw` | 56: плюс `adr_new`, `handoff_create`, `delta_propose`, `evidence_pack`, `lessons_record` и др. | только если человек попросил агентные записи |

> **Известная особенность 0.4.17.** В режиме `--rw=reports` сервер
> показывает в списке инструментов и пишущие инструменты моста (`adr_new`,
> `handoff_create`, `delta_propose`, `evidence_pack`, `agentsmd_generate`,
> `archify_show`, `archify_deliver`, `archify_compare`, `reverse_survey`,
> `rule_template_apply`), но вызов отклоняет с ошибкой «неизвестный
> инструмент». **Не вызывай их в этом режиме.** Если они нужны — попроси
> человека разрешить `--rw`.

Never-список (`bash`, `write_file`, `edit_file`, `subagent_*`, `web_*`)
закрыт в любом режиме — это твои собственные инструменты, не Spine.

### 2.2. Одобрение и перезапуск

- Qwen Code ≥ 0.24 требует одобрить project-сервер: `qwen mcp approve spine`
  (в GigaCode — аналог твоей сборки) или подтверди диалог при следующем
  интерактивном запуске.
- Одобрение действует **со следующей сессии**: если инструменты `spine` в
  текущей сессии не появились, скажи человеку перезапустить GigaCode в этом
  каталоге.
- Статус: `qwen mcp list` → `spine … Connected` (или аналог твоей сборки).

### 2.3. Механическая проверка

```bash
arch-be doctor --host gigacode
```

Ожидается: `✓ arch-be в PATH`, `✓ settings … (rw=reports)`, `✓ skills … 79
скиллов`. Предупреждение `⚠ host gigacode не найден в PATH` допустимо, если
твоя сборка называется иначе; доложи его. Код выхода 1 — разбери находку
до продолжения.

## 3. Гейт: что блокирует, а что нет

У GigaCode (как у qwen-code 0.24) хуки управляются через `qwen hooks` (UI)
и в headless-режиме не срабатывают. Поэтому **Stop-хука, который
остановил бы тебя на красном гейте, здесь нет** — дисциплину держишь ты.

1. **Перед тем как объявить задачу выполненной**, запусти:

   ```bash
   arch-be gate . --route auto
   ```

   | Код | Итог | Что ты делаешь |
   |---|---|---|
   | 0 | PASS | можно докладывать о готовности |
   | 1 | FAIL | чини находки и перезапускай; готовность не объявляй |
   | 3 | INCOMPLETE | обязательная проверка не выполнена — назови человеку, какая и почему |

   Что значит зелёный и чего он не гарантирует: `arch-be gate . --explain`
   (паспорт вердикта) — приложи к докладу его блок «не проверено».

2. **Блокирующий гейт без хуков хоста — git-хуки.** Предложи человеку и
   выполни **только с его согласия** (пишет в `.git/hooks/`):

   ```bash
   arch-be connect git-hooks          # pre-commit: control check; pre-push: gate
   ```

3. **Информационный хук** (необязательно, если твоя сборка поддерживает
   hooks): в `<каталог>/settings.json`

   ```json
   "hooks": {"SessionEnd": [{"hooks": [{"type": "command",
     "command": "arch-be gate --route auto 2>&1 | tail -3"}]}]}
   ```

   Он показывает вердикт, но **не блокирует** завершение — так и скажи
   человеку.

## 4. Проверка подключения (обязательна)

Вызови MCP-инструменты и доложи результаты:

1. `fitness_check` с `{"path": "."}` — `passed`, число находок.
   - `untrusted_skipped` / `command_untrusted` ожидаемы: под MCP правила
     `command_succeeds` не исполняются, пока доверие не подтверждено.
     Предложи человеку `arch-be rules allow` (отпечаток набора команд;
     правка реестра требует повторного доверия) или `ARCH_NO_EXEC=0` в
     окружении сервера. Сам доверие не подтверждай. CLI
     `arch-be control check .` исполняет команды по умолчанию.
2. `skill_search` с `{"query": "saga"}` — перечисли три найденных скилла.
3. `trace_check` с `{"path": "."}` — если нет каталога `model/`, скажи об
   этом: это не ошибка, а пустой проект (раздел 7).
4. `model_query` с `{"path": "model"}` — состав модели, если она есть.

## 5. Работа в задаче под контуром

**В начале изменения:**

- `significance_from_diff` с `{"path": "."}` — маршрут (Fast / Standard /
  Critical) и источник каждого триггера. Маршрут выводится из диффа, а не
  из твоей оценки; заявленные триггеры могут только поднять маршрут.
- `architect_review` с `{"path": "."}` — сводное ревью (маршрут, fitness,
  спайн, трассировка, NFR, контракты); `change_impact` — с кем согласовывать.

**По ходу работы:**

- После правок кода — `fitness_check` с `{"path": "."}`. Находка несёт
  задетый инвариант `AD-*`, `rationale`, `fix_hint` и имя скилла для
  исправления (`skill_load`).
- Контракты API — `openapi_lint`, `asyncapi_lint`, `contract_diff`
  (ломающее изменение — находка).

**В конце:** `arch-be gate . --route auto` (раздел 3) и доклад.

## 6. Смысловые рубрики и связки «критерий ↔ правило» (0.4.17)

Правило `CONSTRAINTS.yaml` видит текст и конструкцию, рубрика — смысл. В
0.4.17 они связываются в одну fitness-функцию (ADR-093): исход правила лежит
в досье, которое ты судишь, и гейт сверяет твой вердикт с измерением.

### 6.1. Перед оценкой — отдай измерения в досье

```bash
arch-be control check . --export-detectors
```

Пишет исход каждого правила в `reports/detectors/rules/<id>.json` (`pass` /
`fail` / `warn` / `skip` / `na` / `overridden`). Делай это **перед**
`rubric_prompt` по досье и **после** правок кода: смена исхода правила
обесценивает отчёт (`semantic_report_stale`). Повторный экспорт того же
исхода отчёт не обесценивает.

### 6.2. Оценка рубрикой (split-judge: судишь ты, Spine сверяет)

1. `rubric_prompt` с `{"rubric": "<имя>", "pack": "<вид>", "subject":
   "<субъект>"}`. Виды досье: `adr_vs_spine`, `entity_links`,
   `nfr_mechanism`, `code_vs_spine`, `solution_vs_standards`,
   `code_vs_scenarios`. Для документа без досье —
   `{"rubric": "<имя>", "target": "<путь>"}`.
2. Выполни выданный промпт **k раз** (k — `judge_config.samples` из ответа)
   **независимо**: каждый ответ — с нуля, не переписывая предыдущий. Каждый
   ответ — строго JSON по `response_json_schema`, цитаты — дословно из
   досье.
3. `rubric_verify` с тем же `rubric` / `pack` / `subject`; `answers` —
   массив сырых ответов строками; `judge_model` — твоя фактическая модель;
   `author_model` — если автор ты (правило 5).
4. Доложи решение (`pass` / `fail` / `human`) и метки. Источник роли
   `detector` в досье — **измерение, а не мнение**: если правило красное, а
   ты ставишь «нарушения нет», отчёт получит `detector_contradiction`, и
   гейт отдаст решение человеку на любом маршруте. Это не ошибка
   инструмента — объясни человеку расхождение.

Порядок по шагам — плейбук `spine-semantic-judge`.

### 6.3. Связки: читать и готовить, но не подписывать

```bash
arch-be rubric bindings --judge <твоя-модель>
```

Показывает для каждого критерия со связкой режим (`advisory` / `blocking`),
правила и роли (`necessary` / `evidence`), подпись, теневые прогоны и что
мешает подписи.

| Находка гейта | Что означает | Что ты делаешь |
|---|---|---|
| `binding_rule_failed` | необходимое правило красное для субъекта — критерий провален измерением | чини код или решение; оспаривать правило рубрикой бесполезно |
| `binding_contradiction` | правило красное, а судья поставил ≥ 3 | перепроверь вердикт по детектору в досье; расхождение решает человек |
| `binding_not_measured` | правило не прогонялось (нет ресурса, доверия, реестра) | назови причину; не выдавай за PASS |
| `binding_rule_toothless` | необходимое правило зелёное, но зубья не подтверждены | предложи человеку `arch-be rules teeth . --save` |
| `binding_rule_unknown` | связка указывает на правило, которого нет в реестре | доложи: это ошибка конфигурации рубрики, сам не исправляй |
| `binding_unsigned` | связка объявлена блокирующей, но не подписана — работает как советующая | доложи теневые цифры из детали `semantic_quality` |
| `binding_unqualified` | блокирующая связка, а судья не прошёл квалификацию | назови причину; квалификация — `arch-be rubric qualify` по решению человека |

Подготовить подпись ты можешь: `arch-be rules teeth . --save`, повторный
`--export-detectors`, `rubric bindings`. **Подписывает человек:**
`arch-be rubric promote <рубрика> <критерий> --judge <модель> --by "Имя
<адрес>"`. Эту команду ты не запускаешь (правило 4).

Досье ровно таким, каким его видят судья и гейт:
`arch-be rubric pack <вид> <субъект> --rubric <имя>`.

### 6.4. Инварианты без правила

Если у сущности `AD` в `model/` стоит `unverifiable`, предложи человеку
закрыть её смысловой проверкой: `judged_by: [<рубрика>#<критерий>]` во
frontmatter. `trace_check` возвращает поле `ad_matrix` — матрицу «AD ×
{правило, рубрика}» со статусами `правило`, `рубрика`, `правило+рубрика`,
`без охраны`, `не покрыт`. Инварианты `без охраны` перечисли в докладе.

## 7. Пустой проект: наполнение контура

Слоя `banking/` в публичном Spine нет — спайн, правила и модель проекта
создаёшь ты по просьбе человека. В **пустом** каталоге проекта быстрее всего
каркас:

```bash
arch-be bootstrap "<название кейса>" --dir . --domain <домен>
arch-be bootstrap --status --dir .     # следующая красная находка и подсказка
```

Каркас намеренно красный: заглушки автора ловятся гейтом. Вручную — по
шагам (шаблоны — в клоне Spine: `кейсы/*/handoff-example/`,
`assets/rubrics/`):

1. `ARCHITECTURE-SPINE.md` — 2–4 инварианта: `## AD-N: <название>` +
   `Binds` / `Prevents` / `Rule`.
2. `CONSTRAINTS.yaml` в корне — правила с `id`, `ad:` (какой инвариант
   охраняют), `rationale`, `fix_hint`.
3. `model/` — сущности с frontmatter: `REQ-…`, `NFR-…` (`verification` или
   `verified_by`), `CMP-…` (`implements: [AD-…]`), `AD-…`
   (`verified_by: [C-NN]` или `unverifiable: <обоснование>` и, где можно,
   `judged_by`).
4. `knowledge/` — заметки проекта и строка `[knowledge] dirs = ["knowledge"]`
   в `arch-harness.toml`. `kb_search` — BM25 по дословным токенам: пиши
   термины явно (по-русски и по-английски).
5. Проверка: `fitness_check`, `trace_check`, `kb_search`, `model_query` —
   доложи вердикты.

Порядок с примерами — плейбук `spine-content-bootstrap`.

## 8. Плейбуки `spine-*`

MCP даёт инструменты, плейбук — метод: в каком порядке вызывать и где
границы. Десять из них сервер отдаёт ещё и как MCP-промпты (`prompts/list`);
файлы — `<каталог>/skills/<имя>/SKILL.md`. Прочитай плейбук перед задачей
своего типа.

| Плейбук | Когда читать | MCP-промпт |
|---|---|---|
| `spine-quickstart` | подключение и диагностика: не видишь инструменты, approve, доверие | да |
| `spine-content-bootstrap` | пустой проект: спайн, правила, модель, знания | да |
| `spine-architect-review` | разбор проекта: маршрут, модель, трассировка | да |
| `spine-fitness-gate` | работа с кодом под гейтом: находки, починка, перепроверка | да |
| `spine-contracts-gate` | перед релизом API: линт и дифф контрактов | да |
| `spine-adr-judge` | оценка ADR/документа рубрикой | да |
| `spine-semantic-judge` | смысловые рубрики: субъекты → досье → k ответов → verify → гейт | да |
| `spine-judge-handover` | передача судейства второму судье и приёмка | да |
| `spine-bundle` | Evidence Bundle под маршрут изменения | да |
| `spine-archify-viz` | «нарисуй архитектуру»: JSON IR → проверки → HTML | да |
| `spine-invariants` | спайн инвариантов для параллельных исполнителей | нет |
| `check-spine-be-docs` | вопросы о самом Spine — отвечай по документации, а не по памяти | нет |

## 9. Визуализация (Archify)

Нужен Node.js ≥ 18 и движок из клона Spine (`vendor/archify/`; в
офлайн-бандле он уже внутри). Попроси человека добавить в `arch-harness.toml`
проекта:

```toml
[archify]
cli_path = "<путь-к-клону-spine>/vendor/archify/bin/archify.mjs"
```

Дальше: пишешь JSON IR (`diagrams/*.architecture.json`) →
`archify_validate` (9 проверок, точечные исправления по `supportedFixes`) →
`archify_show` (требует `--rw`). Порядок — плейбук `spine-archify-viz`.

## 10. Если что-то пошло не так

| Симптом | Что ты делаешь |
|---|---|
| `releases/latest/download/…` отдаёт 404 | сверь имя файла с таблицей 1.1; для платформы без файла — вариант Б или В |
| SHA256 не сходится | не запускай бинарь; перекачай бинарь и `SHA256SUMS` из одного релиза; снова не сходится — стоп и доклад |
| `arch-be --version` ниже 0.4.17 | обнови бинарь (1.2); без этого нет раздела 6 |
| инструментов `spine` нет в сессии | `qwen mcp list`; `Pending approval` → `qwen mcp approve spine`; одобрено — нужен перезапуск GigaCode |
| `command -v arch-be` пусто | положи бинарь в каталог из `PATH` (`~/.local/bin`) и перезапусти сессию |
| вызов инструмента: «неизвестный инструмент» | ты в `--rw=reports` и вызвал пишущий инструмент моста (2.1) — не вызывай или попроси `--rw` |
| гейт `INCOMPLETE`, находки `command_untrusted` | правила `command_succeeds` под MCP не исполняются: предложи `arch-be rules allow` или `ARCH_NO_EXEC=0` |
| `rubric_verify` ответил `artifact_saved: false`, гейт пишет `semantic_report_missing` | сервер подключён только на чтение: попроси переподключить `arch-be connect gigacode --rw=reports` |
| `semantic_report_stale` | изменился источник досье (код, спайн, исход правила): повтори `--export-detectors` и оценку |
| находки `binding_*` в гейте | раздел 6.3 |
| хук не срабатывает | ожидаемо для GigaCode (раздел 3); блокирующий вариант — `arch-be connect git-hooks` с согласия человека |
| 404 по модели GigaCode на openai-совместимом бэкенде | модель задаётся переменной `OPENAI_MODEL`, а не флагом `-m` |

## 11. Итоговый доклад человеку

Одной сводкой:

1. Платформа и выбранный файл релиза (или вариант установки), версия
   `arch-be`.
2. Каталог настроек (`.gigacode/` или `.qwen/`), режим записи MCP (только
   чтение / `rw=reports` / `rw`), статус `spine` (Connected / нужен approve /
   нужен перезапуск), число скиллов.
3. `doctor --host gigacode`: проблемы и предупреждения.
4. Гейт: вердикт `fitness_check` и `arch-be gate . --route auto`; что не
   проверено (SKIP / INCOMPLETE) и почему.
5. Что осталось решить человеку: доверие к командам (`rules allow`),
   git-хуки, режим `--rw`, подписи связок (`rubric promote`), квалификация
   судьи.

Ничего не коммить. Секреты не выводить.
