# Мутационное тестирование архитектурного пакета (`arch-be redteam`)

```bash
arch-be redteam кейсы/digital-ruble-merchant
arch-be redteam <кейс> --format json      # машинный отчёт
arch-be redteam <кейс> --format markdown  # таблица для отчёта
arch-be redteam <кейс> --min-detection 0.9
arch-be selftest --redteam <кейс>         # вместе с метаморфными инвариантами
```

Отвечает на вопрос, который архитектор не может задать вручную: **насколько
мой пакет вообще защищён правилами?** Команда клонирует кейс во временный
каталог, засеивает по одному дефекту из каталога [`MUTATORS`] (26 позиций —
14 из таблицы раздела 7 ТЗ 0.3.4 и 12 отдельных строк: R, D14, D15, D16/D17,
D18 и кодовые D19–D24), гоняет гейт маршрута
Critical и печатает **карту обнаружения**: что поймано, кем именно, и что не
поймано никем.

## Что инструмент гарантирует

- **read-only к исходному кейсу** — вся работа идёт в копии во временном
  каталоге, которая удаляется на выходе, включая git-репозиторий мутанта;
- **без сети и без LLM** — только детерминированный контур контроля (AD-2);
- **детерминированность** — порядок мутаторов фиксирован, результат не зависит
  от времени и абсолютных путей;
- **честность** — дефекты, которые механика не должна ловить (D6, D10, D11),
  названы такими в отчёте, а не спрятаны в знаменатель.

## Как считается доля

Знаменатель — **14 позиций раздела 7** ТЗ (D1…D13 + D11b): это критерий
приёмки релиза 0.3.4 «не меньше 11». Вне доли стоят три строки таблицы:

- `R` (ревью `NOT-READY` в бандле) — дефект настоящий и ловится, но в набор
  из 14 не входит;
- `D14` (контроль) — безвредная правка: вердикт обязан остаться зелёным, а
  аттестация — измениться (иначе «зелёный» не привязан к состоянию, Н3);
- `D15` (нарушение инварианта в реализации скелета) — мутант применяется
  только к кейсу с `.arch-handoff/rule-templates.lock`: эталонная реализация
  применённого шаблона подменяется нарушающей из той же библиотеки, и дефект
  обязан поймать `fitness` (правило `command_succeeds` краснеет; вердикт
  видит это падение только при `severity: error` — правило, оставленное
  предупреждением, краснеет, но составляющая `fitness` гейта не падает, и
  карта честно печатает «не пойман» — это утверждение о решении кейса, а не
  о механике). Он меряет не
  защищённость пакета, а **зубы взятого шаблона** — качество реестра, поэтому
  в знаменатель раздела 7 не входит: иначе критерий «≥ 11 из 14» перестал бы
  сравниваться с ТЗ. Кейсу без лока мутатор не подходит — он печатается как
  `пропущен: нет .arch-handoff/rule-templates.lock …` (см. ниже).

Из знаменателя исключаются мутаторы, которым **не нашлось входа** в кейсе
(`пропущен: …`): неподходящий кейс должен выглядеть «непроверенным», а не
«незащищённым». Семантический дефект, пойманный по ошибке, долю **не
поднимает** — числитель считает только те позиции, что обязаны ловиться.

## Кодовый слой: D18 и корпус реальных нарушений (D19–D24)

Волна B/E 0.3.14 (ADR-065): текстовое правило не ловит удалённую проверку,
если слово осталось в комментарии, и большинство эталонных кейсов вообще не
имеет правил на код. Два дополнения меряют именно это, обе — отдельные строки
вне знаменателя доли:

- `D18` (B2) — лексический обход: в коде скелета проверка удаляется, а
  ключевое слово `pattern` остаётся в комментарии. На кейсе, где инвариант
  охраняет только `must_contain`, — честное «не пойман и не должен»
  (`Semantic`); на кейсе с правилом из шаблона (ADR-050) тест падает —
  `Caught`. Ожидание вычисляется по составу правил кейса на мутанте.
- `D19`–`D24` (E1) — классы корпуса реальных нарушений агентов
  (`experiments/openspec-vs-spine/`, 180 генераций): деньги в f64, `unwrap` в
  денежном пути, ошибки строками, персональные данные в логах, секрет
  литералом, обработчик без ключа идемпотентности. Ожидание динамическое:
  правило класса дефекта (error-severity `must_not_contain` по содержимому
  либо `each_file_must_contain` по отсутствию маркера) покрывает файл —
  `Caught`; правила нет — `Semantic` (это утверждение о реестре кейса, а не о
  механике). warn-правило поимкой не считается: оно не краснит гейт.

## Две доли вместо одной (E2)

Суммарная доля (порог `--min-detection`, дефолт 78 %) считается по набору
раздела 7, как прежде. Рядом отчёт, `--format json` и запись `--save`
(`arch-be/redteam/v1`, аддитивные поля) показывают долю обнаружения
**отдельно для документов+модели и отдельно для кода** — по дефектам слоя,
которые обязаны ловиться (ожидание `Caught`, без пропусков входа).
Текстовые правила реестра больше не маскируют слепоту к кодовым дефектам:
кейс с долей 79 % по документам и 0 ловимых кодовых дефектов покажет
«код: не измерялась», а не общий зелёный.

Порог кодовой доли — конфигурация `[redteam] min_code_detection` (по
умолчанию не задан — поведение прежнее; значение порога — решение
архитектора). Заданный порог при неизмеренном кодовом слое не проходит:
требование не подтверждено. Обе доли показывает и ступень 4 `arch-be trust`.

## Как мутант готовится

1. копия кейса → свой `git init` → базовый коммит;
2. правка мутатора;
3. **переупаковка evidence-бандла** (`evidence pack --route critical`) —
   иначе любая правка удостоверенного файла краснила бы `evidence_verify` как
   «изменён после упаковки», и дефект ловился бы не тем инструментом, который
   проверяется;
4. коммит правки;
5. `gate --route critical --base HEAD~1` — база нужна, чтобы анти-ослабление
   правил (Н5) видело правку реестра, уже лежащую в коммите.

Контрольный мутант `D14` прогоняется в окружении дельты: перед гейтом в копию
мутанта пишется временная дельта `changes/redteam-control/DELTA.md`, называющая
изменённые защищённые пути (ADR-047). Без неё безвредная правка краснит
`delta_guard` — и контроль падал бы на отсутствии дельты в копии мутанта, а не
на вердикте: на кейсе с заархивированными дельтами это давало «контроль
аттестации: нет» при доле выше порога и минус ступень доверия. Дельта живёт
только в копии мутанта; исходный кейс не трогается.

Эталон (кейс без правок) прогоняется первым: **не зелёный кейс — честная
ошибка**, а не «0 % обнаружения». На красном эталоне нельзя отличить «дефект
пойман» от «пакет уже сломан».

## Эталонный прогон: кейс ТСП

`кейсы/digital-ruble-merchant` — контур приёма оплаты цифровым рублём для
ТСП, маршрут Critical (9 инвариантов, 13 правил, 7 ADR, 51 сущность модели).
Результат на ветке `release/0.3.4`:

```
Доля обнаружения: 11/14 = 79% (порог 78%) · контроль аттестации: да
```

В кейсе нет применённых шаблонов, поэтому строка `D15` печатается как
`пропущен: нет .arch-handoff/rule-templates.lock …` — неподходящий кейс
выглядит «непроверенным», а не «незащищённым», и доля от этого не меняется.

Полная карта — `кейсы/digital-ruble-merchant/red-team/RESULTS.md`.

## Смысловой слой: отдельная строка, а не доля (ADR-051)

Три класса дефектов — `D6` (ссылка ведёт «не на ту» сущность), `D10` (решение
противоречит инварианту при формально верном тексте), `D11` (код нарушает
инвариант, правила на этот код нет) — помечены `Expectation::Semantic`:
механика их не ловит **по построению**, и в долю обнаружения они входят как
«не пойман и не должен». Это честно, но бесполезно ревьюеру: класс назван, а
инструмента для него не было.

Теперь у каждого такого мутатора в карте обнаружения есть колонка **«смысловая
рубрика»** — какой рубрикой класс ловится судьёй:

| Мутант | Рубрика | Досье |
|---|---|---|
| `D6` | `model_link_semantics` | `entity_links` |
| `D10` | `adr_spine_consistency` | `adr_vs_spine` |
| `D11`, `D11b` | `code_invariant_conformance` | `code_vs_spine` |

**Судит модель хоста, а не харнесс** — в ядре LLM нет (AD-2). Поэтому прогон с
`--keep-semantic <каталог>` сохраняет клоны смысловых мутантов и кладёт рядом
`SEMANTIC-TODO.json` с заданием: мутант, рубрика, вид досье, субъект.

```bash
# 1. Прогон с сохранением клонов (доля обнаружения считается как раньше)
arch-be redteam кейсы/salary-payments --keep-semantic /tmp/semantic

# 2. В каждом клоне — судья моделью хоста (rubric_prompt → k ответов →
#    rubric_verify под --rw; отчёт ляжет в reports/rubric/ клона)

# 3. Смысловая строка
arch-be redteam semantic-score /tmp/semantic
# смысловой слой: поймано 2 из 4; судья: claude-sonnet-5; независим: да
```

Пойман — главный критерий рубрики (`blocking: true`) с баллом ≤ 2 **и**
подтверждённым обвинением: отчёт без цитат механика сама исключает из итога
(`accusation_unconfirmed`), и засчитывать это поимкой значило бы записывать
судье в заслугу выдуманное свидетельство. Отчёт сверяется с досье по хэшу:
досье изменилось после оценки — вердикт «отчёт устарел», а не «пойман».

**Смысловая строка не входит ни в долю обнаружения, ни в порог 78 %.** Она
отвечает на другой вопрос: не «сколько классов защищено механикой», а
«работает ли суждение там, где механика бессильна». Числа приёмки 0.3.5 —
«11 из 14», и `--keep-semantic` их не меняет.
