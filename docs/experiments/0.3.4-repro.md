# 0.3.4 — журнал воспроизведения находок

Правило ТЗ 1.1: каждая находка сначала воспроизводится на версии 0.3.3
(коммит `9486d79`, релизный бинарь), и только потом чинится. Что не
воспроизвелось — не чинилось и записано ниже.

Стенд: `arch-be 0.3.3`, собранный из `9486d79` (`cargo build --release`),
Linux x86_64, git 2.43.0. Песочницы — во временных каталогах, клоны кейсов из
`кейсы/`.

## Н1. Бандл проверяет наличие файла, а не содержание

```bash
mkdir -p /tmp/repro-h1/docs/adr && cd /tmp/repro-h1 && git init -q .
git config user.email t@t.t && git config user.name t
echo TODO > docs/DECISION.md
echo TODO > WALKING-SKELETON.md
printf '# R\n\nVERDICT: NOT-READY\n' > docs/REVIEW.md
echo x > PROBLEM.md; echo x > SPEC.md; echo x > RISK.md; echo x > ROLLBACK.md
echo x > VALIDATION.md; mkdir -p reports && echo x > reports/fitness.md
echo x > ARCHITECTURE-SPINE.md; echo TODO > docs/adr/ADR-001.md
printf '{"result":"PASS","baseline":"TODO"}\n' > .arch-handoff/REHEARSAL.json
printf 'baseline: TODO\n' > ROLLBACK.yaml
mkdir -p .arch-handoff   # в исходной репродукции — до записи REHEARSAL.json
arch-be evidence pack . --route critical
arch-be evidence verify .
```

0.3.3:

```
Проверка bundle (Critical): артефактов 13, отсутствует 0, изменено 0
Итог: PASS — выпуск разрешён
exit 0
```

13 обязательных артефактов «на месте», хэши сходятся — и зелёный вердикт
удостоверяет наличие файлов, а не записанное решение. Ревьюер написал
`NOT-READY`, механика ответила «выпуск разрешён».

**Важная деталь репродукции.** С первого раза воспроизвелось не полностью: без
`docs/adr/ADR-001.md` и `.arch-handoff/REHEARSAL.json` бандл падал по
*отсутствию* двух артефактов (`Итог: FAIL — выпуск заблокирован`), то есть
проверка полноты работала и маскировала дефект. Нужен был ПОЛНЫЙ набор
заглушек — тогда дефект виден в чистом виде.

После правки (0.3.4): `Итог: FAIL — выпуск заблокирован`, exit 1, с находками
`evidence_stub` (walking_skeleton, adversarial_review, rollback_rehearsal,
validation, fitness_report) и `review_not_ready`.

## Н2. `gate` не включает целостность модели

```bash
cp -r кейсы/011-digital-ruble-programmable /tmp/repro-h2 && cd /tmp/repro-h2
git init -q . && git add -A && git commit -qm base
sed -i 's/depends_on: \[CMP-003, CMP-005\]/depends_on: [CMP-099, CMP-005]/' \
    model/CMP-002-orchestrator-operaciy-cr.md
git add -A && git commit -qm "broken link"
arch-be model validate model   # FAIL: broken-link CMP-099
arch-be gate --route auto      # PASS, exit 0
arch-be review .               # FAIL: model_validate
```

0.3.3: `gate` PASS, exit 0 при `model validate` FAIL и `review` FAIL. Битая
ссылка прошла бы pre-push и Stop-хук.

Отдельная деталь: до коммита правки `gate` всё же краснел — но по
`delta_guard` («правка спайна мимо дельты»), а не по целостности модели. То
есть дефект виден только на закоммиченном изменении (как и в ТЗ).

После правки: `[FAIL] model_validate — сущностей: 92, находок: 1 (error: 1)`,
итог FAIL, exit 1.

## Н3. Аттестация не различает состояния репозитория

```bash
cd /tmp/repro-h2   # после отката битой ссылки
arch-be gate --route fast --format json | jq -r .attestation
# sha256:3128b48ec0b3e06dc8322913e77a5b27f6a35e97e046d38acfeae27ba4abf8ee
sed -i '1s/$/ /' model/CMP-013-arbitrazh.md && git add -A && git commit -qm cosmetic
arch-be gate --route fast --format json | jq -r .attestation
# sha256:3128b48ec0b3e06dc8322913e77a5b27f6a35e97e046d38acfeae27ba4abf8ee  ← та же
```

Совпадение подтверждено (значение воспроизводится в `gate` тесте
`attestation_changes_when_model_changes`). Причина — во входы входил только
хэш реестра правил, а состав конверта — имена и статусы составляющих; находки
не входили вовсе.

## Н4. `delta guard` и git-индекс

Репродукция сделана тестами (в 0.3.3). Обе половины — по коду и по факту:

- **(а)** `guard` строил список изменённых файлов только из
  `git diff --name-only <base>`; неотслеживаемые файлы git-diff не показывает.
  Новый `model/AD-009-*.md` до `git add` давал PASS, после — FAIL.
  Тест `guard_sees_untracked_protected_files`.
- **(б)** `delta_mentions` матчил стем подстрокой: упоминание `model/NFR-005`
  при файле `model/NFR-005-recovery-rto-rpo.md` не засчитывалось (нужен полный
  путь), а `NFR-0051` ложно «покрывал» `NFR-005.md`.
  Тесты `guard_accepts_entity_id_mention`, `guard_does_not_match_id_substring`.

## Н5. Ослабление правила после коммита не видно хукам

Репродукция сделана интеграционным тестом
`tests/cli.rs::pre_push_hook_rejects_committed_rule_weakening`: bare-remote,
правило `spine_present` понижено с `error` до `warn` и закоммичено, правка
покрыта активной дельтой (чтобы красным стало именно `rule_weakened`, а не
`delta_guard`). Контрольная точка в том же тесте: `arch-be gate --route auto`
**без хука** даёт PASS — это и есть дефект 0.3.3. Через pre-push пуш отклоняется,
вывод называет `rule_weakened` и «severity понижен».

## Н6. `control gate A4` без handoff-пакета

Воспроизвелось **частично**, и это важно зафиксировать.

**Что воспроизвелось.** На каталоге с пустым `.arch-handoff/`:

```
$ arch-be control gate A4 .
Error: io: ./.arch-handoff/MANIFEST.json: No such file or directory (os error 2)
exit 1
```

Отказ файловой системы вместо находки архитектурного процесса — да.

**Что НЕ воспроизвелось.** Стектрейс. `RUST_BACKTRACE` в окружении не выставлен,
и `anyhow` печатает `Stack backtrace:` только при `RUST_BACKTRACE=1`:

```
$ RUST_BACKTRACE=1 arch-be control gate A4 .
Error: io: ./.arch-handoff/MANIFEST.json: No such file or directory (os error 2)
Caused by: No such file or directory (os error 2)
Stack backtrace:
   0: <unknown>
   ...
```

Это **желаемое** поведение (ТЗ прямо просит «оставь его под
`RUST_BACKTRACE=1`»), а не дефект. Поэтому «убрать backtrace из
пользовательских ошибок» отдельной правкой не делалось — нечего было чинить.
Тест `a4_without_manifest_is_a_finding_not_io_error` закрепляет границу: с
явно снятым `RUST_BACKTRACE` в выводе нет ни `Stack backtrace`, ни `io:`.

Также проверено: на каталоге вовсе без `.arch-handoff/` 0.3.3 отвечала внятной
ошибкой (`ни handoff-пакет (нет MANIFEST.json), ни репозиторий с
.arch-handoff/`), тоже без стектрейса. Дефект — только у ветки с существующим,
но неполным `.arch-handoff/`.

## Н7. Оценка качества решений живёт вне гейта

Часть про «гейт пропускает ADR с 1,30» воспроизведена по коду: в 0.3.3 в
`gate` нет ни одной составляющей, читающей рубричный отчёт; `docs/adr/ADR-*.md`
упоминается только в необязательном правиле `adr_practice` (репозитория) и в
`adr_registry` (формат прозы). Прогон судьи не оставляет машиночитаемого
следа: `rubric run` пишет markdown в `paths.reports_dir`, MCP `rubric_verify`
отвечает JSON в протоколе — файла, который переживёт сессию и попадёт в гейт,
нет.

Живая проверка «картонного» ADR (D9) на 0.3.3 не проводилась — отмечено в
`0.3.4-что-сделано.md` как несделанное.

## Ограничения этого журнала

- Все репродукции — на одной машине и одном коммите; внешние харнессы
  (Claude Code / OpenClaw / Qwen Code) в прогонах не участвовали, как и в
  исходном исследовании (оговорка приложения к ТЗ).
- Н4 и Н5 воспроизведены тестами, а не ручными shell-сессиями: обе половины
  Н4 — по коду 0.3.3, воспроизведение закреплено падающими до правки тестами.
- Н7 воспроизведена по коду; численный прогон рубрики 1,30 против 3,90 взят из
  ТЗ (значения исследовательского прогона), а не измерен заново.

## Н12. Реестр правил в подкаталоге сверяется с корневым (найдена при W3)

Найдена при работе над новым кейсом: `control check` на кейсе внутри
репозитория краснел.

```bash
cd <репозиторий Spine>
arch-be control check кейсы/digital-ruble-merchant
# [error] …/CONSTRAINTS.yaml:0 rule_weakened — правило 'tests_pass':
#         удалено из реестра — правило присутствовало в базовой версии и удалено
```

Воспроизвелось на **трёх** существующих кейсах (`011-digital-ruble-programmable`,
`digital-ruble-merchant`, `salary-payments`) и на 0.3.4 до правки. Причина:
`git show <rev>:<path>` считает путь от корня git-репозитория, а `rule_anchor`
строил его от переданного каталога. Для реестра в подкаталоге путь указывал на
корневой `CONSTRAINTS.yaml`, и каждое правило корня (46 в Spine) выглядело
удалённым.

Дефект был виден только в этом канале: составляющая гейта
(`gate::component_rule_weakened`) использует путь от корня git и на тех же
данных давала PASS. Один вопрос — два ответа.

После правки: `control check кейсы/digital-ruble-merchant` → PASS, с честной
пометкой «в базе файла нет — новый реестр». Тест
`rule_anchor_reads_the_subdirectory_registry_from_the_git_root` падает до
правки и проверяет обе стороны: чужой реестр не при чём, а ослабление **своего**
правила по-прежнему видно.

## Н13. Объявленная схема MCP скрывает поле, которое инструмент принимает

Найдена живым прогоном split-judge по новому кейсу.

```bash
arch-be mcp serve --rw   # вызов rubric_verify с author_model
# {"code":-32602,"message":"rubric_verify: неизвестный аргумент
#  'author_model'; допустимые: answers, judge_model, model, rubric,
#  target, target_text"}
```

`rubric_verify` разбирает `author_model` (Н7, ADR-042: помета «судья судил
свою работу»), но в `inputSchema` его не было. `tools/list` — единственный
опубликованный контракт, поэтому клиент физически не мог выставить поле, а
защитный отсев незнакомых аргументов (Н8) честно отвергал вызов. Итог:
anti-bias проверка была недостижима через MCP, хотя реализация её умеет.

После правки поле объявлено; тест `every_accepted_rubric_argument_is_advertised`
проверяет все семь аргументов инструмента и то, что вызов доходит до разбора.
Правило поверхности записано рядом с `tool_specs`: поле, которое разбирает
реализация, обязано быть в схеме.
