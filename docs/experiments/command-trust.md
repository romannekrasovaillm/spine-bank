# Аудит: кто доходит до исполнения `command_succeeds` (модель доверия A3)

> Аудит перед внедрением модели доверия исполняемых правил (пункт A3 релиза
> 0.3.7, ADR-053). Только разведка, без кода: таблица всех путей, по которым
> CLI-команды, хуки и MCP-инструменты транзитивно доходят до `bash -c
> <command>` из `CONSTRAINTS.yaml` проверяемого репозитория.

**Дата:** 22 сентября 2026
**Стенд:** `arch-be` 0.3.6 (репозиторий `spine-core`, ветка main)
**Единая точка исполнения:** `src/control.rs` `run_rule` (ветка
`RuleKind::CommandSucceeds`) → `run_with_timeout` → `src/proc.rs`
`run_shell` (`bash -c <command>` в корне репозитория, процессная группа — A1).

## 1. Постановка

Правило `command_succeeds` исполняет произвольный bash из файла
`CONSTRAINTS.yaml` проверяемого репозитория. Для своего репозитория это
нормально; для чужого — нет: `arch-be gate` на PR из форка, MCP-сервер у
агента, склонировавшего незнакомый репозиторий, `control check` по кейсу
коллеги. Это та же дыра, что `direnv` без `direnv allow`. Аудит отвечает на
два вопроса: по каким входам чужой репозиторий может достичь исполнения, и
что каждому входу дают два механизма A3 — `no-exec` (флаг/переменная) и
allow-файл `~/.arch-harness/trusted.json`.

Смежные исполнители команд, которые НЕ читают `CONSTRAINTS.yaml`
проверяемого репозитория, вынесены в §4 — они вне контура A3.

## 3. Что дают механизмы A3 (итоговая матрица поведения)

| Сценарий | no-exec | trusted.json | Поведение |
|----------|---------|--------------|-----------|
| CLI, свой репо, без флагов | выкл | файла нет / записи нет / совпадает | исполнение (обратная совместимость, как сегодня) |
| CLI, `--no-exec` или `ARCH_NO_EXEC=1` | вкл | не консультируется (no-exec приоритетнее) | все `command_succeeds` — SKIP `command_untrusted`, команда НЕ запускается; гейт: составляющая `fitness` SKIP → INCOMPLETE (exit 3), если обязательна |
| MCP-сервер, дефолт | вкл (серверный дефолт) | не консультируется | как выше: SKIP `command_untrusted` |
| MCP-сервер, `ARCH_NO_EXEC=0` | выкл | файла нет / записи нет | исполнение (legacy) |
| MCP-сервер, `ARCH_NO_EXEC=0` | выкл | запись совпадает | исполнение |
| любой вход, no-exec выкл | выкл | запись для репо НЕ совпадает | SKIP `command_untrusted` («реестр менялся после доверия») → переподтвердить `arch-be rules allow` |

Семантика allow-файла — TOFU (trust-on-first-use) с защитой от подмены:
запись для репозитория заводится явным `arch-be rules allow` и фиксирует
SHA-256 канонизированного набора command-строк. Отсутствие записи — «как
сегодня» (обратная совместимость: чужие пайплайны не краснеют, пока
механизм не включён явно). Несовпадение записи — реестр менялся после
доверия: исполнение блокируется до повторного `rules allow`.

## 4. Смежные исполнители (вне контура A3)

Эти пути исполняют команды, но НЕ из `CONSTRAINTS.yaml` проверяемого
репозитория; модель доверия A3 на них не распространяется. Фиксируем, чтобы
граница механизма была честной (кандидаты на отдельное ужесточение — не
этот релиз):

| Вход | Что исполняется | Почему вне A3 |
|------|-----------------|---------------|
| `arch-be rules template verify` (`rule_templates::verify`) | команды из `.arch-handoff/rule-templates.lock` кейса (проверка зубов применённых шаблонов) | явный прогон по запросу пользователя; источник команд — лок-файл шаблонов, не реестр правил. На чужом кейсе исполнит чужие команды — кандидат на тот же no-exec позже |
| `arch-be control gate a4 --rehearse` (`rehearsal`) | bash-команды из плана отката handoff-пакета | план пакета — артефакт своего контура, не реестр чужого репо |
| `archunit`-правила реестра (`src/archunit.rs`) | JUnit-консоль с аргументами, собранными arch-be | реестр задаёт параметры (glob, forbid/allow), но не командную строку — произвольного bash нет; раннер фиксирован |
| Инструмент агента `bash` (`src/tools/bash.rs`) | команды, которые просит модель | отдельный контур доверия: политика автономии R0–R5 (`src/policy.rs`), env-scrub; не читает `CONSTRAINTS.yaml` |
| `eval`/`harness` (прогон сьютов, фича `harness`) | команды из ассетов бенчмарков | свои ассеты, свои прогоны |

## 5. Выводы для реализации

1. **Все нити сходятся в одной точке**: `check_with_options` (`src/control.rs`)
   — достаточно одного снимка решения на прогон (паттерн A2: снимок
   `Runner`). Решение вычисляется один раз до цикла правил и пробрасывается
   в `run_rule`; исполнение не начинается, пока доверие не подтверждено.
2. **Проброс по слоям**: CLI-край (`control check`, `gate`, `review`,
   `trust`) строит `ExecPolicy` из флага `--no-exec` и `ARCH_NO_EXEC`;
   MCP-сервер — из `ARCH_NO_EXEC` с дефолтом «вкл»; библиотечные дефолты
   (`CheckOptions::default()`, `GateOptions::default()`) остаются
   детерминированно legacy (AD-7: вердикт не зависит от машины).
3. **Мостовые MCP-инструменты** получают политику через `ToolContext`
   (новое поле `exec`): `architect_review` доходит до `component_fitness`
   через реестр инструментов, иначе серверный дефолт до него не дошёл бы.
4. **Паспорт вердикта** получает находку `command_untrusted` бесплатно:
   блок 3 строится из SKIP-составляющих, а деталь SKIP несёт имена
   пропущенных правил и причину (как `runner_skip_detail` в A2, но
   блокирующий при любом severity — см. ADR-053).
5. **Хуки-файлы (`src/hooks.rs`) и мост `delta_guard`/`openspec_coverage`**
   до исполнения `command_succeeds` не доходят — фиксируем в аудите, чтобы
   будущий читатель не искал там второй контур.
