# Исполняемые инварианты: библиотека шаблонов, детектор на каждый инвариант

- Дата: 2026-09-20
- Ветка: `release/0.3.5` (база `7fe9fc3` + эта работа)
- Задание: `CLAUDE-TASK-Spine-Core-executable-invariants.md`
- Решение: ADR-050; прогон проверки зубов: `arch-be rules template verify --all`

## 0. Что сделано в одном абзаце

Паспорт вердикта называл слабость контроля числом («правил, судящих по ТЕКСТУ,
— N из M»), но не говорил, какие инварианты задеты и что делать. Теперь есть
библиотека из девяти шаблонов исполняемых правил (восемь паттернов + заготовка)
на двух языках, детектор, который поимённо называет каждый инвариант без
поведенческой проверки и подбирает ему шаблон, поимённая видимость в паспорте,
трассировке и доверии — и механика, которая проверяет, что у теста есть зубы.

## 1. Волна A: библиотека шаблонов (E1–E3)

### Состав

`assets/rule-templates/<id>/`: `template.yaml` (id, version, title, pattern,
match-ru/en, properties, rule, files, violating), `README.md`,
`python/{fakes,reference_impl,violating_impl,test_<id>}.py`, `java/pom.xml`,
`java/src/main/java/{Fakes,Subject}.java`, `java/src/test/java/<Id>Test.java`,
`java/violating/Subject.java`. Всё встроено в бинарь (`include_str!`) и
распаковывается `arch-be init`; каталог читается и без распаковки.

Три принципа (ADR-050): **свойство, а не протокол** (тест на фейке внешней
системы, а не против её протокола); **беззубый тест хуже текстового правила**
(у каждого шаблона есть нарушающая реализация, и механика это проверяет);
**Spine предлагает, архитектор принимает** (`apply` кладёт файлы и печатает
фрагмент правила — реестр и спайн правятся дельтой).

### Проверка зубов: шаблон → свойства → время → эталон/нарушение

Прогон `arch-be rules template verify --all --java-jar /tmp/junit-standalone.jar`
(2026-09-20): **32 проверки, 0 провалов, 1 пропуск** (заготовка).

| Шаблон | Свойств | python: эталон / нарушение | java: эталон / нарушение |
|---|---|---|---|
| `idempotency-key` | 3 | 3 теста, 0.03 с / FAILED 1 | 3 / 1 |
| `unknown-outcome-no-resend` | 4 | 4, 0.04 с / FAILED 1 | 4 / 1 |
| `saga-reserve-compensation` | 4 | 4, 0.04 с / FAILED 2 | 4 / 2 |
| `single-source-of-truth` | 4 | 4, 0.04 с / FAILED 1 | 4 / 1 |
| `append-only-journal` | 4 | 4, 0.04 с / FAILED 3 | 4 / 3 |
| `no-pii-in-logs` | 4 | 4, 0.03 с / FAILED 1 | 4 / 1 |
| `consent-before-auto-action` | 4 | 4, 0.04 с / FAILED 2 | 4 / 2 |
| `validate-before-side-effect` | 4 | 4, 0.05 с / FAILED 3 | 4 / 3 |
| `generic-property-test` | — | заготовка: тест пропускается намеренно | — |

(Число после FAILED — сколько тестов набора падает на нарушающей реализации;
все exit-коды: эталон `0`, нарушение `1`.) Весь python-набор каждого шаблона —
меньше 0.1 с при бюджете 5 с; сети и сна нет, зависимость — только pytest.

Весь прогон `verify --all` — ~41 с (в основном JUnit-консоль: javac + JVM на
каждую из 16 java-проверок).

### CLI и MCP

- `arch-be rules template list | show <id> | apply <id> --ad AD-N --dir <кейс>
  [--lang python|java|both] [--dry-run] | verify [--all|--dir <кейс>] [--java-jar <path>] [--require-python]`.
- `arch-be rules suggest <кейс>` — та же эвристика, что `control rules-suggest`
  (в задании приёмка называет её `rules-suggest`; отдельной команды с таким
  именем в CLI нет, поэтому она доступна как `rules suggest`).
- MCP: `rule_template_list`, `rule_template_show` (read-only, счёт ro-режима
  стал 38: 16 ручных + 22 мостовых) и `rule_template_apply` — только под `--rw`.
- `apply` кладёт файлы в `skeleton/rule_templates/<id>/`, пишет
  `.arch-handoff/rule-templates.lock` (id, версия, инвариант, язык, команда,
  файлы с SHA-256) и **печатает** фрагмент правила со свободным `C-NNN` и строку
  `verified_by`. Существующие файлы не перезаписываются — ошибка с перечнем
  конфликтов. `--ad` проверяется по форме `AD-<n>` и по наличию в спайне.

### Java: чем проверялось и чего не хватает в окружении

Maven и JUnit-jar в образе отсутствуют, а ассеты встраиваются `include_str!` —
бинарный jar в git не положить. Поэтому: шаблоны поставляют обычный Maven-проект
(`pom.xml`, JUnit 5.10.2), а проверка умеет два прогонщика — `mvn` из `PATH` и
JUnit-консоль флагом `--java-jar <junit-platform-console-standalone.jar>`.
**Все 16 java-проверок здесь прогнаны консолью** (jar скачан в `/tmp`, в git не
попадает). Без прогонщика java-половина пропускается с пометкой в отчёте, а в
CI её отсутствие ловит `--require-python` для python-половины.

## 2. Волна B: детектор на каждый инвариант (E4–E5)

Детектор `executable-invariant:AD-N` идёт по сущностям `type: ad`: собирает
правила из `verified_by` и обратную связь `ad:` реестра, смотрит типы и выдаёт
кандидата, если ни одно правило не входит в `BEHAVIOUR_RULE_KINDS`. Подбор
шаблона — счёт совпадений словаря `match` с текстом инварианта в спайне
(заголовок, `Binds`, `Prevents`, `Rule`), без LLM; до двух лучших, при нуле —
заготовка и честная пометка «паттерн не распознан». Инвариант с обоснованным
`unverifiable` пропускается; легаси-кандидат `executable-invariants` не тронут.

### Точность подбора на эталонных кейсах

`кейсы/salary-payments` (7 инвариантов, все правила текстовые):

| Инвариант | Ожидание задания | Подобрано | Точность |
|---|---|---|---|
| AD-001 | `idempotency-key` | `idempotency-key` (5 совпадений) | верно |
| AD-002 | `append-only-journal` | `append-only-journal` (3) | верно |
| AD-003 | `unknown-outcome-no-resend` | `unknown-outcome-no-resend` (3) | верно |
| AD-004 | `no-pii-in-logs` | `no-pii-in-logs` (4) | верно |
| AD-005 | `validate-before-side-effect` | `validate-before-side-effect` (4) | верно |
| AD-006 | — | `unknown-outcome-no-resend` (2) | приемлемо (частичный успех/разбор) |
| AD-007 | — | `append-only-journal` (2) | спорно (сверка по снимку; шаблона нет) |

**5 из 5** заданных заданием пар совпали; 7 из 7 инвариантов названы.

`кейсы/digital-ruble-merchant` (9 инвариантов): названы все девять, у одного
(AD-007 «Интеграция с ПЦР — только через адаптер») паттерн **не распознан** —
предложена заготовка. Это ожидаемо: восемь паттернов библиотеки — про
идемпотентность, журнал, сагу, согласие, проверки, ПДн и источник истины, а не
про границы интеграции (структурные типы правил — вне объёма задания).

Итог по точности: **14 верных из 16** пар «инвариант → шаблон», 1 не распознан,
1 спорный — и во всех случаях шаблон остаётся подсказкой, а не гейтом (П3).

### `load_bearing` (решение владельца: поле добавлено)

Необязательное `load_bearing: true` во frontmatter инварианта:
`#[serde(default)]`, остальная механика работает и без него. Кандидаты по
несущим идут первыми и помечаются в `rationale`; находка `ad-text-only`
адресуется несущим, а если признак не задан нигде — всем непокрытым.

## 3. Волна C: видимость и защита от беззубых тестов (E6–E8)

### Паспорт вердикта

Блок 2 получил вторую строку; на `кейсы/salary-payments` live-прогон
`arch-be gate --explain` даёт:

```
- **fitness** — правил, судящих по ТЕКСТУ файла …, — 15 из 15; … (исполняемых проверок поведения: 0)
- **fitness** — инварианты без проверки поведения: AD-001, AD-002, AD-003, AD-004, AD-005, AD-006, AD-007 — их правила судят по тексту, а не по поведению системы (несущие первыми; шаблон: `arch-be rules template list`)
```

Список ограничен (`MAX_AD_NAMES = 8`, дальше счётчик), несущие первыми. Это
представление: вердикт не меняется (тесты паспорта не тронуты).

### Трассировка

Седьмое, информационное звено; на salary-payments:

```
| AD → исполняемое правило | 0/7 | 0% | AD-001, …, AD-007 |
Итог: PASS (error: 0, warn: 0)
```

Шесть существующих звеньев — 100%, вердикт не изменился. Находка `ad-text-only`
появляется только при `[trace] executable_required = "warn"|"error"`
(дефолт `off`) и адресуется несущим инвариантам (тесты
`executable_level_is_informational_and_config_drives_the_finding`,
`ad_text_only_respects_load_bearing`).

### Доверие

Условие третьей ступени не менялось (решение владельца): `behaviour > 0`.
Деталь якоря дополнена «инвариантов с проверкой поведения: k из n».

### Проверка зубов на уровне кейса и red-team

- `rules template verify --dir <кейс>`: по lock-файлу во временной копии кейса
  эталонная реализация подменяется нарушающей; зелёный тест — находка
  `executable_rule_toothless` (в вердикт гейта не входит). Расхождение файлов с
  lock или переключение команды правила на настоящий код — пометка
  «адаптирован: проверка зубов неприменима, проверьте вручную».
- Red-team: поле `by` мутанта D11 приведено к новому имени кандидата; добавлен
  мутант «нарушение инварианта в реализации скелета» — вне знаменателя порога
  78% (решение владельца), без lock-файла он «неприменим».
- Догфуд: правило `C-31 rule_templates_have_teeth` (`command_succeeds`,
  `arch-be rules template verify --all --require-python`) внесено **дельтой**
  `changes/executable-invariants/` (`arch-be delta guard` — PASS). Реестр
  репозитория теперь проверяет зубья собственной поставки исполнением.

## 4. Волна D: проводник и методика

- **`bootstrap`**: каркас получает одно рабочее исполняемое правило под
  инвариант-пример `AD-2` (файлы шаблона `append-only-journal`, правило
  `command_succeeds` в реестре каркаса, `verified_by` у сущности, lock-файл).
  Каркас остаётся красным по прежним причинам (заглушки бандла) — зелёной
  должна быть именно проверка поведения.
- **Скиллы**: `fitness-functions` (раздел «как превратить инвариант в тест»),
  `fitness-function-catalog` (ссылка на исполняемый шаблон как следующая
  ступень у текстовых пунктов), `spine-fitness-gate` и
  `spine-content-bootstrap` (шаг «по каждому несущему инварианту — шаблон»).
- **Документация**: `CHANGELOG.md`, `ROADMAP.md`, `docs/control.md`,
  `docs/SPINE-BE-GUIDE.md`, README — см. раздел 6 «честно не сделано».
- **Стоимость**: исполняемое правило идёт в каждом прогоне гейта, включая
  Stop-хук и pre-push. Это записано в ADR-050 и в скилле `fitness-functions`.

## 6. Честно не сделано и почему

1. **Документация `CHANGELOG.md`/`ROADMAP.md`/`docs/control.md`/`README.md`** —
   не тронута. Причина: в этих файлах в те же минуты работали параллельные
   агенты (в `CHANGELOG.md` и `docs/experiments/0.3.5-*.md` уже лежит раздел
   волны C соседнего задания). Правка тех же файлов означала бы коммит чужой
   незавершённой работы под своим сообщением. Что нужно дописать: раздел
   «Исполняемые инварианты» в `CHANGELOG` (включая предупреждение о стоимости
   прогона), строку в таблицу команд `docs/SPINE-BE-GUIDE` и раздел
   `docs/control.md` про `rules template`.
2. **Волна D, `bootstrap` и скиллы** — выполнялись параллельными подагентами;
   на момент отчёта результат не подтверждён прогоном, см. раздел 7.
3. **`init --refresh`** (задание 0.3.5, дефекты): `write_defaults` не
   перезаписывает файлы, поэтому новые шаблоны приедут на диск, а обновлённые
   скиллы — нет. Если `init --refresh` не влит, это надо назвать в CHANGELOG.
4. **Java-половина в CI**: JUnit-консоль не скачивается автоматически
   (осознанно: сеть в проверке — плохая идея). В CI работает python-половина
   (`--require-python`); чтобы гонять java, нужен шаг установки Maven или jar.
5. **Мутант red-team на эталонных кейсах «неприменим»** — у
   `кейсы/salary-payments` и `кейсы/digital-ruble-merchant` нет lock-файла
   (шаблоны к ним не применялись). Это ожидаемое поведение, но означает, что
   сквозная проверка мутанта требует кейса с применённым шаблоном.
6. **`[trace] executable_required` не подключён к составляющей гейта**: гейт
   по-прежнему зовёт трассировку с дефолтом `off`. Ключ действует в CLI
   (`arch-be trace`) и MCP. Подключение к гейту — отдельное решение: оно
   меняет вердикт по конфигу.

## 8. Как воспроизвести

```bash
cd /home/roman/spine-bank-034
cargo build
./target/debug/arch-be rules template list
./target/debug/arch-be rules template show idempotency-key
# проверка зубов библиотеки (java — если есть Maven или JUnit-консоль)
./target/debug/arch-be rules template verify --all --require-python

./target/debug/arch-be rules template verify --all --java-jar /tmp/junit.jar

./target/debug/arch-be trace check кейсы/salary-payments
cd кейсы/salary-payments && ../../target/debug/arch-be gate --explain | grep -A2 "Заявлено"
```
