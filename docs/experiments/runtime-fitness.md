# Runtime fitness для NFR (волна D, D4; ADR-059)

**Статус:** исследование/прототип за флагом. В дефолтное поведение не входит;
новых сетевых зависимостей в ядре нет (Core-граница C-34). Дата: 2026-10-04.

## 1. Зачем

NFR в модели проверяются один раз — на бумаге: `arch-be nfr budget`
складывает заявленные бюджеты hop'ов `INT-*` против цели p99, `availability`
компонует доступность участков против SLA. После деплоя цикл разрывается:
фактические метрики с целями модели не сверяются. `nfr verify` замыкает цикл
на первом, файловом шаге: бюджеты и SLA из модели ← фактические метрики из
внешнего источника.

## 2. Прототип: `arch-be nfr verify --metrics <файл>`

Аргументы: `<dir>` — корень кейса (каталог с `model/`, по умолчанию `.`);
`--metrics <файл>` — JSON-файл фактических метрик.

Схема файла метрик (`metrics.json`):

```json
{
  "window": "2026-10-04T00:00:00Z/2026-10-04T01:00:00Z",
  "operations": [
    { "id": "INT-001", "p99_ms": 950 },
    { "name": "Payment authorization", "p99_ms": 1100 }
  ],
  "availability": 0.9975,
  "error_rate": 0.001,
  "error_rate_target": 0.002
}
```

- `operations[]` — по элементу на операцию/hop: `id` (обычно `INT-*`) либо
  `name` (название hop'а), `p99_ms` — измеренный p99. Обязателен один из
  идентификаторов.
- `availability` — измеренная доступность (доля, 0..1), опц.
- `error_rate` — измеренная частота ошибок (доля в запросах), опц.
- `error_rate_target` — явный бюджет частоты ошибок; если не задан, бюджет
  выводится из SLA как `1 − SLA` (см. §3).
- `window` — свободная метка окна измерения (в отчёт).

Сверка (переиспользует сравнения и валидацию модуля `nfr`):

| Метрика | С чем сверяется (модель) | Правило |
|---|---|---|
| p99 операции | `latency_budget_ms` hop'а `INT-*` | `runtime-latency-exceeded` [error] с hop'ом |
| доступность | строжайший `availability_target` среди `NFR-*` | `runtime-availability-below-sla` [error] с NFR |
| частота ошибок | `error_rate_target` или `1 − SLA` | `runtime-error-rate-exceeded` [error] |

Диагностика «сверять не с чем» — warn, не блокирует: неизвестная операция
(`runtime-unknown-operation`), hop без бюджета (`runtime-no-budget`), нет SLA
(`runtime-no-sla`), нет бюджета ошибок (`runtime-no-error-budget`). Битый JSON
— ошибка чтения (не молчаливый PASS). `error` → exit 1, как у остальных `nfr`.

Пример прогона (фикстура [`runtime-fitness-metrics.json`](runtime-fitness-metrics.json)):

```
$ arch-be nfr verify кейсы/<кейс> --metrics docs/experiments/runtime-fitness-metrics.json
# Runtime fitness: кейсы/<кейс>
| Субъект | Измерено | Бюджет/цель | Статус |
| INT-001 | 1200.000000 | 800.000000 | РАСХОЖДЕНИЕ |
...
- [error] runtime-latency-exceeded: INT-001 (Hop) — фактический p99 1200 мс превышает бюджет 800 мс
Итог: FAIL (сверок: N, error: 1, warn: 0)
```

## 3. Честные границы

- **Источник — файл, не Prometheus.** Ядро без сети (C-34): клиента метрик в
  Rust нет. Экспорт Prometheus/OpenSearch → файл — шаг CI заказчика; живой
  коннектор — будущая работа (не в этой волне).
- **Бюджет ошибок выводится из SLA.** Явной цели `error_rate` в модели нет:
  по умолчанию бюджет = `1 − SLA` — это ВЕРХНЯЯ граница (весь простой как
  ошибки), а не измеренный error budget. Проект может задать
  `error_rate_target` в файле метрик. Смешение доступности и частоты ошибок —
  известная слабость прототипа, отмечена для следующего шага (поле в NFR).
- **Доступность — одна на кейс.** Сверяется минимум SLA по всем `NFR-*`; связь
  измеренной доступности с конкретной цепочкой (какой SLA какому контуру)
  прототипом не проводится — уточнение в следующей волне.
- **Окно и агрегация вне модели.** «p99 за час» и «p99 за сутки» — разные
  величины; прототип доверяет файлу (метка `window` попадает в отчёт, но не
  проверяется).
- **Метрика ≠ инвариант.** `nfr verify` измеряет факт против цели, но не
  подменяет архитектурное решение: расхождение — повод для решения человека,
  а не автоматический откат.

## 4. Черновик канареечного шаблона (из `QAS-*` / `NFR-*`)

Будущий шаг — генерация шаблона канареечного анализа из сущностей модели:
`QAS-*` дают стимул/артефакт/меру, `NFR-*` — измеримую цель. Черновик формы
(генерируется в handoff-пакет рядом с `TASK.md`; в этой волне — только
образец):

```markdown
# Канареечный анализ: <CAP/SYS> (черновик из QAS-*/NFR-*)

## Сценарии (из QAS-*)
- **QAS-001** — стимул: <stimulus> → артефакт: <artifact> → реакция: <response>
  - мера: <measure>  → сверка: `nfr verify --metrics <файл>`

## Цели (из NFR-*)
| NFR | Метрика | Цель | Источник факта |
|-----|---------|------|----------------|
| NFR-001 | p99 | <p99_target_ms> мс | metrics.json:operations[].p99_ms |
| NFR-004 | доступность | <availability_target> | metrics.json:availability |

## Критерий прохождения канарейки
- `arch-be nfr verify <кейс> --metrics <файл>` → `Итог: PASS` (нет error-находок).
- Наблюдение: <окно>, откат при `РАСХОЖДЕНИЕ` по критичной операции.
```

Шаблон — черновик: генератор в этой волне не реализован (вне объёма D4),
форма зафиксирована для следующего шага.

## 5. Что не сделано (границы волны)

- Генератор канареечного шаблона в handoff-пакете — только эскиз (§4).
- Живой источник метрик (Prometheus и пр.) — вне границы ядра.
- Поле цели `error_rate` в модели NFR — не вводится (формат модели —
  совместимость, правило 4 TASK).
