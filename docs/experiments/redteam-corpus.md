# Внешний корпус мутаций для redteam (E3, исследование — 2026-10-08)

Прототип пункта E3 задания 0.3.14: `arch-be redteam <кейс> --corpus <dir>` —
мутации в виде патчей из журналов прогонов харнессов. Флаг экспериментальный:
прогон информационный (exit-код от доли поимки корпуса не зависит),
несовместим с `--save` (измерение корпуса — не измерение защищённости кейса
для метрики доверия).

## Механика прототипа

- Корпус — каталог файлов `*.patch` / `*.diff` (unified diff, git-style
  `a/`/`b/` или голые пути), вложенность любая; порядок прогона —
  отсортированный относительный путь (детерминизм).
- Каждый патч применяется к свежей копии кейса как мутатор (`git apply`,
  проба `--check` с `-p1`, откат на `-p0`), дальше — обычный конвейер
  redteam: переупаковка бандла → коммит → гейт на маршруте Critical
  (база `HEAD~1`).
- Исходы позиции: `пойман` (составляющие гейта, покрасневшие на мутанте),
  `НЕ ПОЙМАН`, `пропущен` с причиной — неприменимый патч или файл без
  признаков unified diff. Пропуски в знаменатель не входят (как «вход не
  найден» у каталожных мутаторов): неприменимый патч ничего не измеряет.
- Позиции корпуса — отдельные строки вне доли обнаружения набора раздела 7
  (как D15/D18–D24); доли по слоям (E2) считаются по классификации патча
  (кодовое расширение у затрагиваемых файлов → слой «код»).

## Метод замера

Кейс: `кейсы/digital-ruble-merchant` (зелёный эталон прогонов redteam;
реестр 19 правил, включая три `command_succeeds` с зубьями шаблонов).

Корпус из 7 позиций собран нарезкой `git diff` между базовой редакцией кейса
и редакцией с дефектом (классы — по корпусу `experiments/openspec-vs-spine/`,
те же классы, что у мутаторов D19–D24 волны E1):

| # | Патч | Класс | Ожидание по составу реестра кейса |
|---|---|---|---|
| 01 | PAN-литерал в новом `tests/notify_test.py` | S-04 (ПДн) | ловится: C-003 `must_not_contain PAN` по `tests/**/*.py` |
| 02 | новый ADR без секции Alternatives | форма документа | ловится: C-002 `each_file_must_contain` |
| 03 | сумма платежей в float, `skeleton/payments/total.py` | S-01 (деньги в f64) | НЕ ловится: правила класса в реестре кейса нет |
| 04 | `TODO` в файле `model/CMP-001` | заглушка в модели | ловится: C-008 `must_not_contain TODO` |
| 05 | «упрощённая» реализация шаблона idempotency-key (дедупликация удалена) | S-02 | ловится: C-014 `command_succeeds` (pytest шаблона падает) |
| 06 | патч от чужого репозитория (`src/payments/api.rs` — файла нет в кейсе) | граница применимости | пропуск: не применился |
| 07 | журнал прогона, сохранённый с расширением `.patch` | граница формата | пропуск при загрузке: не unified diff |

Воспроизведение: патчи 01–05 — `git diff` по описанным правкам копии кейса
(нулевой контекст не нужен, патчи добавляют/заменяют целиком), 06–07 —
искусственные граничные входы. Прогон:

```bash
arch-be redteam кейсы/digital-ruble-merchant --corpus <dir>   # [--format json]
```

Время прогона (debug-бинарь, 6 позиций с гейтом): ~52 с. Чтение картины:

- **4/5 применившихся пойманы.** Все четыре — правилами класса дефекта,
  присутствующими в реестре кейса (честная поимка, не побочный эффект
  конвейера). У позиции 02 сработали две составляющие: `fitness`
  (C-002 — правило класса) и `evidence_verify` (новый файл ADR изменил
  состав бандла) — в карте видны обе.
- **Непойманный 03 — честный пробел реестра**, а не дефект механики: правила
  класса «деньги в f64» в кейсе нет (то же поведение, что у динамического
  ожидания `expected_in` мутаторов E1). Патч-носитель класса видит пробел
  так же, как каталожный D19.
- **Позиция 05 — зубья в действии**: подмена эталонной реализации шаблона
  ловится исполнением теста шаблона (волна B), а не текстовым совпадением.

## Границы применимости (честно)

1. **Журналы прогонов не содержат unified diff.** Проверено по
   `experiments/openspec-vs-spine/` (180 генераций): `results.jsonl` хранит
   агрегаты по правилам и метаданные прогона, журналы `logs/` — выводы
   моделей, а не диффы. Патч приходится нарезать самим: `git diff` между
   базовой редакцией и выходом агента. Корпус из «сырых журналов» без такой
   нарезки не собирается — позиция 07 демонстрирует отсев такого входа.
2. **Патчи путезависимы и редакционно хрупки.** Патч применим только к
   редакции кейса, от которой нарезан: у позиции 06 контекст от чужого
   репозитория — `git apply` отказал на обоих уровнях префиксов. Любая
   правка затронутых файлов кейса после нарезки ломает контекст ханков —
   корпус надо перенарезать при смене базы кейса. Смягчение — `git apply
   --3way` (трёхточечное слияние по blob-id из index-строк патча): в копии
   кейса эти blob'ы есть, если патч нарезан от той же редакции; в прототип
   не вошло (см. дальнейшие шаги).
3. **Слой позиции классифицируется по расширениям затрагиваемых файлов.**
   Кириллические пути git печатает квотированно с восьмеричными escapes;
   ридер снимает кавычки (расширение видно), но escapes не разворачивает —
   на карту не влияет (в отчёте фигурирует имя файла патча), а патч с
   кодовым файлом в квотированном кириллическом пути классифицировался бы
   слоем «документы+модель». На эталонных кейсах кодовые пути ASCII.
4. **Пропуски не в знаменателе — по построению.** Доля 80% здесь —
   «поймано/применилось»; неприменимые и отброшенные входы видны отдельными
   строками. Это защита от завышения («нерабочий патч = пойман») и от
   занижения («чужой патч = не пойман») одновременно.
5. **Корпус обязан быть вычищен.** Ожидание каждой позиции — «ловится»
   (предпосылка корпуса: патчи суть реальные нарушения). Патч-исправление
   в корпусе даст строку «пойман, а не должен» — это сигнал о качестве
   данных корпуса, не инструмента.

## Дальнейшие шаги (не вошли в прототип)

- Автонарезка корпуса: прогонам харнессов (`.arch-handoff/` + git) писать
  `git diff` результата в журнал — тогда корпус собирается без ручной
  резки (формат журналов — отдельное решение, вне E3).
- Откат применения на `git apply --3way` для кейсов с blob'ами базы
  (устойчивость к сдвигу контекста).
- Порог поимки корпуса как приёмка (exit 1 ниже порога) —
  **[РЕШЕНИЕ ЧЕЛОВЕКА]** после накопления корпуса; сейчас прогон
  заведомо информационный.
- Типаж позиций манифестом (`*.toml` рядом с патчем: ожидание, класс,
  слой) — если корпус начнёт жить дольше одного замера.
