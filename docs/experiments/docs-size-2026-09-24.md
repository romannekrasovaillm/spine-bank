# Размер docs/ и тяжёлые бинарные файлы — 2026-09-24

Замер к волне D (открытость для контрибьюторов) релиза 0.3.7: насколько
`docs/` утяжеляет клон и есть ли смысл выносить бинарные файлы из git.
Вынос/перемещение не выполнялись — это решение меняет семантику клона и
ссылки README, поэтому фиксируется как заметка с вариантами.

## Фактура (команды: `du -sh docs`, `find docs -type f -size +500k`)

- `docs/` всего — **21M**, 286 файлов в git.
- `docs/diagrams/` — **11M**: 13 HTML-экспортов Archify на 9,1M
  (корень — 2,9M, `guide/` — 6,2M), PNG-рендеры — 1,8M (10 файлов),
  исходные JSON IR — 52K.
- `docs/screenshots/` — **7,5M**: 49 PNG (корень 2,2M — 9 файлов;
  `harnesses/` 4,2M; `connect/` 1,0M) + 46 SVG на 232K.
- Файлов крупнее 500K — ровно 13, все — HTML в `docs/diagrams/`
  (максимум 772K, `spine-be-detail.html`). Скопления «тяжёлых сюрпризов»
  вне этих двух каталогов нет: следующий по размеру — `docs/control.md`,
  100K текста.

## Что регенерируемо

- **SVG-кадры TUI** в корне `docs/screenshots/` — из кода:
  `ARCH_GEN_SHOTS=1 cargo test gen_readme_screenshots` (`src/tui/shot.rs`).
- **HTML диаграмм** — из JSON IR, лежащих рядом (`*.architecture.json` и
  др.), через вендоренный Archify (`vendor/archify/`, нужен Node.js ≥ 18);
  PNG диаграмм — производные от тех же IR.
- **PNG скриншотов** (`harnesses/`, `connect/`) — кадры живых прогонов
  харнессов; из кода не воспроизводятся, переснимаются вручную. Удалять
  «как регенерируемые» их нельзя.

## Варианты

**1. Оставить как есть.** Плюсы: README рендерит скриншоты относительными
путями на любой ревизии и офлайн; контрибьютору не нужен git-lfs; 21M —
приемлемая цена клона для документации с картинками. Минусы: бинари в
истории навсегда; каждое обновление кадра добавляет дельту в историю.

**2. Git LFS для PNG/HTML.** Плюсы: свежий клон кода худеет. Минусы:
реальный выигрыш требует перезаписи истории (бинари уже в ней); git-lfs
становится обязательной зависимостью контрибьютора; квоты GitHub LFS
(1 ГБ трафика/мес на бесплатном плане); скачивание raw-файлов с GitHub
отдаёт pointer вместо содержимого.

**3. Вынос в релизные ассеты / внешний хостинг.** Плюсы: репозиторий
содержит только текст и код. Минусы: README начинает ссылаться наружу
(рендер ломается без сети и при ротации ссылок); скриншоты отрываются от
версии кода — перестаёт работать «документация как код»; регенерация и
ревизия кадров перестают быть частью PR.

## Рекомендация

Оставить как есть (вариант 1). Размер сконцентрирован в двух каталогах,
каждый файл < 1M, основная масса регенерируема из артефактов, лежащих в
репозитории, — вынос даст экономию ~20M ценой ломки офлайн-рендера и
усложнения контура контрибьютора. Триггеры пересмотра: рост `docs/` за
50M, появление файлов > 5M, либо начало регулярных обновлений PNG живых
прогонов (тогда рассмотреть LFS точечно для `docs/screenshots/harnesses/`
без перезаписи истории).
