# 0.3.5: репродукции дефектов

Срез, на котором ищутся дефекты, — `0539223` (0.3.4, тег `v0.3.4`). Все
команды ниже проверены на **релизном** бинаре 0.3.4, скачанном из GitHub
Releases (`arch-be-linux-x86_64`, sha256 начинается на `9653f460`), — не на
отладочной сборке: дефект контура обязан воспроизводиться на том, что у
пользователя.

Каждая запись: команда → вывод → вердикт «воспроизведено / не
воспроизведено». Невоспроизведённое не чинится.

## T-03. Двойной `...HEAD` — воспроизведено

```bash
/…/arch-be-0.3.4-release gate --repo . --route auto --base 0539223
/…/arch-be-0.3.4-release gate --repo . --route auto --base "0539223...HEAD"
```

```
Маршрут: Fast (auto: score 0 (триггеров нет))
Маршрут: Critical (auto: дифф недоступен (control: anti-bypass: . — база диффа
недоступна: неоднозначный аргумент «0539223...HEAD...HEAD»: неизвестная
редакция или не путь в рабочем каталоге. …) — fail-safe маршрут Critical)
```

**Причина в коде найдена:** `control::detect_diff_triggers` (`src/control.rs`)
формирует диапазон как `format!("{r}...HEAD")`, а шаблоны `connect`
(Stop-хук, pre-push, CI GitLab/GitHub) передают базу уже с `...HEAD`
(`src/connect.rs`). Документированная в `--help` форма `origin/main...HEAD`
ломает детектор — гейт всегда уходит в fail-safe Critical.

## T-04. `significance_score` засчитывает несуществующие триггеры — воспроизведено

```bash
/…/arch-be-0.3.4-release control score --trigger foo=true --trigger bar=true \
  --trigger baz=true --trigger qux=true --trigger quux=true
```

```
Score: 5 (bar, baz, foo, quux, qux триггеров) → маршрут Critical
EXIT=0
```

То же через MCP (консверт инструмента):

```json
{"fired": ["bar","baz","foo","quux","qux"], "route": "Critical", "score": 5,
 "unknown_triggers": ["bar","baz","foo","quux","qux"]}
```

**Причина в коде найдена:** счёт (`control::significance_score_with_limits`)
идёт по всей карте ответов, а словарь канонических имён
(`SIGNIFICANCE_TRIGGERS`) используется только для подсветки «вне канонических»
после счёта. Обратная сторона той же ошибки — опечатка в настоящем имени:
`--trigger new_components=true` давал «Score: 1 → маршрут Fast», то есть
значимость **занижалась** молча.

видна ни в балле, ни в метке.

## T-08. Контроль аттестации «нет» после архивации дельт — воспроизведено

Фикстура: копия `кейсы/digital-ruble-merchant` (дельты `merchant-tsp`
заархивирована), имена файлов модели транслитерированы в ASCII — иначе опыт
мерит сопутствующий дефект гарда (ниже), а не контроль.

```bash
cp -r кейсы/digital-ruble-merchant /tmp/t08/case2
arch-be-0.3.4-release delta archive --repo /tmp/t08/case2 merchant-tsp
arch-be-0.3.4-release redteam /tmp/t08/case2 --format json
```

```json
{"caught": 11, "total": 14, "detection_ratio": 0.7857142857142857,
 "control_ok": false, "passed": false, "min_detection": 0.78,
 "D14": {"expected": "контроль", "caught": true,
         "caught_by": "аттестация 1ef4af72fbd6 → e21a8a523ea9"}}
```

```
Доля обнаружения: 11/14 = 79% (порог 78%) · контроль аттестации: нет
Итог: FAIL                                                       (exit 1)
```

Тот же прогон с `--save` роняет якорь 4 метрики доверия, и она объясняет
провал НЕ ТОЙ причиной:

```
[✗] 4. Пакет защищён измеренно — .arch-handoff/redteam.json: доля обнаружения
       11/14 = 79 % (порог 78 %), контроль аттестации: нет
     → контроль аттестации не сработал: безвредная правка не изменила
       аттестацию — вердикт не привязан к состоянию дерева (Н3)
```

Аттестация как раз менялась (строка D14 это и печатает) — упал не контроль
привязки, а вердикт контрольного мутанта.

**Причина в коде найдена:** `redteam::run` (`src/redteam.rs`) судит контроль как
«вердикт совпал с эталоном И аттестация изменилась». Гейт мутанта идёт по
маршруту Critical, где обязателен `delta_guard`, а безвредная правка `model/CMP-*`
без активной дельты — честное нарушение «правка защищённого пути мимо дельты».
Вердикт мутанта менялся (`PASS` → `FAIL`), `same_verdict = false` — контроль
падал, и прогон краснел при доле выше порога. Архивация дельты (нормальный
порядок работы) переводила пакет в это состояние сама.

**Сопутствующий дефект (найден при этой же репродукции):** на кейсе с русскими
именами файлов (`кейсы/*` — все такие) контроль остаётся «да», потому что
`delta_guard` защищённых файлов не видит:

```bash
cd <копия кейса> && git init -q && git add -A && git commit -qm baseline
printf '\nУточнение формулировки без смены решения.\n' >> model/CMP-001-оркестратор-операций.md
git add -A && git commit -qm mutant
arch-be-0.3.4-release gate --repo . --route Critical --base HEAD~1
```

```
[PASS] delta_guard * — изменённых файлов: 1, защищённых среди них: 0
```

Файл изменён, но в отчёте гарда защищённых правок ноль. Причина: `git diff
--name-only` по умолчанию экранирует не-ASCII путь
(`"model/CMP-001-\320\276…"`), префикс `model/` перестаёт совпадать.

**Проверка после правок** (тесты + прогон в worktree):

```
[PASS] delta_guard * — изменённых файлов: 1, защищённых среди них: 1   # 0.3.5
test redteam_control_survives_delta_archival ... ok                   # CLI
D14: control_ok: true, control_note: null, caught: 11/14, passed: true
```

Тест-сторож проверен с обеих сторон: с отключённым прикрытием он падает и
показывает причину словами измерения —
`"безвредная правка изменила вердикт (PASS → FAIL) — правка не должна менять
вердикт: проверьте составляющие delta_guard"`.


## T-11. `change_impact` вернул 0 владельцев — воспроизведено

```bash
arch-be model impact кейсы/digital-ruble-merchant --id CMP-002
```

```
Правила CONSTRAINTS.yaml:
  C-001 (spine_present; владелец: OWNER-001)
  … C-009 (acceptance_present; владелец: OWNER-001)
Итог: Изменение «CMP-002» затрагивает сущностей: 40 (…); правил: 9;
      контрактов: 2; владельцев: 0
```

Два ответа на один вопрос: в списке правил «владелец: OWNER-001», в итоге
«владельцев: 0».

**Причины в коде найдены (обе):**

1. `review::impact_core` собирал владельцев ТОЛЬКО из достигнутых обходом
   сущностей `OWNER-*`. `OWNER-001` в модели не связан с `CMP-002` ни одним
   ребром (`depends_on`/`implements`/`affects`/`verified_by`), поэтому в список
   не попадал, хотя карточки девяти затронутых правил называют его владельцем.
2. `review::rule_cards` читал реестр ТОЛЬКО в корне кейса
   (`<case>/CONSTRAINTS.yaml`). Кейс, где реестр лежит в
   `.arch-handoff/CONSTRAINTS.yaml` (обычный случай после `bootstrap`/
   `handoff`), карточек не находил вовсе:

```bash
mv CONSTRAINTS.yaml .arch-handoff/CONSTRAINTS.yaml
arch-be model impact <копия кейса> --id CMP-002
```

```
Правила CONSTRAINTS.yaml:
  C-008 (?)
  C-009 (?)
Итог: … владельцев: 0
```

**Проверка после правки:**

```
Согласовать с владельцами:
  OWNER-001 · Владелец контура приёма
Итог: … правил: 9; контрактов: 2; владельцев: 1
```

Владелец, названный в карточке идентификатором сущности, показывается с
заголовком; свободный текст («Команда платежей») — как есть. Пустой список
сопровождается объяснением: `owners_note` называет, что проверили (сущности
`OWNER-*`, поле `owner` в карточках затронутых правил, наличие реестра).
