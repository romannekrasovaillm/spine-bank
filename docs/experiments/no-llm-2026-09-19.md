## 1. Цель и постановка

Проверить, работает ли архитектурный контур Spine в режиме **«Spine Core без своей LLM»**: все проверки, гейты, модель и передача артефактов исполняются детерминированно, а роль модели (проектирование, суждение, формулировки) берёт на себя внешний кодовый агент.

Режим проверялся по трём осям:

1. **Детерминированное ядро без ключей** — работает ли контроль, если ни одного API-ключа модели не передано процессу.
2. **Боевая задача** — можно ли построить полноценный архитектурный комплект, где LLM — внешний агент, а Spine только контролирует.
3. **MCP и скиллы** — как контур отдаёт себя наружу (кодовому агенту) и что это даёт.

### Метод снятия ключей

Ключи провайдеров вырезались из окружения каждого процесса Spine:

```bash
env -u DEEPSEEK_API_KEY -u ZHIPU_API_KEY -u KIMI_API_KEY \
    -u GIGACHAT_API_KEY -u GIGACHAT_API_CREDENTIALS -u GIGACHAT_API_SCOPE \
    -u OPENAI_API_KEY -u OPENAI_BASE_URL arch-be <команда>
```

Ключи самого Claude Code (`ANTHROPIC_*`) не трогались — они относятся к внешнему харнессу, а не к Spine.

**Оговорка о честности:** локальный `~/.config/arch-harness/config.toml` остался рабочим (плагины и скиллы на месте, 7 каталогов знаний, 4 MCP-сервера, конфиг cron). Мы проверяли работу ядра без LLM, а не «пустой харнесс». Заодно всплыло расхождение в счётчиках самого Spine: `doctor` сообщает «13 плагинов, 81 скиллов», а `skills list` и `plugins list` — «79 скиллов в 14 плагинах» (см. §7.3).

## 3. Часть 2. Боевая задача: сервис цифрового рубля для физлиц

### 3.1 Задание и подход

Задание дано одной строкой: **«построй сервис для цифрового рубля для физлиц»**. Модель — внешний агент (Claude Code); Spine — детерминированный контроль.

Ключевые факты, на которые опирается решение:

- цифровой рубль — третья форма национальной валюты, **счёт (кошелёк) открывается на платформе Банка России, а не в банке**; банк — участник платформы;
- из локальной базы знаний харнесса (`kb_search`) поднят факт: **массовый запуск обязательного этапа — с 1 сентября 2026**, то есть рельса уже в проде;
- платформенный протокол ПЦР публично не раскрыт → все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]`, а не выданы за установленные (та же дисциплина, что в кейсе 001 `sbp-gateway`).

### 3.4 Модель как граф

`model graph` показал 65 сущностей и 161 связь. Типы связей и их смысл:

- `AD.verified_by → C-0NN` — **обязательное звено**: инвариант без правила фитнеса и без явного `unverifiable` даёт error;
- `CMP.implements → AD-*` — компонент обязан реализовывать хотя бы один инвариант;
- `ADR.affects → CMP-*` — решение обязано затрагивать хотя бы один компонент;
- `INT.contract → <путь>` — у интеграции обязан существовать файл контракта (битый путь — error);
- `NFR.affects → CMP/INT` + поле `verification` — у NFR обязан быть способ проверки;
- ссылочная целостность: битая ссылка, дубль ID, цикл `depends_on` — error.

Отдельно: `spine_crosscheck` сверяет инварианты файла `ARCHITECTURE-SPINE.md` с моделью — каждый AD из спайна обязан быть в модели (иначе error), AD модели вне спайна — warn. Спайн и модель не могут разъехаться незаметно.

### 3.5 Дефекты, найденные гейтами в моих же артефактах

| Что нашёл | Гейт | Исправление |
|---|---|---|
| фраза `лаг сверки` стояла в косвенном падеже («измеримым лагом сверки»), правило C-007 не срабатывало | `control check` | переформулировал текст ADR-007 |
| `Разграничение ответственности` с заглавной буквы не совпадало с паттерном | `control check` | правило C-010 сделано регистронезависимым `(?i)` |
| в спеках не было обязательных секций `## Проблема / ## Критерии приёмки / ## Риски` | `control sensors` | секции добавлены в оба документа |
| правила без карточек: owner/expiry/effort не заданы (26 ч сопровождения невидимы) | `control rules-report` | карточки заполнены для всех 15 правил |

Все четыре — механические расхождения между замыслом и записью. Мой собственный ревью их не видит принципиально: он смотрит на смысл, а не на байты.

## 5. Часть 4. Скиллы: методики исполнены на кейсе

Библиотека: **79 скиллов в 14 плагинах**. Загружены и исполнены три методики, релевантные кейсу.

### 5.1 `readiness-gate` → вердикт **CONCERNS**

Вопрос гейта: «сможет ли исполнитель реализовать, НЕ изобретая отсутствующих решений?»

- `[FAIL]` требования не декомпозированы на работы: 6 REQ против 1 задачи в `TASK.md`;
- `[CONCERN]` критерии приёмки не в нотации EARS (`When/While/If/Where`);
- `[CONCERN]` нет SLA на разбор операций в `UNKNOWN`: лаг сверки 5 мин задан, срок закрытия расхождения — нет;
- `[CONCERN]` ёмкость сверки после восстановления платформы (лавина операций) не посчитана;
- `[PASS]` NFR измеримы, инварианты с ID, сенсоры зелёные, конфликтов SLA нет.

### 5.2 `adversarial-review` → вердикт **NOT-READY** (4 major, 2 minor)

Каждая находка со свидетельством (правило навыка: свидетельство, а не вкус):

1. `[major]` нет численных таймаутов и политики повторов к платформе — ни одного значения в `docs/contracts/*`;
2. `[major]` заявлены RTO 15 мин / RPO 60 с, но решения по репликации/DR нет ни в одном из 9 ADR;
3. `[major]` аутентификация описана только для стыка с ПЦР (`ADR-008`); стык канал→шлюз (`INT-003`) без требований;
4. `[major]` решение «разблокировка антифрода человеком» без контура аудита действий сотрудника;
5. `[minor]` не описаны backpressure и DLQ;
6. `[major]` `TASK.md` декларирует «SPEC.md заполнен архитектором», но файл скомпилирован генератором из spine/ADR/NFR — исполнитель примет компиляцию за авторскую спеку.

**Честная оговорка:** ревьюер здесь = автор, а это антипаттерн, названный в самом навыке. Независимым контуром такое ревью не является — «второй LLM-ревьюер» читал бы тот же текст с той же интерпретацией.

### 5.3 `handoff-packaging` → 4 из 5 элементов пакета

Пакет собран корректно по составу (TASK/ARCHITECTURE/CONSTRAINTS/RUBRIC/adr/MANIFEST), но два пункта провалены:

- `CONSTRAINTS.yaml` пакета **синтаксически невалиден** (дефект Spine, см. §6.1);
- epic-context усечён до 6000 символов, и в него попало **9 инвариантов из 10** (AD-010 обрезан), тогда как навык требует spine-блоки целиком.

## 6. Часть 5. Хуки

**Факты:** 5 плагинов несут `hooks.json` (всего 7 хуков), в конфиге `include_hooks = true`. В Claude Code хуки Spine не заведены (в `~/.claude/settings.json` и `settings.local.json` секции `hooks` нет) — механизм относится к собственному циклу `arch-be run`/TUI, который в этом режиме не запускался.

### 7.1 `arch-be handoff` генерирует невалидный `CONSTRAINTS.yaml` (воспроизводимо)

**Симптом.** Первая строка правила теряет отступ, остальные ключи сохраняют 4 пробела:

```yaml
rules:
- name: readme-exists
    type: file_exists
    path: README.md
    severity: warn
```

**Проверка:** `python3 -c "import yaml; yaml.safe_load(...)"` → `ScannerError: mapping values are not allowed here`; `arch-be control check . --constraints .arch-handoff/CONSTRAINTS.yaml` → `Error: mapping values are not allowed in this context at line 7 column 9`.

**Воспроизведение:** на generic-стеке (кейс ЦР) и на Rust-стеке (пробный репозиторий с `Cargo.toml`) — дефект одинаков. Воспроизводится одной командой:

```bash
mkdir -p /tmp/stack-probe && cd /tmp/stack-probe
printf '[package]\nname = "probe"\nversion = "0.1.0"\n' > Cargo.toml
echo 'fn main(){}' > main.rs && echo "# probe" > README.md
arch-be handoff claude-code --repo /tmp/stack-probe --task "probe" --route fast
cat .arch-handoff/CONSTRAINTS.yaml
```

**Причина.** `src/harness.rs` (шаблоны правил для стеков, ~строки 147–233): каждая строка шаблона начинается с `"\` + перевод строки. В Rust такая запись съедает перевод строки **и ведущие пробелы следующей строки** — поэтому отступ теряется только у первого ключа (`- name:`), а у последующих (`type:`, `glob:`…) сохраняется. Итог — невалидный YAML. Затронуты все пять шаблонов (Rust, Python, Go, Node, generic).

**Почему дефект не виден в самом репозитории:** файл `.arch-handoff/CONSTRAINTS.yaml` там перезаписан вручную под эпик, и валидность не проверяется ни одним гейтом.

**Влияние:** пакет передачи приходит кодовому агенту со сломанным файлом ограничений; `control check` по нему не запускается. Лечится либо снятием первого отступа в шаблонах, либо тестом на парсинг генерируемого файла.

### 7.2 Усечение epic-context режет инварианты

Пакет собирает `ARCHITECTURE.md` до 6000 символов и в честной сноске пишет: «Контекст усечён до 6000 символов». В результате в пакет попало **9 инвариантов из 10** — AD-010 обрезан на полуслове. Навык `handoff-packaging` требует обратного: spine-блоки включаются целиком, усечению подлежат только спеки (заголовки + ключевые секции). Сейчас бюджет режет то, что должен сохранять.

### 7.3 Мелочи API

- `significance_score` по MCP ждёт `triggers` **картой** (`{"new_component": true}`), а CLI — флагами `--trigger new_component=true`: две разные формы одного входа.
- `rubric_run` резолвит `target` относительно cwd, а не относительно кейса: относительный путь `docs/SPEC.md` из другого каталога падает с `No such file or directory`.
- Счётчики библиотеки расходятся между командами: `arch-be doctor` → «13 плагинов, 81 скиллов», `arch-be skills list` → «79 в 14 плагинах», `arch-be plugins list` → «Плагины (14)». Пять плагинов имеют каталог `hooks/`, что, вероятно, и даёт разные правила подсчёта; для пользователя цифры выглядят противоречиво.

### 7.4 Дефект в моих артефактах, найденный через MCP

`AD-007` в спайне ссылался на `NFR-008` (ёмкость), тогда как лаг сверки — это `NFR-009`. **Ни один гейт этого не поймал:** линтер спайна сверяет с моделью только AD-id, ссылки на NFR не проверяет. Исправлено; зафиксировано как слепое пятно гейта.

## 8. Что дал архитектурный контур Spine — оценка ценности

Ниже — моя оценка, основанная на этой сессии. Я разделяю измеренное и суждение.

### 8.1 Формула

Мой харнесс — генератор: он производит любой артефакт и не умеет независимо его опровергнуть. Spine добавил **внешний, версионируемый, не-LLM-ный оракул над моей же работой** и **язык артефактов**, в котором полнота становится проверяемой, а не заявляемой. Ценность держится не на том, что Spine что-то знает — знаний у меня больше, — а на том, что **он не я**.

### 8.2 Пять ценностей

**1. Проверяющий, который не я.**
Три дефекта в моих же артефактах нашли гейты, а не я (фраза в косвенном падеже, заглавная буква, ссылка на неверный NFR). Каждый тривиален, но природа одна: механическое расхождение между замыслом и записью, которого мой собственный ревью не видит принципиально. Второй LLM-ревьюер тоже не помог бы — он читал бы тот же текст с той же интерпретацией.

Жёсткая форма этого свойства: **гейт сказал «нет» моей работе** — `evidence verify` вернул FAIL и заблокировал выпуск. В своём харнессе я физически не могу произвести отказ от собственного результата: любой мой «итог» — утверждение, а не гейт, и его можно переубедить словами.

**2. Схема, которая заставляет полноту вместо дисциплины.**
Модель потребовала: у инварианта — правило фитнеса или явное `unverifiable`; у интеграции — существующий файл контракта; у ADR — затронутый компонент; у NFR — способ проверки. Пять контрактных файлов появились не потому, что я так решил, а потому что модель без существующего пути даёт error. Итог — 161 связь и 100% по шести звеньям. В прозе «трассируемость» — моё утверждение о себе; здесь — свойство графа, которое ломается, если пропустить звено.

**3. Числа, которые проверяются, а не декларируются.**
Доступность цепочки посчитана как произведение по участкам с учётом реплик: **99,4004% против цели 98%** (3151,5 мин простоя в год). Латентность: 2150/3000, 1900/3000, 2700/5000 мс. Ёмкость: 3200/3600/3000 rps против 2400. TCO 46,86 млн ₽/год и цена выхода 8,9 млн ₽ = 19% годового TCO. Всё это — арифметика над моделью, которую пересчитал не я. В проектных документах такие числа обычно декоративны: никто не станет перемножать доступности по цепочке. Плюс warning `budget-hop-uncovered`, который я в свой документ не вписал бы: я пишу то, что работает.

**4. Governance, которого у меня нет по устройству.**
Три вещи я бы не произвёл ни при какой мотивации:
- **цена сопровождения моих же правил** — 26 ч/год по 15 правилам, с владельцем и сроком пересмотра (`expiry 2027-06-30`). В моём харнессе архитектурное правило — абзац без владельца, который не устаревает;
- **маршрут значимости как гейт, а не суждение** — score 10/15 → Critical, форсированный неотключаемыми триггерами. Я склонён просто делать работу; здесь решение о критичности принимает не мой вкус;
- **человеческий гейт, который нельзя закрыть за человека** — A3 остался Proposed, и это же стало причиной блокировки выпуска.

Единственная категория, где ценность не в проверке качества, а в **ограничении моей автономии**: механизм, сопротивляющийся моей готовности закончить.

**5. Передача и сопоставимость — артефакты как интерфейс.**
Методика readiness-гейта лежит файлом с вердиктами PASS/CONCERNS/FAIL, форматом вердикта и списком антипаттернов — и оттуда же прилетело обвинение «ревьюер = автор» про мою работу. Пакет передачи собран в **1500 токенов** с машинным контрактом результата (`complete|partial|blocked` + `conflicts_with_prior_decisions`) — архитектура передаётся не «вот документы», а в бюджете и с детектором молчаливого расхождения. Рубрика `solution_architecture` с весами (сумма 100) дала сопоставимое число **3,85/5** с опорой на якоря 1/3/5 — измерение, воспроизводимое в другой сессии и на другом кейсе, а не мнение.

### 8.4 Границы этой ценности — честно

- **Содержательные пробелы гейты не нашли.** Отсутствие декомпозиции на работы, не-EARS критерии, отсутствие решения по репликации под заявленные RTO/RPO, неаутентифицированный стык канал→шлюз, отсутствие аудита действий оператора, backpressure — всё это вытащили **методики**, не инструменты. Детерминированный слой проверяет форму, числа и связи; полноту решений он не проверяет и не может.
- **Судейство остаётся за моделью.** Из 10 MCP-инструментов девять детерминированы, десятый (`rubric_run`) требует свою LLM. В этом режиме судьёй был я — то есть bias «автор = ревьюер» вернулся через ту же дверь, о которой предупреждает навык.
- **Дефекты самого Spine стоили времени** (§7): невалидный YAML пакета, усечение инвариантов, расхождение формы `triggers`, путь в `rubric_run`.
- **Слепое пятно гейтов:** ссылки из спайна на сущности модели, кроме AD-id, не проверяются (§7.4).

### 8.5 Итог одной фразой

Spine даёт мне то, чего мой харнесс не даёт по своей природе: не текст, а **измерение текста** — независимую проверку с exit-кодом, схему, требующую полноты, числа, которые пересчитывают, ограничения моей автономии и интерфейсы передачи. Без него я быстрее произвожу архитектуру и не могу ни доказать её полноту, ни сравнить с прошлой, ни отдать другому агенту в проверяемой форме — и, что важнее, **не могу получить «нет» на свою работу**.

### 11.1 Уточнение к §7.3: механизм расхождения счётчиков (A5)

Ответ объясняет расхождение так: «`doctor` считает SKILL.md обходом каталогов,
`skills list` — по манифестам». По исходникам это не так:

- `src/doctor.rs:198–232`: плагин = каталог с `plugin.json`; скиллы =
  `count_files_named(&p, "SKILL.md", 3)` — обход каталога с ограничением
  глубины 3;
- `skills list` показывает **79** загруженных объектов и **включает** 15 скиллов
  плагина `arch-distilled`, у которого манифеста нет, — то есть «по манифестам»
  неверно.

Фактические числа на одной и той же библиотеке:

| Источник | Скиллов | Плагинов |
|---|---|---|
| Файловая система (`find … -name SKILL.md`) | **80** | 14 каталогов, 12 с `plugin.json` |
| `arch-be skills list` | **79** | 14 |
| `arch-be doctor` | **81** | 13 |
| README репозитория | **94** | 14 |

Ни одна пара не сходится, и «единая функция подсчёта» из ответа закрепит одну
из четырёх цифр, не объяснив остальные. Найденная причина дрейфа — раскладка
библиотеки: два скилла лежат не по канону (`plugins/<плагин>/skills/<имя>/SKILL.md`),
