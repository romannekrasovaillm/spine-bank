# ADR-078. Остатки волн S/K/P1: зубья структурных правил, data_ownership, корпус дефектов, раннеры метрик 4/5/6

- Date: 2026-10-12
- Status: Accepted [ADOPTED] — S5/S9, K3 и раннеры метрик 4/5/6 (волна 0.4.2,
  TASK 0.4.0 §6/§7/§9) фиксируются по итогам живых прогонов
- Модель-автор: spine-arch (claude) — исполнено флот-агентом волны 0.4.2
  (`feat(S9)`, `feat(S5)`, `bench(P1)`, `feat(K3)`), ADR оформлен интегратором
- Пересмотр: S6 (ArchUnit-подсказка при классах+JDK) и K4 (FP-реплей чистой
  истории) не вошли — 0.4.3; при втором потребителе data_ownership вне
  JSS-009 — пересмотреть формат owners
- Провенанс: продолжает ADR-070 (типы правил), ADR-065 (зубья), ADR-071
  (контур на реальном коде), ADR-069 (recover-граф как источник для правил)

## Context

Волна 0.4.0 оборвалась на середине: S5 (зубья структурных), S6, data_ownership
(S9 — единственное оставшееся `unverifiable` стандарта), K3/K4 и раннеры метрик
4/5/6 остались обрывками. Метрика 7 стояла на 11/12; метрики 4/5/6 мерились
косвенно (DEVIATIONS D11); контроль зубьев структурных правил отсутствовал —
вакуумное правило (никогда не срабатывает) ловилось только warn'ом B4, без
машинного прогона.

## Decision

1. **S9 `data_ownership` (тип правила):** хранилище recover-графа
   (`store:схема://хост`, ADR-069) читается/пишется только компонентами из
   `owners` правила; второй компонент с ребром connect к тому же хранилищу —
   `[error] data_ownership_violated`. Владельцы — по имени/title компонента
   либо id модели. JSS-009 (database-per-service) перевыражен в стандарте
   (та же процедура, что ADR-070/D-записи; DEVIATIONS D12). **Метрика 7:
   12/12.**
2. **S5 зубья структурных правил:** `rules teeth` синтезирует нарушающий
   импорт (`dependency_direction`) и зависимость (`deny_dependency`) в копии
   репо и требует, чтобы правило покраснело; вакуумное правило не получает
   зуб (честный вердикт, не FAIL). Кейс read-only: исходник не мутируется.
3. **K3 внешний корпус дефектов:** 5 патчей реальных классов нарушений
   (PAN-литерал в тестах, ADR без альтернатив, TODO в модели, pan! в
   исходнике, float для денег) в `benchmarks/architect-value/corpus/`;
   применяются к кейсам, метрика 12 объединяет K2 (стандарт на реальном
   коде) и K3: **detection 0.93, FP 0.00** (пороги ≥0.80/≤0.03).
4. **Раннеры метрик 4/5/6:** stores_recover (recall хранилищ), 
   externals_recover (precision внешних систем), survey_noise (доля строк
   шума карты). Итоги живых прогонов: **5 = 1.00 OK; 6 = 4.3% ≤5% OK;
   4 — FIND** (petclinic: datasource в Spring Cloud Config вне репо;
   buckpal: h2 — build-dependency без строки подключения) — порог не
   меняется, граница механики задокументирована (DEVIATIONS).

## Alternatives

- **data_ownership по текстовым глобам конфигов.** Отвергнуто: конфиг может
  лежать вне репо (petclinic — Spring Cloud Config) — граф as-built с
  владельцем по ребру честнее; текст слеп к внешним конфигам.
- **Зубья без копии репо (in-memory).** Отвергнуто: `check` читает дерево —
  копия (tempdir) сохраняет семантику и не мутирует кейс (уже ADR-065).
- **K3 как расширение мутаторов K2.** Отвергнуто: корпус — патчи РЕАЛЬНЫХ
  классов (PAN/пан/float), не синтетика стандартных правил; раздельные
  знаменатели показывают разные слои защиты.

## Consequences

- **Положительные:** стандарт 12/12 механизирован (метрика 7 выше цели
  §9: ≥11/12); структурные правила получают зубья (вакуумность ловится
  прогоном, а не только warn'ом); метрики 4/5/6 измерены раннерами (D11
  закрыт частично: 5 и 6 формально, 4 — с честным FIND).
- **Отрицательные:** data_ownership зависит от recover-графа в
  `control check` — на больших репо это стоимость прохода графа (ограничено
  bounded-механикой снимков); метрика 4 ниже порога на репо с внешним
  конфигом — осознанная граница (порог не меняется, FIND зафиксирован);
  корпус K3 — 5 патчей, расширение курируемое.
- **Риски:** owners по имени — коллизии имён компонентов; формат owners
  (список) не различает read/write — при первом прецеденте расширить.

## Reversibility

Высокая: тип правила аддитивен (отсутствие data_ownership-правил = прежнее
поведение), зубья — расширение существующей команды, корпус и раннеры —
файлы бенчмарка. Откат — удаление коммитов; JSS-009 возвращается к
unverifiable git-историей стандарта.
