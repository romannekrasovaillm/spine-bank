## Context

**Диффу не верили на ревью.** Живой прогон (TASK §2.3): 6 непустых
диффов на 140 реальных коммитах — все шум или неверное описание;
единственный архитектурный коммит PetClinic `79b527a` (новый микросервис
с внешним LLM) показан как «новая связь с tracing-server»; эталонный
состав не сверялся никак. Метрика 13 «до»: 0/2 по составу, 6/6 непустых —
шум. Волны B/R починили сам граф (рёбра env/route/stub, провайдеры,
денилист); волна D должна это доказать на размеченной истории.

## Decision

1. **`arch-be bench arch-diff-replay <repo> --last N --labels
   labels.yaml`** (и раннер `replay.py` для бенчмарка): для каждой метки —
   `arch-diff --base <sha>~1 --head <sha> --format json`, сверка
   всплывшего состава с ожиданием метки.
2. **Метрики:** recall значимых (доля меток с ≥1 совпавшим токеном),
   composition-F1 (macro по меткам), шум (доля окон-шума с непустым
   составом).
3. **Семантика сверки токенов** (доработка интегратора после первого
   прогона — дефекты измерения):
   - токены узлов — из `title` (короткие имена `api-gateway`), не из
     внутренних id (`dir:spring-petclinic-api-gateway`);
   - рёбра состава — только компонент→компонент: ребро к внешней
     системе/хранилищу не порождает токен-ребро (внешка уже учтена
     узлом) — иначе состав задваивался бы ложными FP;
   - матчинг «ожидание ⊆ всплывший» по эндпоинтам отдельно: имена
     модулей длиннее эталона (`spring-petclinic-api-gateway` ⊃
     `api-gateway`);
   - непустой дифф для шума = изменён состав (узлы/рёбра/контракты),
     ровно по замороженному правилу значимости labels; триггеры/маршрут
     сами по себе (new_vendor на бампе, spurious new_component) — сигнал
     ревью, но не «архитектурное изменение» по правилу разметки.

## Alternatives

- **Считать непустым всё, что подняло маршрут.** Отвергнуто: смешивает
  «изменился состав» с «сработал детектор значимости» — окна-шум с
  бампами зависимостей давали бы 100 % FP при честном составе.
- **Точное равенство токенов.** Отвергнуто: имена модулей репозиториев
  длиннее эталона B.3 — измеряло бы длину имён, не состав.
- **Правка эталона под findings.** Запрещено пререгистрацией: labels
  заморожены хэшами; расхождения (vertex-ai — реальная внешняя система
  `shoppingassistantservice`, не включённая в эталон B.3) честно считаются
  FP и фиксируются в DEVIATIONS.

## Consequences

- **Положительные:** метрика 13 (живой прогон, клоны на SHA из
  repos.lock): recall 2/2 = 1.00; composition-F1 0.90; шум 0/6 = 0.00 —
  пороги ≥0.80/≥0.80/≤0.10 выполнены; `79b527a` показывает полный
  эталонный состав (genai-service + openai/azure-openai + 3 ребра),
  `2932624` — shoppingassistantservice + alloydb + ребро frontend.
- **Отрицательные:** vertex-ai на `2932624` — честный FP (реальная
  внешка, эталон уже); spurious `new_component` на Vue-миграции
  dc9ca15 остаётся в триггерах (детектор значимости считает массовую
  замену фреймворта фронта новым составом компонента) — состав при этом
  пуст, шум не даёт; D3 (сортировка review inbox по confidence) —
  следующая итерация.
- **Риски:** substring-матчинг допускает ложные совпадения коротких
  ожиданий в длинных именах — контролируется длиной токенов эталона
  (куратор разметки).

## Reversibility

Высокая: бенчмарк и раннер аддитивны, продуктовой логики не меняют.
Откат — удаление команды/раннера; семантика сверки живёт в раннере и
версионируется git-историей вместе с результатами.
