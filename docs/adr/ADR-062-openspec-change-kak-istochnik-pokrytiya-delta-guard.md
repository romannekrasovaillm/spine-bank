# ADR-062. Change OpenSpec — равноправный источник покрытия `delta_guard`

- Дата: 2026-10-07
- Статус: Proposed (волна F релиза 0.3.14, пункт F1 задания TASK-v2; принимает владелец)
- Модель-автор: kimi-k3 (подготовка), решение — человек

## Context

Чтение OpenSpec в адаптере сделано нативно (`openspec/specs/`, дельты активных
changes, `covers:`), но запись изменений Spine шла только своим форматом
`changes/<name>/DELTA.md`, и составляющая гейта `delta_guard` признавала
покрытием исключительно его. Команда на OpenSpec, поправившая `model/` в рамках
своего change, получала FAIL и вынуждена была дублировать описание правки в
`DELTA.md` — двойной учёт одного и того же изменения в двух форматах
(репродукция — `docs/experiments/fork-repro-0.3.14.md`, раздел F: на 0.3.13
правка `model/CMP-001.md` при активном `openspec/changes/add-limits`,
упоминающем файл в proposal.md и tasks.md, давала `delta_guard` FAIL, exit 1).

При этом подключение второго источника покрытия не должно было ослабить контур:

1. **Правило владения (ADR-055).** Дельта, созданная внутри диапазона прогона
   исполнителя, не узаконивает ослабление/расхождение (находка
   `self_approved`). Если бы change OpenSpec стал покрытием без той же
   дисциплины, F1 открывал бы обход, закрытый 0.3.12.
2. **Markdown OpenSpec Spine не пишет** (требование `docs/openspec.md`, правило
   9 задания): иначе ломается `openspec validate --strict` у самих команд.
3. **Обратная совместимость:** вердикт `gate-verdict/v1`, exit-коды 0/1/2/3 и
   поведение репозиториев без разметки OpenSpec меняться не должны.

## Decision

1. **Источники покрытия `delta::guard`.** К активным дельтам
   (`changes/<name>/DELTA.md`) добавлены активные changes OpenSpec
   (`openspec/changes/<id>/`, без `archive/`). Упоминание защищённого файла
   ищется в `proposal.md`, `design.md`, `tasks.md` и `specs/**/*.md` той же
   функцией `delta_mentions` и тем же правилом совпадения (полный путь, имя
   файла, стем, идентификатор сущности) — механика одна, дублирования нет.
2. **Архив.** Заархивированный change (`openspec/changes/archive/<каталог>/`)
   засчитывается только если архивация вошла в проверяемый диапазон — та же
   логика `archived_within`, что у дельт (T-07). Имя каталога архива OpenSpec
   может нести префикс даты (`2026-10-07-add-limits`), поэтому идентичность —
   каталог целиком, без выделения `<id>`.
3. **Правило владения действует одинаково.** `delta::guard_with` принимает
   диапазон прогона исполнителя (`AgentRange`, ADR-055): покрытие, чьи
   файлы-носители (`DELTA.md`; proposal/design/tasks/specs change) появились
   или изменились в диапазоне, правку НЕ узаконивает — ни у change, ни у
   дельты. Такая правка — находка `self_approved` (error) в составляющей
   `delta_guard` (пост-гейт `harness_run` передаёт диапазон, как для
   `rule_weakened`/`control_plane`). Без диапазона (обычный CI по PR) правило
   не применяется: в PR change и правка приходят вместе по построению.
4. **Источник назван в отчёте.** Метки покрытий — `delta:<name>` и
   `openspec:<id>`: в `covered`/`mentions`/`archived_in_range` отчёта
   `GuardReport`, в текстовом рендере и в JSON MCP-инструмента `delta_guard`
   (аддитивные поля `sources`, `active_changes`, `self_approved`; ключи прежние).
5. **Состав источников — конфигурация кейса.** `[delta] sources = ["spine",
   "openspec"]` в `arch-harness.toml` кейса; дефолт — оба источника при
   наличии каталога `openspec/`, иначе только `spine` (поведение версий ≤ 0.3.13
   в репозиториях без OpenSpec не изменилось). Неизвестное имя или пустой
   список — ошибка: опечатка в конфиге контура не должна молча отключать
   источник покрытия.
6. **`delta new` при `sources = ["openspec"]`** не создаёт `DELTA.md`, а
   подсказывает оформить change средствами OpenSpec (та же проверка в
   MCP-инструменте `delta_propose`): markdown OpenSpec Spine не пишет.

## Alternatives

- **(а) Конвертировать change OpenSpec в DELTA.md при гейте** — отвергнуто:
  Spine начал бы писать чужой формат/свои дубли (правило 9), а двойной учёт
  остался бы — просто скрытый автоматикой.
- **(б) Отдельная составляющая `openspec_guard`** — отвергнуто: два гейта одной
  дисциплины («правка спайна описана изменением») с разными правилами архива и
  владения — источник рассинхрона; единый гейт с общим списком покрытий
  дешевле и честнее.
- **(в) Покрытие по `<id>` change из имени каталога архива без префикса даты** —
  отвергнуто: формат имени каталога архива у OpenSpec не зафиксирован
  (проверено чтением кода, не прогоном их CLI); сопоставление по каталогу
  целиком не зависит от их соглашения.

## Consequences

- Положительные: двойной учёт снят — команда на OpenSpec правит `model/` в
  рамках своего change без `DELTA.md`; правило владения закрывает обход через
  самодельный change симметрично самодельной дельте; отчёт гейта честно
  называет источник покрытия.
- Отрицательные: в пост-гейте `harness_run` покрытие (дельта или change),
  созданное исполнителем в его диапазоне, больше не узаконивает правку
  защищённых путей — оформление переносится в основной репозиторий решением
  владельца (та же цена, что у ADR-055 для ослаблений); метки покрытий в
  `covered`/`mentions` получили префикс источника — потребителям JSON,
  парсившим имя дельты без префикса, нужна миграция (формат значения).
- Граница: `delta_guard` проверяет наличие описания, а не его адекватность;
  содержание proposal/design остаётся работой ревьюера (паспорт вердикта).

## Обратная совместимость

- `gate-verdict/v1`, exit-коды 0/1/2/3 и состав составляющих не изменены;
  находка `self_approved` — существующий код (ADR-055), появляется только при
  переданном диапазоне исполнителя (пост-гейт).
- Репозиторий без `openspec/` работает с источником `spine` — вердикты
  идентичны 0.3.13.
- Поля `sources`, `active_changes`, `self_approved` в JSON инструмента
  `delta_guard` аддитивны; прежние ключи сохранены.
- Откат: `git revert`; поведение до ADR — `sources = ["spine"]` в кейсе.

## Reversibility

Высокая: источник `openspec` отключается строкой `[delta] sources = ["spine"]`
в кейсе (без правки кода); полный откат — revert коммита. Правило владения
отключается вместе с пост-гейтом (`post_gate = false`), как в ADR-055.
