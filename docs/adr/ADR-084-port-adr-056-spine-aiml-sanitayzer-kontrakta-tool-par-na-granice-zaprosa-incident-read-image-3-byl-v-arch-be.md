# ADR-084. Порт ADR-056 (spine-aiml): санитайзер контракта tool-пар на границе запроса — инцидент read_image:3 был в arch-be

- Date: 2026-10-14
- Status: Accepted
- Модель-автор: deepseek (spine-arch, агентная сессия)

## Context

Инцидент 2026-10-14 08:43: ход на kimi (k3) умер с HTTP 400 «assistant message with 'tool_calls'
must be followed by tool messages … did not have response messages: read_image:3». Первичный разбор
ошибочно отнёс сбой к редакции arch-ml (spine-aiml) — там и был реализован фикс (spine-aiml ADR-056,
коммит 3b146d0). Повторная сверка журнала падающей сессии
(`~/.arch-harness/sessions/session-20261014-084215-1311952.jsonl`, системный промпт банковской
редакции) показала: сбой был в **arch-be (этот репозиторий)**, у которого защиты контракта tool-пар
нет до сих пор.

Факты инцидента (проверены прямыми прогонами против `api.kimi.com/coding/v1`):
`read_image:3` — каноническая форма валидатора kimi `{имя}:{глобальный номер tool_call, 0-based}`;
журнал содержит оба tool-ответа; байт-в-байт реконструкция запроса валидна → расхождение
«история ↔ запрос» недетерминировано, класс ошибки фатален для хода агента.

## Decision

Портировать в arch-be решение spine-aiml ADR-056 (эталон — коммит `3b146d0` в
`/home/.../spine-aiml`), с адаптацией под расхождения редакций (прямой cherry-pick не накладывается):

1. `src/llm.rs` — `ToolPairRepair` + `sanitize_tool_pairs(&mut Vec<ChatMessage>) -> ToolPairRepair`:
   висячему `tool_call.id` достраивается синтетический tool-ответ-заглушка с явным маркером,
   tool-сироты удаляются; валидная история byte-identical, идемпотентно; работает на КОПИИ истории
   запроса (AD-5).
2. `src/retry.rs` — `is_tool_pair_contract_error(status, text)`: 400 + маркеры провайдера.
3. `src/agent.rs` — `build_request` прогоняет санитайзер и возвращает `ToolPairRepair`; ненулевой
   ремонт — `tracing::warn!` + событие `tool_pairs_repaired` в журнал сессии; error-путь LLM-запроса
   получает ветку «400 по контракту tool-пар → пересборка + ровно один повтор, без L3».
4. Тесты эталона портируются полностью: сценарий инцидента (второй read_image пачки без ответа),
   сироты, byte-identical валидной истории, идемпотентность, интеграционный на AgentSession.

Синхронность редакций: фикс считается парным — дрейф «одна редакция защищена, другая нет»
недопустим; при следующих правках агентного цикла сверять обе редакции.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Cherry-pick 3b146d0 как есть | Механическая простота | Не накладывается: agent.rs/llm.rs/retry.rs редакций разошлись |
| Не портировать (ждать слияния редакций) | Нулевая стоимость | Сбой повторяем именно в рабочей банковской редакции; слияние редакций не запланировано |
| Своя реализация «с нуля» под arch-be | — | Двойная работа и риск расхождения семантики с эталоном |

## Consequences

### Positive

- Рабочая редакция (arch-be) получает ту же защиту: 400 по контракту tool-пар перестаёт убивать ход.
- Семантика идентична эталону (тесты портируются дословно) — поведение редакций сопоставимо.

### Negative

- Парность фиксов надо поддерживать вручную, пока редакции живут раздельно (риск дрейфа при
  следующих правках цикла).
- Те же оговорки эталона: заглушка может дезориентировать модель (смягчено маркером); санитайзер без
  журнального события маскировал бы баги истории — событие обязательно.

## Reversibility

reversible: порт — чистая функция + точки вызова; удаление возвращает статус-кво без миграций.
