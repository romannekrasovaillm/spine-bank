# ADR-067. Покрытие требований OpenSpec — в едином гейте, гейте change и handoff-пакете

- Дата: 2026-10-08
- Статус: Proposed (волна F релиза 0.3.14, пункты F2/F3/F6 задания TASK-v2; принимает владелец)
- Модель-автор: kimi-k3 (подготовка), решение — человек

## Context

Адаптер OpenSpec умел считать покрытие требований (`openspec coverage`) и
гейтить архивацию change (`openspec gate --archive`), но оба были отдельными
командами вне единого гейта: MR, оставляющий SHALL активного change без
решения, проходил контур незамеченным, если проект не вызывал `openspec
coverage --strict` явно (репродукция — `docs/experiments/fork-repro-0.3.14.md`,
раздел F). Одновременно волна B (ADR-065) показала вторую половину проблемы:
правило с `covers:` может быть формальным — демонстрируемо беззубым
(`toothless`/`trivial`), и тогда «покрыто детектором» не отличить от «написано
слово».

Ограничения:

1. **Обратная совместимость:** `gate-verdict/v1`, exit-коды 0/1/2/3 и вердикты
   репозиториев без `openspec/` меняться не должны; ужесточения — только
   явным решением проекта (схема «warn → error по включению»).
2. **Markdown OpenSpec Spine не пишет** (правило 9 задания): handoff читает
   файлы change, не правя их.
3. **Зубья измеряются отдельно** (`arch-be rules teeth --save`,
   `.arch-handoff/teeth.json`, ADR-065): гейт читает сохранённое измерение и
   не имеет права падать на его отсутствии — «не измерено» ≠ «зубьев нет».

## Decision

1. **Составляющая `openspec_coverage` единого гейта (F2).** Прогоняется на
   любом маршруте; без каталога `openspec/` — SKIP с явной пометкой (паспорт
   вердикта подхватывает её в блок «не проверено»). Находка
   `requirement_uncovered` (требование без решения — ни детектора, ни
   `unverifiable` с owner) — `error`, если составляющая в `[gate.required]`
   маршрута, иначе `warn`: блокировка — осознанное решение проекта, как у
   `decision_quality`. Область — `[gate.openspec_coverage] scope`:
   `changed` (дефолт: требования дельт активных changes, затронутых диффом,
   плюс требования живых спек, чьи файлы изменены) или `all` (как
   `openspec coverage`). Осиротевшие `covers:` (F4) доезжают warn-находкой
   `covers_orphan`.
2. **Зубья покрытия (связка волн B и F).** Покрытие детектором расщепляется
   по доказательности: правило с подтверждёнными зубьями (запись `confirmed`
   в `teeth.json`, отпечаток сошёлся) — полное покрытие; без подтверждённых
   зубьев — «покрыто текстом», отдельной строкой отчёта (`covered =
   covered_teeth + covered_text`). Все покрывающие правила измерены беззубыми
   — warn-находка `requirement_text_only`; измерения нет вовсе — честное
   «зубья не измерены» в границах вердикта, без находок: отсутствие замера —
   не дефект реестра.
3. **`arch-be openspec gate --change <id>` (F3).** Гейт MR, реализующего
   change: покрытие требований его дельты (F2 в области change), `delta_guard`
   с источником `openspec` (правки защищённых путей обязаны упоминаться в
   change), `control check` по реестру и маршрут значимости по диффу
   `base..HEAD` (детектор триггеров, как у `gate --route auto`). Провал любой
   части — exit 1. Без git-репозитория `delta_guard` и маршрут честно
   помечаются недоступными и не притворяются пройденными. `--expiry` остаётся
   в roadmap.
4. **`arch-be handoff … --openspec-change <id>` (F6).** `proposal.md`,
   `design.md`, `tasks.md` и дельты спек change кладутся в пакет как
   `--spec` (первыми — лесенка усечения epic-context режет с хвоста, предмет
   задачи не должен резаться); порог контекста Critical считается с их
   учётом. Требования change добавляются в `RUBRIC.yaml` пакета критерием
   `openspec_change_requirements` (перечень id + SHALL) — приёмка по
   требованиям, а не по пересказу. Существующая `RUBRIC.yaml` не затирается:
   требования не вписываются, и пакет предупреждает. `MANIFEST.json` несёт
   `openspec_change` (аддитивно).

## Alternatives

- **(а) Отдельная команда `openspec gate --strict` в CI вместо составляющей** —
  отвергнуто: вердикт зависел бы от способа вызова, а не от состояния
  репозитория (та же претензия, по которой `model_validate` вошёл в гейт, Н2
  волны A 0.3.4).
- **(б) `requirement_uncovered` всегда error** — отвергнуто: ужесточение
  покраснело бы чужие пайплайны при обновлении без явного решения проекта
  (прецедент `decision_quality`, ADR-042).
- **(в) Покрытие текстом — блокирующая находка** — отвергнуто (это
  ужесточение): беззубое правило — дефект качества реестра, видимый
  `rules teeth` и ступенью 3 доверия; блокировать его в гейте покрытия
  требований — двойной учёт наказания. Доводка — warn `requirement_text_only`.
- **(г) Копия файлов change внутрь `.arch-handoff/`** — отвергнуто: дубль
  расходится с источником; пакет несёт тексты в `ARCHITECTURE.md`/`SPEC.md`
  (скомпилированные) и ссылки в `MANIFEST.json`, markdown OpenSpec не
  копируется и не правится (правило 9).

## Consequences

- Положительные: непокрытый SHALL активного change краснит единый гейт на
  маршрутах, где проект включил составляющую; «покрыто формально» отделено от
  «покрыто с подтверждёнными зубьями» одним числом в отчёте; MR по change
  гейтится одной командой; пакет исполнителю несёт требования change в
  рубрике приёмки.
- Отрицательные: составляющая присутствует в каждом вердикте (SKIP без
  `openspec/`) — паспорт и снапшоты вывода стали на строку длиннее;
  `openspec coverage --json` несёт два новых счётчика (аддитивно).
- Граница: составляющая проверяет наличие решения и зубьев, а не
  соответствие правила смыслу требования — это блок 2 паспорта и смысловые
  рубрики (ADR-052).

## Обратная совместимость

- `gate-verdict/v1`, exit-коды 0/1/2/3 и формат `CONSTRAINTS.yaml` не
  изменены; репозиторий без `openspec/` получает SKIP-строку, вердикт тот же.
- Поля `covered_teeth`/`covered_text` в `CoverageReport` и JSON инструмента
  `openspec_coverage` аддитивны (serde default); `openspec gate --archive`
  работает как раньше (позиционный `<change-id>` сохранён).
- Откат: `git revert`; составляющая выключается исключением из
  `[gate.required]` (строки конфига, без правки кода).

## Reversibility

Высокая: составляющая необязательна по построению (без включения в
`[gate.required]` — только отчёт и warn); `gate --change` и
`--openspec-change` — новые команды/флаги, их неиспользование возвращает
поведение 0.3.13.
