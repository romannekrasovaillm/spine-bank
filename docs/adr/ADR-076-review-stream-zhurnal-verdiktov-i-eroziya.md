# ADR-076. Пакетный ревью-поток с журналом вердиктов и кумулятивной эрозией (волна RS)

- Date: 2026-10-11
- Status: Accepted [ADOPTED] — команда `arch-be review stream <repo>
  --last N` с журналом `.arch-review/stream.jsonl` (upsert-by-sha) и
  кумулятивным отчётом `--report`; контракт `arch-be/review-stream/v1`
- Модель-автор: spine-arch (claude)
- Пересмотр: при появлении второго носителя истории вердиктов (фоновый
  CI-демон, серверный реестр по ADR-033 п. «процессная обвязка снаружи») —
  пересмотреть формат журнала; при необходимости различать «запись
  устарела» (пересчёт по смене входов) — добавить в строку версию
  significance-конфига; при снятии требования «файлы, не сервисы»
  (ADR-033) — рассмотреть БД вместо jsonl
- Провенанс: продолжает `arch-diff` (ADR-063/ADR-064) и `review inbox`
  («Review inbox — очередь ревью по маршрутам значимости»); опирается на
  D3 (ADR-075, `inferred_edges` в inbox), на границу продукта
  «файлы, не сервисы» (ADR-033) и на отказ git-notes (ADR-064); номер
  ADR-075 последний занят — эта запись 076

## Context

**1. Поток PR терял состояние между сессиями.** ArchBenchmarks_v2, задача
AB-09: поток из ~60 коммитов, разобранный за 3 сессии кодового агента.
Вердикт `arch-diff` — одномоментный: он оценивает один PR против одного
основания и не помнит прошлых. Значит, к третьей сессии агент не знает,
что 40 коммитов до него уже дали 12 значимых, что маршрут трижды
поднимался до standard, что счётчик inferred-рёбер растёт. Состояние
потока жило только в голове агента и умирало вместе с контекстом окна.

**2. Значимое размазано по потоку — не видно на одном PR.** На пилоте v1
(10 коммитов) один PR с изменённым таймаутом контракта поднял
`ArchScore` на 8 пунктов — но в сам момент ревью этот PR выглядел как
«fast, triggers=[], graph_delta=false»: значимость проявилась не в
декомпозиции одного коммита, а **накопленная** (таймаут стал следствием
серии правок конфигурации). Однокоммитный вердикт такое не показывает в
принципе: нужен кумулятивный счётчик по окнам.

**3. `review inbox` (K7) видел только текущие артефакты.** Ящик
сканировал `.arch-review/*.json` рабочих артефактов и показывал
неподтверждённые решения и inferred-рёбра (D3), но не имел памяти о
вердиктах прошедших коммитов: «висит без подтверждения 9 дней» по
вчерашнему коммиту невозможно, если вердикт нигде не сохранён.

**4. Цена прогона — секунды, а не часы.** Реконструкция `arch-diff`
детерминированна (AD-2, без LLM) и на petclinic-потоке держит
≈1.3 с/коммит; это позволяет прогонять поток целиком, а не выборочно,
и хранить журнал, а не пересчитывать его.

## Decision

1. **Команда `review stream <repo> --last N`.** Идёт по первым родителям
   (`git log --first-parent`) `N` последних коммитов; для каждого считает
   лёгкий вердикт `arch-diff` (route / triggers / graph_delta /
   added_nodes / added_edges / inferred_edges) и печатает сводку потока:
   сколько fast/standard/critical, какие коммиты подняли маршрут,
   значимое по композиции против шума (без архитектурной дельты).
   Корневой коммит сравнивается с `EMPTY_TREE`. Флаги: `--window M`
   (размер окна отчёта, по умолчанию 10), `--report` (только отчёт по
   журналу, без прогона), `--format text|json` (headless JSON).

2. **Журнал `.arch-review/stream.jsonl` — one line = one verdict.**
   Строка: `{sha, date, route, score, triggers, graph_delta, added_nodes,
   added_edges, inferred_edges, verdict_hash}`. `verdict_hash` —
   `sha256:` от канонического представления записи (детерминизм, AD-2):
   повторный прогон того же sha даёт тот же хеш. Запись **upsert по
   sha**: тот же sha обновляется на месте, новый — добавляется в конец.
   Так повторный прогон перекрывающегося диапазона (`--last 30`, затем
   `--last 10`) **не дублирует** записей и **сохраняет** старые.
   Расхождение с append-only моделью (ADR-064 `accept`): там важен след
   решения человека, здесь — состояние вердикта, а он детерминирован по
   входу, поэтому перезапись той же записи аудита не теряет.

3. **Кумулятивные метрики эрозии — `review stream --report`.** Читает
   журнал и печатает: долю значимых в целых промилле (`significant /
   total × 1000`; целое — чтобы JSON-контракт не нёс плавающую точку),
   шум (без архитектурной дельты), число дельт графа, **кумулятивный
   счётчик inferred-рёбер** (D3-механика, ADR-075), динамику маршрутов
   **по окнам** (таблица: f/s/c, значимых, `inf∑`), топ-триггеры
   (`new_vendor`, `new_component`, …) с частотами.

4. **Интеграция с `review inbox`.** Ящик дополняется разделом «Ждут
   подтверждения»: записи журнала старше `DEFAULT_AWAITING_DAYS = 7` дней
   без подтверждения (для inferred-рёбер — «требуется подтверждение»).
   Поле `awaiting` добавлено аддитивно в `InboxReport` (JSON-контракт
   `arch-be/review-inbox/v1` не ломается; массив и `awaiting_days`
   добавлены, старые ключи без изменений).

5. **Журнал — файл в репозитории, в `.gitignore` НЕ добавляется.**
   Явное решение пользователя: владелец репозитория сам решает, версионировать
   `.arch-review/stream.jsonl` или нет. Инструмент лишь не прячет его.

**Поправки:** нет (первая редакция).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. jsonl-журнал в рабочем дереве, upsert-by-sha, отчёт по окнам** (принято) | Контур офлайн, без сети; журнал читается `cat`/`jq`; повторный прогон идемпотентен (sha — естественный ключ); согласуется с «файлы, не сервисы» (ADR-033) и с существующим `.arch-review/*.json` | Журнал растёт линейно; при параллельных ветках возможны merge-конфликты в одной строке |
| B. Журнал в git notes / отдельной ветке | Не лежит в рабочем дереве; привязан к sha | Требует сети и push (граница C-34, офлайн-контур); **отвергнуто в ADR-064** для журнала модели — та же причина; чтение через `git notes show` неудобно для отчёта по окнам |
| C. БД/сервис (PostgreSQL/SQLite, отдельный демон) | Запросы, индексы, конкурентность из коробки | Прямо противоречит ADR-033 (граница продукта: «файлы, не сервисы», процессная обвязка снаружи); новый runtime-контракт и зависимость там, где хватает jsonl; ломает офлайн-контур |
| D. Ничего не хранить, пересчитывать поток каждый раз | Нет состояния, нет merge-конфликтов | Нельзя показать «висит без подтверждения 9 дней» и кумулятивный `inf∑` за прошлые сессии — а именно это и есть AB-09; пересчёт всего потока на каждый вопрос дороже хранения |
| E. Записывать в сам `arch-diff` артефакт, расширив `arch-diff/v1` | Один артефакт вместо журнала | Смешивает одномоментный вердикт PR (данные CI) и накопленный журнал потока; байт-в-байт аддитивность v1 ломается для потребителей; `arch-diff` не место для межкоммитной памяти |

## Consequences

### Positive

- Поток перестаёт быть без памяти: кумулятивный журнал — единственный
  носитель состояния между сессиями; третья сессия видит, что было в
  первых двух (доля значимых, подъёмы маршрута, суммарные inferred-рёбра).
- Повторный прогон дешёв и идемпотентен: upsert-by-sha не плодит копий
  (живой прогон: `--last 30` дал 30 строк, затем `--last 10` оставил
  ровно 30), старые записи сохраняются.
- Эрозия измерима: `--report` печатает долю значимых в промилле, окна и
  топ-триггеры — «размазанное по потоку значимое» (пилот v1: сдвиг
  ArchScore на 8 пунктов одним таймаутом) становится видимым числом.
- `review inbox` получает время: записи старше 7 дней без подтверждения
  не теряются между сессиями.
- Контракт аддитивен: `arch-be/review-stream/v1` — новый файл; `arch-diff/v1`
  и `review-inbox/v1` не ломаются.

### Negative

- **Журнал в репозитории → merge-конфликты.** Две ветки, ревьюящие
  пересекающиеся sha, правят одну jsonl-строку. Митигация: upsert по sha
  делает содержимое детерминированным (одна и та же строка), конфликт
  разрешается «любой стороной»; инструмента объединения пока нет.
- **Размер растёт линейно** (≈1 строка на коммит). На потоке в 60
  коммитов это доли мегабайта; на очень длинной истории — вопрос
  архивации. Митигация: `--last N` ограничивает прогон, а не журнал;
  при необходимости — отдельный `--prune`.
- **`--last N` не берёт merge-коммиты** (только первые родители):
  значимое, пришедшее влитым сайд-бранчем, в журнал потоковых вердиктов
  не попадёт напрямую. Осознанная цена линейного обхода.
- **Доля значимых зависит от конфигурации significance**: `limits()` и
  `diff_globs()` читаются из проекта; смена порогов меняет историю оценок
  при том же sha. Журнал хранит вердикт «как было посчитано», а не
  пересчитывает — при смене конфига запись устаревает молча (кандидат на
  поле-версию, см. Пересмотр).

## Reversibility

**Обратимо, цена низкая.** Журнал — обычный файл: откат — удалить
`.arch-review/stream.jsonl`; потребителей, кроме `--report` и раздела
«Ждут подтверждения» в inbox, нет. Команда `review stream` снимается
удалением `ReviewCmd::Stream` и `src/review_stream.rs` — остальные
подкоманды Review не задеты. Поле `awaiting` в `InboxReport` —
аддитивное: откат — убрать поле, раздел рендера и ключ JSON; контракт
`review-inbox/v1` вернётся к прежним ключам. Никакая запись не подменяла
данные CI (сырой `route` `arch-diff` не менялся). Необратим ровно один
аспект — номер ADR-076 (номера не переиспользуются): цена фиксации, а не
риск отката.
