# ADR-050. Библиотека шаблонов исполняемых правил: предложение, а не правка

- Date: 2026-09-20
- Status: Accepted
- Reversibility: обратимо. Снятие — удаление каталога `assets/rule-templates/` и
  модуля `rule_templates`: детектор, строка паспорта и звено трассировки
  исчезают, ничего не ломая (все они аддитивны и по умолчанию молчат).
  Необратимо другое: применение шаблона кейсом пишет файлы в `skeleton/` и
  lock-файл — откат требует удалить их вручную, харнесс не откатывает.
- Judge: judge_is_author — рубрикой `adr_quality` документ оценивала та же
  модель, что его писала (независимый судья в этом окружении недоступен)

## Context

Паспорт вердикта 0.3.4 честно сообщает строкой блока 2: «правил, судящих по
ТЕКСТУ файла, — N из M; они зеленеют и когда инвариант соблюдён, и когда о нём
просто написали». Это признание проблемы, но не помощь: инструмент называет
слабость контроля общим числом и молчит о том, **какие инварианты** ею задеты и
что с этим делать.

Живое исследование на кейсе «Кошелёк цифрового рубля физлица» (2026-09-19)
показало цену молчания: четыре инварианта из девяти названы в отчёте несущими,
но проверку поведения получил один. Кандидат `executable-invariants` в
`rules_suggest` замолкает после первого же `command_succeeds` в реестре, говорит
о кейсе в целом, а не об инварианте, и предлагает закомментированный
`cargo test` — то есть перекладывает на архитектора и постановку задачи, и
поиск формы.

При этом каждый кейс библиотеки уже содержит walking skeleton с тестами
(`кейсы/salary-payments/tests/`), а спайны формулируют проверяемые свойства
(«две доставки с одним ключом → один эффект»). Не хватает не материала, а
короткого пути от записи к проверке.

## Decision

1. **Библиотека шаблонов исполняемых правил** (`assets/rule-templates/<id>/`,
   встроена в бинарь как ассеты, распаковывается `arch-be init`). Восемь
   шаблонов по архитектурным паттернам спайнов (`idempotency-key`,
   `unknown-outcome-no-resend`, `saga-reserve-compensation`,
   `single-source-of-truth`, `append-only-journal`, `no-pii-in-logs`,
   `consent-before-auto-action`, `validate-before-side-effect`) плюс заготовка
   `generic-property-test` для нераспознанного паттерна. Каждый поставляет
   правило `command_succeeds`, тест свойства, фейк внешней системы и эталонную
   реализацию — на двух языках (python/pytest и Java/JUnit 5) по решению
   владельца задачи.

2. **Три принципа, обязательные для каждого шаблона.**
   - **П1. Свойство, а не протокол.** Тест проверяет архитектурное свойство на
     фейке внешней системы («после таймаута ровно одна отправка»), а не
     конкретный протокол: иначе шаблон не переносим между кейсами.
   - **П2. Беззубый тест хуже текстового правила.** У каждого исполняемого
     шаблона есть нарушающая реализация, и `arch-be rules template verify`
     механикой проверяет, что тест на ней **падает**. Тест, зелёный при любом
     поведении, создаёт ложное чувство проверки и попадает в счёт «проверяют
     поведение» — это хуже честного `must_contain`.
   - **П3. Spine предлагает, архитектор принимает.** `apply` кладёт файлы в
     `skeleton/`, пишет `.arch-handoff/rule-templates.lock` (шаблон, версия,
     инвариант, файлы, SHA-256) и **печатает** фрагмент правила со свободным
     `C-NNN` и строку `verified_by`. Реестр правил и спайн модуль не правит:
     это защищённые файлы, их изменение идёт дельтой. Заготовка правила —
     `severity: error`: нарушение инварианта обязано краснеть, иначе исполняемая
     проверка не отличается от текстовой по последствиям (понизить до `warn`
     архитектор может, пока проверка не перенесена на настоящий код).

3. **Детектор на каждый инвариант.** По каждой сущности `type: ad` модели
   собираются правила из `verified_by` (и обратная связь — поле `ad:` реестра),
   определяется их тип, и если ни одно не входит в `BEHAVIOUR_RULE_KINDS` —
   выдаётся кандидат `executable-invariant:AD-00N` с шаблонами, подобранными по
   тексту инварианта в спайне (детерминированно, без LLM, до двух лучших).
   Легаси-кандидат `executable-invariants` остаётся на прежних условиях.

4. **Поимённая видимость.** Паспорт вердикта после общей строки называет
   инварианты без проверки поведения (несущие первыми, список ограничен, при
   обрезании — счётчик); трассировка получает седьмое, информационное звено
   «AD → исполняемое правило»; третья ступень доверия в детали показывает
   «инвариантов с проверкой поведения: k из n».

5. **Требование — через конфиг, а не по умолчанию.** `[trace]
   executable_required = "off|warn|error"`, дефолт `off`: находка
   `ad-text-only` появляется только по явному решению проекта и адресуется
   несущим инвариантам, а если признак `load_bearing` нигде не задан — всем
   непокрытым. Новое необязательное поле `load_bearing: true` во frontmatter
   инварианта (`ADR-050` ← это решение).

6. **Проверка зубов на уровне кейса** (`rules template verify --dir`): по
   lock-файлу во временной копии кейса эталонная реализация подменяется
   нарушающей; тест остался зелёным — находка `executable_rule_toothless`
   (в вердикт гейта не входит, печатается командой и в `rules-report`).
   Файлы разошлись с lock — «адаптирован: проверка зубов неприменима».

## Alternatives

- **Расширить существующий кандидат `executable-invariants`.** Дешевле, но
  неверно по сути: кандидат про кейс, а пробел — про инвариант. «В реестре нет
  `command_succeeds`» перестаёт быть правдой после первого же правила, и
  сигнал замолкает ровно там, где работа только начинается (один инвариант из
  четырёх закрыт).
- **Генерировать тесты моделью.** Отвергнуто стоп-условием задания: шаблоны
  статические, а подгонку под кейс делает агент харнесса, не ядро. Плюс
  сгенерированный тест нельзя проверить на зубы без эталона — а именно эта
  проверка и делает библиотеку честной.
- **Считать `unverifiable` пробелом.** Отвергнуто: это обоснованный отказ
  архитектора (ADR-006), а не недоработка. Детектор молчит по таким инвариантам.
- **Включить находку `ad-text-only` по умолчанию (`warn`).** Отвергнуто:
  покраснение чужих пайплайнов после обновления — цена выше пользы; требование
  включается ключом конфига.
- **Только python, без Java.** Отвергнуто решением владельца задачи: кейсы
  банка живут и на JVM. Цена — вторая половина у каждого шаблона и
  прогонщик: Maven, а без него — JUnit-консоль флагом `--java-jar`
  (бинарный jar в git не кладём: ассеты встраиваются `include_str!`).

## Consequences

- Восемь шаблонов × два языка = 16 исполняемых проверок свойств; `rules template
  verify --all` прогоняет 32 проверки (эталон и нарушение на каждый язык) за
  ~40 секунд с JUnit-консолью.
- Применённое правило идёт в **каждом** прогоне гейта, включая Stop-хук и
  pre-push: исполняемая проверка — не бесплатная. Это записано в документации.
- Существующие установки: `write_defaults` не перезаписывает файлы, поэтому
  новые шаблоны приедут на диск, а обновлённые скиллы — нет (до `init --refresh`).
- Паспорт, трассировка и доверие получили по строке или звену — все аддитивно,
  вердикт по умолчанию не меняется.
- Граница честности: механика проверяет, что **есть исполняемая проверка и есть
  ли у неё зубы**. Соответствие теста смыслу инварианта — работа рубрики
  `rule_invariant_fit` (задание про смысловые рубрики), здесь её нет.
