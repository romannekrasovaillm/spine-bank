# ADR-042. Качество решений как составляющая гейта — через отчёт судьи, без LLM в ядре

- Date: 2026-09-19
- Status: Accepted
- Reversibility: обратимо — составляющая включается только через
  `[gate.required]`, по умолчанию SKIP; выключение = удаление имени из списка

## Context

Рубрика `adr_quality` различает сильный и слабый ADR (3,90 против 1,30) и
обнуляет выдуманные цитаты (`evidence_not_found`), но оценка живёт **вне
гейта**: ADR с 1,30 проходит `gate`, pre-push и Stop-хук, потому что
механический контур проверяет наличие секции «Alternatives», а не качество
её содержимого. Red-team дефект D9 («картонный» ADR: секции есть, содержания
нет) на 0.3.3 не ловится никем.

Добавить LLM-судью в ядро нельзя: AD-2 (детерминированный слой контроля без
LLM). Но отчёт судьи — это **артефакт**, и его можно проверить механически:
есть ли он, к какой редакции документа относится, какой балл записан.

## Decision

**1. Машиночитаемый отчёт рубрики.** `rubric::write_artifact` пишет
`<repo>/reports/rubric/<slug>.json` (схема `arch-be/rubric-report/v1`):
имя рубрики, относительный путь цели, `target_sha256` содержимого,
`judge_model`, `author_model`, `weighted_total`, `verdict`, флаги `unstable`
и `evidence_not_found`, метка времени. Пишут его `arch-be rubric run` (CLI) и
MCP `rubric_verify` (под `--rw`: read-only контур MCP не оставляет след в
рабочем каталоге, в ответе остаётся строка о том, почему отчёт не записан).

Корень репозитория для отчёта — `rubric::repo_root_of`: ближайший вверх
каталог с `.git` или `.arch-handoff`. Иначе отчёт лёг бы рядом с документом
(`docs/adr/reports/…`), где гейт его не ищет.

**2. Составляющая `decision_quality`.** Для каждого `docs/adr/ADR-*.md` со
статусом Accepted (разбор форм `Status:`/`Статус:`, с `**` и без) ищет отчёт:
сначала по совпадению `target_sha256`, затем по пути цели. Далее:

| Состояние | Находка | Severity |
|---|---|---|
| отчёта нет | `rubric_report_missing` | error |
| путь тот же, хэш другой | `rubric_report_stale` | error |
| балл ниже `[gate.decision_quality] min_score` | `decision_quality_low` | error |
| `judge_model == author_model` или `author_model` не указан | `judge_is_author` | warn (`error` при `require_distinct_judge = true`) |

Нет каталога `docs/adr` или нет ни одного Accepted-ADR → SKIP.

**3. По умолчанию составляющая выключена.** В `[gate.required]` её нет ни на
одном маршруте: без включения она SKIP. Причина — правило поэтапного
ужесточения (ТЗ 1.5): гейт, который вдруг начал требовать отчёт судьи у всех
существующих проектов, покраснил бы чужие пайплайны без предупреждения.
Включение — одна строка конфига:

```toml
[gate.required]
standard = ["fitness", "spine_lint", "trace_check", "rule_weakened", "nfr",
            "model_validate", "decision_quality"]

[gate.decision_quality]
min_score = 3.5
require_distinct_judge = false
```

**4. Предупреждения не теряются на PASS.** `GateComponent::pass_with_findings`
сохраняет warn-находки у пройденной составляющей: `judge_is_author` — вердикт
судьи о своей же работе, он обязан доезжать до читателя, даже когда балл выше
порога.

## Alternatives

**А. LLM-судья прямо в гейте.** Отклонено: AD-2 и правило ТЗ «без LLM в ядре».
Гейт обязан быть детерминированным и работающим офлайн; судья — отдельный
контур, чей результат материализуется в файл.

**Б. Составляющая обязательна на Critical по умолчанию.** Отклонено: на момент
обновления ни у одного существующего проекта нет отчётов, и все они получили
бы `INCOMPLETE` (exit 3) после апгрейда. Схема «SKIP по умолчанию → включение
флагом» оставляет миграционный коридор.

**В. Проверять «свежесть» отчёта по времени (`judged_at`), а не по хэшу.**
Отклонено: время не говорит, о какой редакции судили. Правка ADR через минуту
после оценки — уже другая редакция, и балл к ней не относится; обратно, старая
оценка того же текста остаётся валидной сколько угодно долго.

**Г. Писать отчёт всегда, включая read-only MCP.** Отклонено: read-only контур
MCP — это обещание «вызов не оставляет следов в рабочем каталоге клиента».
Нарушать его ради удобства нельзя; под `--rw` запись разрешена, и там отчёт
пишется.

## Consequences

**Что может покраснеть после обновления.** Ничего: составляющая выключена по
умолчанию. Проект, который её включит, обязан сначала прогнать судью по своим
Accepted-ADR — иначе увидит `rubric_report_missing` на каждом из них.

**Порог 3,5** — стартовое предложение (как в чек-листе скилла `adr-authoring`),
не измеренный оптимум: ADR «проходного» качества в реальных прогонах даёт
3,90, «картонный» — 1,30. Порог настраивается.

**Честная граница.** Составляющая проверяет НАЛИЧИЕ и СВЕЖЕСТЬ оценки и
записанный балл — не смысл решения и не подлинность судейства. Судья, судивший
свою работу, помечается (`judge_is_author`), но механика не может доказать,
что модель-судья действительно была той, что записана. Это место блока 2
паспорта вердикта (W1).

**Проверяемость.** Тесты `decision_quality_is_skip_by_default`,
`decision_quality_fails_below_threshold`, `decision_quality_flags_stale_report`,
`decision_quality_warns_when_judge_is_author`,
`decision_quality_requires_report_when_enabled`. На red-team наборе это
закрывает дефект D9.
