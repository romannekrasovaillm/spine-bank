# ADR-061. Детектор значимости: new_vendor — только новые имена пакетов, api_contract_change — с классификацией contract_diff

- Дата: 2026-10-07
- Статус: Proposed (волна D релиза 0.3.14, пункт D3 задания TASK-v2; принимает человек)
- Модель-автор: kimi-k2.5 (подготовка), решение — человек

## Context

Детектор маршрута значимости (`src/control/diff_triggers.rs`, S-1, ADR-034)
имеет два ложных источника шума, подтверждённых воспроизводящими тестами
(волна D, D3):

1. **`new_vendor` зажигается на смене версии существующего пакета.** Детектор
   срабатывал на любую добавленную строку, похожую на зависимость, — правка
   `serde = "1.0"` → `serde = "1.1"` в `Cargo.toml` давала тот же триггер, что
   и появление нового вендора. Bump версии — рутина сопровождения, а не
   архитектурное событие; каждый такой дифф завышал маршрут (score +1,
   вплоть до ложного Standard вместо Fast) и размывал доверие к детектору.
   Воспроизведение: тест `new_vendor_fires_only_on_new_dependency_name`
   (падал до фикса).
2. **`api_contract_change` не отличал аддитивное изменение от ломающего.**
   Срабатывание на правку контракта сообщало только факт правки, хотя
   классификатор `src/contract_diff/` (CD-001…CD-010 и далее по форматам)
   уже умеет отличать ломающий дифф от аддитивного. Ревьюер маршрута не
   видел, чем правка грозит потребителям. Воспроизведение: тест
   `api_contract_change_is_classified_breaking_or_additive` (падал до фикса).

Замер доли ложных срабатываний `new_vendor` (смена версии) на истории
spine-bank — `docs/experiments/significance-replay.md` (пункт D4 той же
волны, прогон `arch-be control score --replay HEAD` на 437 коммитах):
по старой логике срабатываний было бы 24, из них истинно новые имена — 5,
только смена версий — 19: **доля шума ≈ 79 %** (релизные bump'ы уходили в
Standard). Остаточный шум — ключи секций `[package]`/`[features]` новых
манифестов, консервативно считаемые новыми именами (fail-safe, см.
Consequences).

## Decision

1. **`new_vendor` зажигается только на новом имени пакета.** Для изменённого
   манифеста зависимостей (`Cargo.toml`/`pom.xml`/`package.json`/`go.mod`)
   имена добавленных строк-зависимостей сверяются с именами в версии
   манифеста на базе диффа (`git show <base>:<path>`). Имя, бывшее на базе,
   — обновление версии: триггер НЕ зажигается, а в `DiffTriggers.notes`
   пишется «обновление зависимости <name> в <path> (смена версии, не новый
   вендор)». Имя, которого на базе не было, — срабатывание, основание
   перечисляет новые имена. Это **ослабление детектора** (исключение из
   правила «детектор только добавляет», раздел 1 правила 8 TASK-v2) — поэтому
   вводится отдельным ADR.
2. **Консервативные оговорки ослабления.** Строка зависимости, имя из которой
   не извлеклось эвристикой, считается новым именем (срабатывание). Манифест,
   появившийся в этом диффе (нет базы), — все его зависимости новые.
   Недоступность базовой версии — прежнее поведение (срабатывание).
3. **`api_contract_change` срабатывает как раньше** (изменение контракта
   значимо само по себе), но основание и `notes` получают классификацию
   `contract_diff` по содержимому обеих версий: «ломающее (error-находок:
   N)» / «аддитивное/совместимое» / «без классификации (причина)».
   Классифицируются только изменённые файлы ('M'): добавленный контракт
   аддитивен по определению, удалённый — ломающий по определению. Для этого
   `contract_diff` получает строковую форму `diff_report_str` (дифф без
   файлов на диске, версии читаются из git).

## Alternatives

- **Оставить как есть (шум терпим).** Отвергнуто: рутинные bump'ы зависимостей
  — самый частый дифф зрелого репозитория, и каждый из них ложно поднимал
  маршрут; доверие к детектору — главный актив anti-bypass floor.
- **Полный парсер манифестов (toml/JSON/XML).** Отвергнуто: новых
  зависимостей в `[dependencies]` быть не должно (правило задания), а
  эвристика по имени покрывает канонические формы строк; нераспознанная
  строка консервативно считается новым именем.
- **Классификацию контрактов делать блокирующей находкой.** Отвергнуто:
  класс — контекст для ревьюера маршрута, а не вердикт; ломающий дифф
  контракта и так поднимает маршрут, а блокировку даёт `contract_diff`
  как самостоятельный инструмент/правило.

## Consequences

- Положительные: рутинные bump'ы версий перестают завышать маршрут (замер
  доли — в significance-replay.md); ревьюер видит класс изменения контракта
  рядом с фактом правки; `notes` доезжают до CLI (`control score`) и MCP
  (`significance_from_diff`, ключ `notes`).
- Отрицательные/границы: ослабление опирается на эвристику извлечения имён —
  экзотическая форма записи зависимости может быть принята за новое имя
  (ложное срабатывание сохранено как fail-safe); для диапазона `A...HEAD`
  старой версией контракта/манифеста берётся сам `A`, а не merge-base
  (приближение, в типовом CI база — предок); в режиме диапазона опознание
  контракта «по содержимому» читает рабочее дерево (для реплея истории
  контракт без «openapi» в имени и вне каталога контрактов виден, только
  если путь существует в текущем дереве).
- Обратная совместимость: срабатывание `api_contract_change` не меняется;
  `new_vendor` сужается по ADR; `DiffTriggers.notes` — аддитивное поле;
  схемы `gate-verdict/v1` и `verdict-passport/v1` не затронуты.

## Reversibility

Высокая: поведение детектора возвращается откатом коммита; поле `notes`
аддитивно и может игнорироваться читателями. Если замер D4 покажет, что доля
истинно новых вендоров среди срабатываний `new_vendor` была высокой и
ослабление теряет реальные сигналы (нераспознанные формы записи), эвристику
имён расширяют точечно, не меняя решения.
