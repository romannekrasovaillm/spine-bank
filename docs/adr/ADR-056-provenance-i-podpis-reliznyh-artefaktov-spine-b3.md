# ADR-056. Provenance и подпись релизных артефактов Spine (B3)

- Дата: 2026-10-03
- Статус: Accepted (вариант (а) выбран владельцем 2026-10-03 из трёх предложенных; волна B релиза 0.3.12, пункт B3 задания TASK-Spine-Core-0.3.12.md)
- Модель-автор: deepseek (подготовка), решение — человек

## Context

Релиз Spine публикует восемь бинарей (`arch-be` и `arch-be-core` под
linux-x86_64, linux-aarch64, macos-arm64, windows-x86_64) и сводный
`SHA256SUMS` в GitHub Release по тегу `v*` (`.github/workflows/release.yml`).
Потребитель артефакта — в том числе контур банка — сейчас может проверить
только целостность (хэш из `SHA256SUMS`), но не **происхождение**: что бинарь
собран из заявленного коммита именно этим workflow, а не подменён на любом
шаге между сборкой и скачиванием. Это открытый GAP из `docs/threat-model.md`
§5 и `docs/supply-chain.md`.

Дополнительная сила — волна A этой же дельты: контрольная плоскость теперь
проверяет *результат агента*, но цепочка «исходники → CI → релизный артефакт»
остаётся без верифицируемого звена. B1 (релиз только с зелёного CI) закрывает
«собран с красного коммита», B3 закрывает «собран не тем, чем заявлено».

Ограничение среды: `SHA256SUMS` и артефакты публикуются на github.com;
keyless-инфраструктура Sigstore доступна (публичный репозиторий). В контуре
банка прямое обращение к Fulcio/Rekor может быть недоступно, а ГОСТ-подпись
требуется средствами заказчика.

## Decision

**Принят вариант (а) — GitHub-native SLSA.** В `release.yml` (по тегу `v*`):

1. джоба публикации получает `permissions: id-token: write, attestations: write`
   (в дополнение к существующему `contents: write`) — минимально необходимый
   набор для OIDC-аттестации;
2. `actions/attest-build-provenance` выпускает SLSA build provenance для
   собранных `dist/arch-be-*`;
3. `cosign sign-blob` (keyless, Sigstore) подписывает `SHA256SUMS`;
4. инструкция проверки (`gh attestation verify <file> --repo <owner/repo>` и
   `cosign verify-blob` с ожидаемыми identity/issuer) добавляется в
   `docs/supply-chain.md`.

Версии обеих actions фиксируются по полному SHA с комментарием версии —
требование B4 той же волны; точные версии — **[ТРЕБУЕТ ПРОВЕРКИ]** по
первоисточнику в момент реализации (в подготовке сеть была недоступна).

**Честная граница:** ГОСТ-подпись для контура банка этим решением **не**
закрывается; keyless-цепочка предполагает доступ к GitHub/Sigstore. Для
контура заказчика остаётся открытый GAP — вынесен в `docs/supply-chain.md`
как процедура для заказчика (вне автоматики Spine), кандидат в отдельный
ADR, если потребуется штатная поддержка ГОСТ.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **(а) GitHub-native SLSA — ✅ выбран:** `actions/attest-build-provenance` для всех `dist/*` + `cosign sign-blob` (keyless, Sigstore) для `SHA256SUMS`. Проверка: `gh attestation verify <file> --repo …`, `cosign verify-blob`. `permissions: id-token: write, attestations: write` в джобе публикации. | Нет долгоживущих секретов-ключей (OIDC); SLSA Build L2/L3 без управления ключами; проверка одной командой у потребителя; размещение аттестаций в GitHub API рядом с релизом. | Жёсткая зависимость от инфраструктуры GitHub + Sigstore (Fulcio/Rekor): в закрытом контуре проверка/выпуск недоступны; ГОСТ-требования банка не покрываются; нужен сетевой доступ CI к Fulcio/Rekor. |
| **(б) Ключевая подпись GPG/ГОСТ:** `gpg --detach-sign` (или КриптоПро в банковском раннере) для `SHA256SUMS`; открытый ключ публикуется в репозитории. Проверка — по инструкции `docs/supply-chain.md`. | Работает офлайн и в закрытом контуре; привычная банку модель доверия (сертификат/ключ подписи); ГОСТ-подпись закрывает регуляторное требование напрямую. | Приватный ключ (или ГОСТ-ключ) как секрет CI — новая критичная поверхность (утечка = подделка любого релиза); ротация и отзыв — отдельный процесс; provenance (связь «коммит → бинарь») сам по себе не даётся, только целостность подписанного манифеста. |
| **(в) Гибрид:** публичный релиз на GitHub — по (а) (SLSA-provenance + keyless `cosign`); для контура заказчика — документированная процедура перехода на (б): ГОСТ-подпись силами заказчика над опубликованным `SHA256SUMS`, ключи банка в банковском же хранилище, в GitHub не попадают. | GitHub-потребитель получает максимальную проверяемость без секретов; контур банка получает ГОСТ-совместимый путь без компрометации ключей в публичном CI; граница «где какие ключи» явно проведена. | Два механизма и две инструкции сопровождения; часть работы (ГОСТ-подпись) выносится за периметр репозитория — в README/`docs/supply-chain.md` нужно честно отметить, что это ответственность заказчика, а не автоматика Spine. |

**Рекомендация подготовки:** вариант **(в)** — публичный релиз не должен
держать приватные ключи, а требование контура банка закрывается процедурой
на стороне заказчика; вариант (а) как минимум обязателен внутри (в).

## Consequences

### Positive

- Потребитель может верифицировать происхождение артефакта, а не только хэш.
- Проверяемость релиза становится воспроизводимой командой, пригодной для
  аудита поставки (звено «CI → релиз» в модели эшелонированной защиты).

### Negative

- (а)/(в): зависимость от внешней инфраструктуры и сетевого доступа CI;
  при недоступности Fulcio/Rekor прогон релиза падает — нужен явный
  fail-closed либо осознанный fallback (решение владельца).
- (б): хранение ключа подписи в секретах CI — новая критичная поверхность;
  требуется регламент ротации, иначе B3 сам создаёт класс риска, который
  волна A закрывала.
- Любой вариант добавляет шаг в `release.yml` — растёт время релиза и
  число точек отказа (митигация: шаг после сборки, отдельной джобой, редкий
  триггер по тегу).
- Инструкции проверки должны поддерживаться; устаревшая инструкция хуже
  отсутствующей (митигация: проверка инструкции — критерий приёмки B3).

## Reversibility

**Reversible** для (а): аттестации и подписи — дополнительные артефакты,
отключение шага не ломает публикацию бинарей. **Costly** для (б): после
внешнего распространения открытого ключа и появления потребителей,
проверяющих подпись, смена механизма требует согласованного перехода
(двойной период). Откат любого варианта — `git revert` коммита `ci(B3)`,
при (б) дополнительно отзыв/архивация ключа.
