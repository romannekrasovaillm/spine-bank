# ADR-054. Выделение ядра `spine-core` в cargo workspace: план сплита на 0.4.0

- Date: 2026-09-23
- Status: Proposed (принято агентом в автономном режиме доработки 0.3.7 как
  план; схема префиксов ADR-CORE/ADR-BE в задании помечена [РЕШЕНИЕ
  ЧЕЛОВЕКА] и подлежит ратификации архитектором вместе с этим ADR)
- Reversibility: в 0.3.7 — полностью обратимо (добавлены только гейт C-34,
  скрипт и документы; код `src/` не двигается). Сам сплит 0.4.0 обратим до
  публикации crate наружу: откат — git-revert переноса, workspace остаётся
  локальной раскладкой монорепо

## Context

Инверсия «Spine без собственной LLM» (`docs/INVERSION.md`) уже дала
cargo-фичи: `harness` (полная сборка по умолчанию) и `core` (слим-сборка
«орган чужого CLI-агента» без TUI и сети). Ядро как зависимость нужно двум
наследникам: продукту Banking Edition (этот репозиторий, ADR-010/ADR-013)
и AI/ML-редакции. Волна B1 ревью 0.3.6 закрыла декомпозицию модулей
(C-33, ≤3000 строк); волна B2 — подготовка физического выделения ядра.

Фактическая граница сегодня чиста. Вывод
`cargo tree --no-default-features --features core -e normal --depth 1`
(2026-09-23, v0.3.6, коммит `cae89dc`):

Полное дерево (191 строка) не содержит ни одного опционального
harness-крейта (`reqwest`, `ratatui`, `crossterm`, `arboard`, `scraper`,
`tokio-util`); `tokio` — неопциональная зависимость ядра (процессы, MCP).
Проверка воспроизводится гейтом: `bash scripts/check_core_deps.sh`
(правило C-34).

Но физически код остаётся одним crate: публичный API ядра и продукта не
различимы (`pub` везде единый), граница удерживается только дисциплиной
`#[cfg(feature = "harness")]`, а независимое версионирование ядра
невозможно. Для open-core модели (ADR-013) и второй редакции нужен crate
с собственной semver-политикой (`docs/SPINE-CORE-API.md`).

## Decision

### 1. Релиз 0.3.7 — только удержание границы (этот коммит)

Код не двигается. Добавляются: правило **C-34 `core_boundary_no_tui_net`**
(`command_succeeds`, critical) поверх `scripts/check_core_deps.sh`;
`docs/SPINE-CORE-API.md` — фиксация стабильной поверхности; этот ADR —
план. С этого момента загрязнение core-профиля harness-крейтом краснит
догфуд и CI до самого сплита.

### 2. План 0.4.0 — workspace из двух crate

- `crates/spine-core` (lib, MIT) — состав по `docs/SPINE-CORE-API.md`:
  модель, контур контроля (`control/`, `gate/`, `review`, `trace`,
  `evidence`, `nfr`, `delta`, `rule_templates`, `cmd_trust`…), контракты
  (`contract_diff/`, `openapi`, `asyncapi`, `archunit`), рубрики
  (`rubric/`, `judge`, `stubs`), протокол MCP (`mcp_server/`, `mcp`,
  `mcp_journal`), handoff и инфраструктура (`error`, `config`, `hash`,
  `proc`, `secrets`, `tool`, `tools`, `llm`-трейт + `harness_cli`…).
- `crates/arch-be` (bin + product lib) — TUI, агентный цикл, сетевые
  LLM-провайдеры, `connect`, `bench`, `cron`, `distill`, `eval`, `harness`,
  `ralph`, `subagent`, `worktree`, `web`, `net`, точка входа и проводка
  CLI. Банковская зона `banking/` остаётся продуктовой надстройкой
  (ADR-013) и в публикацию ядра не входит.
- Корневой манифест становится виртуальным `[workspace]`; фичи
  `harness`/`core` уходят — гейтинг заменяется самой границей crate.

### 3. Порядок работ в 0.4.0

1. **Манифест workspace**: корневой `Cargo.toml` → `[workspace] members =
   ["crates/*"]`, общий `Cargo.lock`, `workspace.package`/`workspace.lints`
   (MSRV 1.85, `unsafe_code = forbid`, политика pedantic — наследуются).
2. **Вынос lib**: `git mv` core-модулей в `crates/spine-core/src` чистым
   перемещением; импорты `crate::` → `spine_core::` механической заменой;
   продуктовый crate объявляет зависимость `spine_core = { path = ... }`.
3. **Перенос путей**: тесты переезжают вместе с модулями; интеграционные
   `tests/` и `benches/` распределяются по владельцам кода; контрольная
   сумма тестов до/после обязана совпасть (прецедент B1: 1579 default /
   1235 core — суммы фиксировались на каждом коммите разбиения).
4. **CI и релиз**: джобы clippy/test прогоняют workspace (`--workspace`),
  dogfood-джоба сохраняется на корневом `CONSTRAINTS.yaml`; релизные
  ассеты собираются из `crates/arch-be`; публикация ядра наружу — отдельным
  решением после стабилизации 0.4.x.
5. **Документы**: `AGENTS.md` (карта модулей), README, `docs/INVERSION.md`
  (шаг 4 закрыт), этот ADR → Accepted.

### 4. Риски и их гашение

- **Feature-перепроводка**: `#[cfg(feature = "harness")]` внутри core-модулей
  (кусочки `llm.rs`, `tools.rs`, `cli/`) при сплите теряют смысл. Гасится
  фактом: граница уже чиста (C-34 держит её гейтом с 0.3.7), гейтинг
  заменяется перемещением файла целиком, а не перекройкой условной
  компиляции.
- **Тесты**: дробление `tests/` по двум crate — источник потерянных
  прогонов. Гашение: контрольные суммы `cargo test` (default и core)
  сверяются на каждом шаге переноса, CI краснит при расхождении.
- **Benches**: `benches/harness_benches` (criterion) привязан к lib;
  переносится в crate-владельца замеряемого кода, прогон — из workspace.
- **SDK и потребители CLI**: тонкие клиенты (ADR-028) ходят поверх headless
  CLI; контракт `arch-be/gate-verdict/v1` и exit-коды 0/1/3 (ADR-040) не
  меняются — сплит для SDK незаметен, регресс-гейт SDK в CI подтверждает.
- **Deploy-kit / релизная упаковка**: пути сборки бинаря меняются
  (`target/release/arch-be` собирается из workspace); обновляются
  `scripts/make_offline_bundle.sh` и релизные заметки, проверка — сборка
  ассетов на RC 0.4.0.

### 5. Схема префиксов ADR — ПРЕДЛОЖЕНИЕ (ратификация архитектором)

После сплита решения разводятся по владельцам: **ADR-CORE-NNN** — решения
ядра (контур контроля, протоколы, машинные контракты), **ADR-BE-NNN** —
решения продукта (TUI, провайдеры, banking-профиль). Существующие
ADR-001…054 остаются общей предысторией монорепо и **не перенумеровываются**
(перенумерация ломает ссылки из модели, дельт и отчётов). Реестр ADR-036
агрегирует оба префикса без изменения механики — по каталогам
`crates/*/docs/adr`. Пункт помечен [РЕШЕНИЕ ЧЕЛОВЕКА] в задании: до
ратификации новые ADR продолжают общую нумерацию.

## Alternatives

**(а) Остаться на feature-границе без сплита.** Ноль работы, граница уже
под гейтом C-34. Отклонено: `pub` единого crate не различает «API ядра» и
«внутренности продукта», независимое semver-версионирование ядра невозможно,
а вторая редакция (AI/ML) вынуждена тащить форк вместо зависимости.

**(б) Сплит в 0.3.7 сразу.** Отклонено рамкой задания: волна B2 —
«подготовка, без поломки сборки», а схема префиксов ADR не ратифицирована.
Сплит без ратифицированной нумерации решений создал бы долг документации
в момент максимального движения кода.

**(в) Два репозитория вместо cargo workspace.** Чистое разделение, но
теряются атомарные коммиты «ядро + продукт» и единый CI; синхронизация
версий через опубликованный crate замедляет итерации 0.4.x. Отложено:
вынос репозитория ядра — отдельное решение после стабилизации workspace,
когда semver-политика ядра докажет себя на практике.

## Consequences

**Положительные.** (1) Граница ядра перестаёт быть дисциплиной и становится
механикой: сначала гейтом C-34 (0.3.7), затем границей crate (0.4.0).
(2) Ядро получает собственную semver-политику и документированную
поверхность — основу open-core поставки (ADR-013) и повторного использования
второй редакцией. (3) Потребители машинных контрактов (SDK, CI) не
затрагиваются: `gate-verdict/v1` и exit-коды неизменны.

**Отрицательные.** (1) Перенос путей — массовый, хоть и механический дифф;
конфликты с параллельными ветками на время сплита. (2) Два crate = две
точки версионирования и changelog-дискауса. (3) Схема префиксов ADR до
ратификации — открытый вопрос; задержка сплита дорожает с ростом
расхождения редакций.

**Как удержаны отрицательные.** Сплит назначен отдельным релизом 0.4.0 без
других волн; контрольные суммы тестов и догфуд C-33/C-34 — сторожа
переноса; префиксная схема зафиксирована здесь как предложение с явным
владельцем решения (архитектор), а не оставлена подразумеваемой.
