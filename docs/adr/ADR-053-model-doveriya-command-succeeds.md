# ADR-053. Модель доверия `command_succeeds`: no-exec, allow-файл по хэшу, находка `command_untrusted`

- Date: 2026-09-22
- Status: Proposed (принято агентом в автономном режиме доработки 0.3.7 —
  в задании пункт A3 был помечен [РЕШЕНИЕ ЧЕЛОВЕКА], и оркестратор выбрал
  вариант (в); подлежит ратификации архитектором)
- Reversibility: полностью обратимо — без `--no-exec`, `ARCH_NO_EXEC` и
  `~/.arch-harness/trusted.json` поведение побитово прежнее; откат —
  удалить запись из trusted.json и/или снять флаги, миграции данных нет

## Context

Правило `command_succeeds` исполняет `bash -c <command>` из
`CONSTRAINTS.yaml` проверяемого репозитория (`src/control.rs` →
`src/proc.rs`). Для своего репозитория это нормально; для чужого — опасно:

- `arch-be gate` / `control check` на PR из форка в CI исполняет команды
  автора форка с правами раннера;
- MCP-сервер (`arch-be mcp serve`) обслуживает агента, который мог
  склонировать незнакомый репозиторий и гонять по нему контур — команды
  реестра исполняются без ведома оператора сервера;
- `control check` по кейсу коллеги — то же исполнение чужого кода.

Это та же дыра, что `direnv` без `direnv allow`: исполнение начинается без
какого-либо решения о доверии. Аудит путей к исполнению —
`docs/experiments/command-trust.md` (19 входов, 4 смежных исполнителя вне
контура). Требования к решению: обратная совместимость CLI на своём
репозитории (дефолт — исполнять), MCP по умолчанию безопасен, тестируемость
без мутаций окружения (паттерн A2 — инжекция снимка), аддитивность схемы
`gate-verdict/v1` и неизменность exit-кодов 0/1/3.

## Decision

Внедряются **оба механизма сразу** (вариант (в)) с обратно-совместимыми
дефолтами.

### 1. no-exec (флаг + переменная + серверный дефолт)

- CLI-команды, транзитивно исполняющие правила (`control check`, `gate`,
  `review`), получают флаг `--no-exec`; переменная окружения
  `ARCH_NO_EXEC=1` действует как флаг (явное `0` — выключить; значения
  `1/true/yes/on` и `0/false/no/off`, регистронезависимо).
- При активном no-exec правила `command_succeeds` НЕ исполняются:
  результат — пропуск с причиной `command_untrusted` и подсказкой, как
  разрешить (снять флаг/переменную; для MCP — `ARCH_NO_EXEC=0`).
- **MCP-сервер работает с no-exec=вкл по умолчанию** (все инструменты,
  доходящие до исполнения: `fitness_check`, `architect_review`,
  `verdict_explain`, `trust_report`); отключить — явным `ARCH_NO_EXEC=0`
  в окружении сервера. Дефолт «вкл» вычисляется один раз при старте
  сервера.
- no-exec имеет приоритет над allow-файлом: решение о запрете для ЭТОЙ
  сессии сильнее постоянного разрешения.

### 2. Allow-файл по хэшу (opt-in, TOFU)

- Новая подкоманда `arch-be rules allow` пишет в
  `~/.arch-harness/trusted.json` (права 0600) запись для текущего
  репозитория: SHA-256 канонизированного набора command-строк всех
  `command_succeeds`-правил разрешённого (resolved) реестра.
- **Канонизация**: строки `command:` вербатим (без тримминга и
  нормализации пробелов — менялся любой байт = менялся реестр), сортировка
  байтово-лексикографическая, склейка разделителем `\n`, хэш —
  `hash::sha256_hex` (существующая реализация, новых зависимостей нет).
  Пустой набор команд — валидная запись: добавление первого
  `command_succeeds`-правила после такого доверия тоже даст несовпадение.
- **Семантика проверки**: файл/записи для репозитория нет → доверие как
  сегодня (обратная совместимость: чужие пайплайны не краснеют, пока
  механизм не включён явно). Запись есть и хэш совпадает → исполнение.
  Запись есть и хэш НЕ совпадает → SKIP `command_untrusted`: реестр
  менялся после доверия — переподтвердить `arch-be rules allow`.
- Отсутствие записи для репозитория при существующем файле — тоже «как
  сегодня»: доверие opt-in по репозиторию, а не белый список машины
  (см. Alternatives).

### 3. SKIP-механика и находка `command_untrusted`

- `FitnessReport` расширяется аддитивно: поле `untrusted_skipped`
  (`{rule, severity, reason}`; reason с префиксом `command_untrusted`),
  рядом с `runner_skipped` из A2. Пропуск — не находка: `passed` и
  exit-код `control check` не меняются.
- В гейте пропуск по доверию ЛЮБОГО `command_succeeds`-правила (включая
  warn-severity) переводит составляющую `fitness` в SKIP с деталью,
  перечисляющей правила и причину. Это строже A2 (там warn-пропуски
  вердикт не меняют) сознательно: пропуск по решению о доверии — событие
  политики, а не разрыв окружения; зелёный PASS при неисполненных по
  политике правилах был бы молчаливой ложью. Обязательная составляющая в
  SKIP даёт INCOMPLETE (exit 3) — «зелёный неполон», а не «выпускать».
- Паспорт вердикта (блок 3 «что не проверено») перечисляет
  command_succeeds-правила, пропущенные по no-exec/untrusted, с причиной —
  через SKIP-деталь составляющей, без изменения схемы паспорта.

### 4. Тестируемость без мутаций окружения

Решение «исполнять ли команды» — снимок `ExecPolicy`
(`{no_exec, trust_file}`), строящийся на краях (CLI из флага+env, MCP из
env с дефолтом «вкл») и пробрасываемый в `check_with_options` → `run_rule`
— как снимок `Runner` из A2. Библиотечные дефолты
(`CheckOptions::default()`, `GateOptions::default()`) — детерминированно
legacy (`no_exec: false`, allow-файл не консультируется): вердикт не
зависит от машины (AD-7), тесты не мутируют `std::env`.

## Alternatives

**(а) Только no-exec.** Проще, но не покрывает «реестр поменялся после
того, как я его видел»: CI на своём репозитории исполняет команды всегда,
и тихая подмена `CONSTRAINTS.yaml` в обход ревью остаётся невидимой.
Отклонено: защита от подмены после доверия — отдельная ценность.

**(б) Только allow-файл.** TOFU-защита есть, но первого контакта она не
закрывает: репозиторий без записи исполняется «как сегодня», а MCP-агенту
нужен безопасный дефолт БЕЗ предварительных действий человека. Отклонено:
без no-exec MCP-дефолт остаётся дырой.

**(в) Оба механизма (принято).** no-exec закрывает первый контакт и
сессионный запрет, allow-файл — подмену после доверия; приоритет no-exec
над allow делает сессионный запрет непробиваемым. Цена — два механизма
вместо одного (см. Consequences).

**Белый список вместо TOFU** (файл существует ⇒ репозиторий без записи не
исполняется). Строже, но ломает обратную совместимость при первом же
`rules allow`: все остальные репозитории пользователя начали бы краснеть
(gate INCOMPLETE), хотя механизм включали ради одного. Отклонено: opt-in
обязан быть точечным.

**Конфиг-секция вместо/вместе с флагом.** `[control].no_exec` дало бы
постоянный запрет на машине, но создало бы второй источник истины о
сессионном решении и рассинхрон «конфиг против CLI». Отклонено: запрет —
свойство сессии/сервера, не проекта.

## Consequences

**Положительные.** (1) MCP-дефолт безопасен без каких-либо действий
оператора: чужой репозиторий у агента не исполняется, находка
`command_untrusted` называет это прямо. (2) CI может запретить исполнение
одной переменной окружения, не правя пайплайны. (3) Подмена реестра после
явного доверия блокируется механически, а не замечается случайно.
(4) Паспорт вердикта честно показывает, что именно не проверено.

**Отрицательные.** (1) Два механизма — две семантики, которые надо
объяснять (этот ADR + `docs/experiments/command-trust.md` + тексты
подсказок в находках). (2) MCP-дефолт no-exec делает вердикт
`fitness`-составляющей SKIP/INCOMPLETE на любом репозитории с
command-правилами, пока оператор не задаст `ARCH_NO_EXEC=0`: шум
осознанный — цена безопасного дефолта, и он читается как «не проверено»,
а не как «провал». (3) Allow-файл — TOFU: первый контакт в CLI остаётся
доверенным по умолчанию (закрывается флагом/переменной, не файлом).
(4) Канонизация по вербатиму означает, что косметическая перестановка
пробелов в команде тоже требует переподтверждения — выбрана строгость
перед удобством.

**Как удержаны отрицательные.** Тексты причин в `command_untrusted`
называют, как разрешить исполнение для каждого случая (снять флаг /
`ARCH_NO_EXEC=0` / `rules allow`). Дефолт CLI на своём репозитории не
изменился — ужесточение никого не застаёт врасплох. Смежные исполнители
(verify шаблонов, репетиция отката, archunit, bash-инструмент агента)
зафиксированы в аудите как находящиеся вне контура — граница механизма
честна.
