# ADR-059. Слои после гейта (волна D): теневой гейт, Bitbucket Code Insights, runtime fitness — прототипы за флагами

- Дата: 2026-10-04
- Статус: Accepted (рамка волны D предрешена TASK-0.3.12 §6: «ADR и прототип
  за флагом; в дефолтное поведение не входят»; детали ниже — решение
  архитектора в этой рамке). D3 — отдельно, **[РЕШЕНИЕ ЧЕЛОВЕКА]** по формату.
- Модель-автор: claude-opus

## Context

Эшелонированная защита 0.3.12 закрывает «разработчик → CI → мерж → реестр →
вход в рантайм», но слои **после** гейта в продукте почти отсутствуют
(TASK §0, п.4):

- **Обратная связь CI-площадкой.** `connect ci` умеет GitLab/GitHub/Jenkins;
  Bitbucket Data Center заказчика не поддержан: вердикт не виден в
  merge checks («Required builds», Code Insights) — гейт живёт вне ревью.
- **Эволюция правил вслепую.** Новый пин `extends` реестра правил или правка
  CONSTRAINTS.yaml поднимает порог без измерения: «что может покраснеть»
  пишется вручную в CHANGELOG (несверяемо, быстро дрейфует).
- **Инварианты не доехали до рантайма.** Правила CONSTRAINTS.yaml проверяют
  код, но развёртывание (образы, лимиты, non-root) контролируется другими
  механизмами кластера; моста нет (кроме JVM-моста ArchUnit, ADR-039).
- **NFR измеряются один раз на бумаге.** Бюджеты p99 и SLA из модели
  (nfr budget/availability) не сверяются с фактическими метриками после
  деплоя.

Ограничения: волна D — P2, прототипы за флагами, дефолт не меняется; Core-
граница C-34 (без сетевых/TUI-крейтов в ядре); правило 4 — обратная
совместимость gate-verdict/v1 и exit-кодов 0/1/2/3.

## Decision

Три прототипа за флагами + один пункт, ожидающий решения человека:

### D2 — теневой гейт (канарейка реестра) `arch-be gate --shadow-constraints <файл>`

1. Гейт вычисляет вердикт **дважды**: решающий — по текущему реестру
   (как сегодня), теневой — по файлу `--shadow-constraints` (кандидатная
   версия CONSTRAINTS.yaml с `extends`-пином на будущее).
2. Решает только основной вердикт: exit-код, gate-verdict/v1 и
   обязательные составляющие не меняются (правило 4). Теневой прогон
   добавляет в отчёт отдельный блок **shadow**: какие находки появятся /
   исчезнут / сменят severity (по id правила), сводка «что покраснеет
   при переходе».
3. Теневой файл с ошибкой разбора не красит основной вердикт — находка
   `shadow_constraints_invalid` в shadow-блоке.
4. Флотовой срез: `control report --level corp` агрегирует shadow-дифф по
   проектам (счётчики появляющихся находок) — решение о поднятии пина
   становится измеримым.
5. Цель — заменить ручной раздел CHANGELOG «что может покраснеть»
   измерением до поднятия `extends`.

### D1 — `connect ci --provider bitbucket` (Core)

1. `CiProvider::Bitbucket`: генерация блока Jenkinsfile (маркерный блок,
   как у Jenkins-провайдера) + отчёт `--format bitbucket-insights`
   (JSON-отчёт Code Insights: key, title, result PASS/FAIL, findings как
   аннотации-ссылки на файлы).
2. Публикация — **из CI-скрипта curl'ом** в `/rest/insights/1.0/projects/…`
   и build-status API: сеть живёт в пайплайне заказчика, НЕ в Rust-коде
   (Core-граница C-34 — новых сетевых крейтов нет).
3. Сгенерированный блок документирует merge checks «Required builds» +
   «Code Insights» в Bitbucket DC.

### D4 — runtime fitness для NFR (исследование)

1. Результат пункта — `docs/experiments/runtime-fitness.md`: дизайн,
  честные границы, прототип.
2. Прототип `arch-be nfr verify --metrics <файл>` (за флагом):
   метрики-файл (JSON-фикстура: p99 по операциям, availability, error rate)
   сверяются с бюджетами/SLA из модели (`nfr budget`, `availability`);
   расхождение — находка с виновным hop/звеном.
3. Без сетевых зависимостей в ядре: источники метрик — файлы
   (Prometheus-экспорт — будущая работа, отметка в отчёте).
4. Генерация шаблона канареечного анализа из `QAS-*`/`NFR-*` в
   handoff-пакете — черновик в том же отчёте.

### D3 — экспорт инвариантов в политики кластера — решено владельцем 2026-10-04

**Формат выбран: отдельная секция `deployment:` в CONSTRAINTS.yaml**
(инварианты развёртывания: образы — внутренний реестр и подпись, non-root,
лимиты ресурсов, deny_dependency для образов). Обоснование: честное
разделение семантики — гейт проверяет код, кластер проверяет деплой; секция
`rules:` не трогается вовсе (правило 4 TASK соблюдено без оговорок);
`rules_report`/`control report` могут показывать обе плоскости. `arch-be
policy export kyverno|rego` читает `deployment:` и генерирует политики;
оверрайды/дашборд для deployment-инвариантов — отдельной логикой (минус
осознанно принят). Реализация — следующей волной/дельтой после 0.3.12
(в 0.3.12 пункт закрыт ADR-решением, как допускает §7).

## Alternatives Considered

- **Сразу включить в дефолт** (полный shadow-режим в вердикте, публикация
  Insights из Rust) — отвергнуто: P2-прототипы обязаны жить за флагами
  (TASK §6), сеть в ядре запрещена C-34.
- **«Что покраснеть» продолжать писать руками** — статус-кво; несверяемо,
  дрейфует, не масштабируется на флот — ради этого пункта и существует D2.
- **Runtime-метрики тянуть по сети из ядра** (Prometheus-клиент в Rust) —
  нарушает Core-границу; метрики-файл + CI-шаг экспорта закрывают сценарий
  без крейтов.
- **D3 делать сейчас с выбранным за заказчика форматом** — нельзя: формат
  CONSTRAINTS.yaml — совместимость экосистемы, решение человека (TASK §6).

## Consequences

### Positive

- Гейт доезжает до merge checks Bitbucket DC заказчика — вердикт виден там,
  где принимается решение о мерже.
- Эволюция реестра правил становится измеримой: shadow-дифф до поднятия
  пина, флотовой срез в control report.
- NFR получают замкнутый цикл: цель в модели → проверка на гейте →
  сверка с фактом после деплоя (первый шаг, файловый).

### Negative

- Три новых пути кода за флагами — площадь тестирования растёт (митигация:
  теневой прогон переиспользует существующий конвейер вердикта, Insights —
  генератор по образцу существующих провайдеров).
- Shadow-дифф может ложно успокаивать: он меряет правила, но не семантику
  новой версии детекторов — граница фиксируется в отчёте.
- D1 привязан к REST API Bitbucket DC [ТРЕБУЕТ ПРОВЕРКИ по документации
  Atlassian при реализации: точные пути /rest/insights/1.0 и build-status
  API версии].
- D3 остаётся открытым до решения человека — волна D закрывается не вся.

## Reversibility

**Reversible.** Всё за флагами/генераторами: `--shadow-constraints` без
флага не существует; `--provider bitbucket` не меняет других провайдеров;
`nfr verify --metrics` — отдельная подкоманда; дефолтное поведение
байт-в-байт прежнее. Откат — git revert, миграций нет.
