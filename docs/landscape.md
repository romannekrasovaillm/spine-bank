# Ландшафт систем и сверка с CMDB

Документ описывает два контура работы с корпоративным ландшафтом:

1. **Агрегация ландшафта** (`arch-be landscape` — сводка моделей проектов,
   ADR-036/ADR-037) — read-only сведение `model/` по корню и подкаталогам.
2. **Сверка с выгрузкой CMDB** (`arch-be landscape diff`, ADR-077, волна
   LANDSCAPE, бенчмарк AB-02) — сопоставление ландшафта (модель ⊕ граф кода)
   с внешним инвентарём и три класса расхождений.

## 1. Агрегация ландшафта

`build_landscape(root)` (ADR-037) читает `model/` самого корня и
непосредственных подкаталогов (минус `SKIP_DIRS`), дедуплицирует системы по
нормализованному `canonical_name` (trim, lowercase, `-`→пробел, схлопывание
пробелов) и собирает находки. ID сущностей локальны проекту — глобальных ID
нет; коллизии имён снимаются картой алиасов (`--aliases`, см. `load_aliases`).

## 2. Сверка с CMDB (`landscape diff`)

```
arch-be landscape diff --cmdb <файл> [--root <dir>] [--aliases <файл>]
                       [--repo <dir>] [--rev <rev>] [--format md|json]
                       [--model-out <dir>]
```

- `--root` — корень ландшафта (по умолчанию `.`).
- `--cmdb` — файл выгрузки CMDB (обязателен).
- `--aliases` — карта алиасов имён (как у агрегации).
- `--repo` — корень репозитория кода; включает в сверку граф «как построено»
  (`arch_diff::as_built_with`, компоненты `NodeKind::Component`). Без него
  сверка идёт только по модели.
- `--rev` — ревизия для графа кода (по умолчанию `HEAD`).
- `--format` — `md` (по умолчанию) или `json` (схема
  `arch-be/landscape-diff/v1`).
- `--model-out` — каталог неразрушающего черновика модели из записей CMDB.

### 2.1. Формат выгрузки CMDB

Минимальный YAML (выбран вместо CSV ради единообразия с моделью и
`serde_yaml_ng`, который разбирает и JSON — тот же файл можно подать в
JSON-форме). Два допустимых корня: обёртка `systems:` либо «голый» список.

```yaml
systems:
  - id: CMDB-001          # опционально; если пусто — вместо ID берётся имя
    name: customers-service # обязателен (иначе запись отвергается)
    owner: CRM            # опционально; свободный текст
    status: active        # active | deprecated | retired (по умолчанию active)
    replaces: CMDB-000    # опционально; информативное поле
```

Голый список эквивалентен обёртке:

```yaml
- {name: customers-service, owner: CRM, status: active}
```

Правила разбора (`load_cmdb`):

- пустой файл/пустой список — ошибка;
- запись без `name` — ошибка («запись CMDB без имени»);
- `status` нормализуется; `retired`/`decommissioned`/`eol` считаются выведенными
  из эксплуатации (`CmdbSystem::retired`);
- записи сортируются по `(canonical_name(name), id)` — детерминизм вывода.

### 2.2. Классы расхождений

Сверка сопоставляет три источника — **модель** (SYS/INT с владельцем из тела),
**граф кода** (`--repo`) и **CMDB** — и выдаёт три класса:

| Класс | Severity | Условие | Смысл |
|-------|----------|---------|-------|
| `cmdb-missing` | **error** | система есть в модели/коде, но её нет в CMDB | объект не заведён в инвентарь |
| `cmdb-orphan` | warn | запись CMDB есть, но системы нет ни в модели, ни в коде | «висит» в CMDB без реализации |
| `owner-conflict` | **error** | владелец CMDB ≠ владелец модели | расхождение владения данными |

**Владелец в модели:** у сущности нет первоклассного поля `owner`; владелец
берётся из тела `SYS`/`INT` по строке `Владелец: «…»` (`owner_from_body`).
Сравнение — по `norm_owner` (схлопывание пробелов, lowercase), так что
различия регистра и лишних пробелов конфликтом не считаются.

**`retired` гасит шум:** запись CMDB со статусом `retired`, которой нет в
модели/коде, не попадает в находки — отсутствие реализации для снятой с
эксплуатации системы ожидаемо (вердикт «подтверждена»).

### 2.3. Вердикт по каждой записи CMDB (AB-02, задача 5)

Для каждой записи CMDB формируется вердикт:

- **`подтверждена`** — сопоставлена с моделью/кодом, владелец согласован
  (либо запись `retired`);
- **`ошибочна`** — запись висит без модели/кода либо владелец конфликтует;
- **`не проверяема`** — в ландшафте нет ни одного источника (ни модели, ни
  графа кода): сверять не с чем. Ложных orphan при этом не выдаётся —
  срабатывает `has_sources`, чтобы не штрафовать за отсутствие данных.

### 2.4. Черновик модели `--model-out`

Как и `recover --model-out` (ADR-069), `landscape diff --model-out DIR` пишет
`SYS-NNN.md` со `status: inferred` и `source: cmdb@<файл>` для записей CMDB.
Прогон **неразрушающий**: сущность со `status`, отличным от `inferred`
(правка архитектора), не перезаписывается — такие записи попадают в список
`пропущено (уже в модели)`. Владелец из CMDB переносится строкой
`Владелец: «…»`.

## 3. JSON-контракт `arch-be/landscape-diff/v1`

```json
{
  "schema": "arch-be/landscape-diff/v1",
  "arch_be": "0.4.1",
  "root": "/path",
  "cmdb": "/path/cmdb.yaml",
  "counts": {"design_systems": 8, "code_systems": 8, "cmdb_records": 8,
             "errors": 0, "warnings": 0, "verdicts": 8},
  "findings": [{"class": "...", "severity": "...", "subject": "...",
                "message": "...", "evidence": "..."}],
  "verdicts": [{"id": "...", "name": "...", "verdict": "...", "reason": "..."}],
  "model_out": null,
  "passed": true
}
```

`passed = true` при нуле находок уровня error (warn не роняет сверку). Вывод
детерминирован: находки сортируются по `(severity, class, subject)`, записи
CMDB — по `(canonical_name, id)`.

## 4. Живой прогон (petclinic)

Клон `spring-petclinic-microservices` (8 Spring-сервисов), выгрузка CMDB на
8 систем. Последовательность:

1. Черновик модели: `landscape diff --root /tmp/pc-ls --cmdb cmdb.yaml
   --model-out model` → 8 orphan [warn], записаны `SYS-001…008` со `status:
   inferred` и владельцами.
2. Чистая сверка: `… --repo <petclinic>` → `passed: true`, ошибок 0,
   предупреждений 0, все 8 записей «подтверждена».
3. Убрать сервис из CMDB → `cmdb-missing` [error] на этот сервис.
4. Сменить владельца в модели → `owner-conflict` [error] с обоими значениями.
