# Архитектурный дифф каждого PR (`arch-be arch-diff`)

Один экран на каждый pull request: **что изменилось в системе** — новые связи
между компонентами, внешние системы и хранилища, контракты, сдвиги NFR,
задетые инварианты — с основаниями `файл:строка`, без LLM (AD-2). Пустой
дифф означает «архитектуре ревью не нужно». Решение принадлежит волне K
(TASK-v2 §9), контракты — ADR-063.

```
arch-be arch-diff --repo . --base origin/main [--format md|mermaid|json|sarif]
```

Модель (`model/`) не обязательна: без неё граф строится по манифестам сборки
(компоненты с пометкой `inferred`), просто без колонки «в модели» и без
инвариантов. Это входная точка продукта в любом репозитории.

## Что показывает дифф (три измерения)

1. **Реальность PR** — добавленные и удалённые узлы и рёбра графа «как
   построено» между `--base` и `--head` (по умолчанию `HEAD`). Переименование
   и перенос файлов внутри одного компонента изменением архитектуры не
   считаются.
2. **Расхождение с моделью** — каждое ребро помечается `в модели / нет в
   модели` (импорт — по `depends_on` CMP, обращение — по хосту в INT/SYS,
   контракт — по полю `contract` INT); объявленные рёбра без кода — списком
   `declared-unused`.
3. **Смысл** — задетые инварианты AD с правилами-охранниками и классом зубов
   (из `.arch-handoff/teeth.json`, волна B; без файла — честное «зубы не
   измерены»), затронутые ADR, классификация изменений контрактов
   (ломающее/аддитивное — `contract_diff`), сдвиг NFR «было → стало», маршрут
   значимости с источником каждого триггера (`declared`/`diff`).

## Пример (демо-сценарий)

Ветка `agent/direct-ledger-write`: агент из компонента «Приём реестров»
(CMP-001) пишет напрямую в хранилище ядра проводок (CMP-004), минуя
Оркестратор, и добавляет строку подключения в конфиг:

```
$ arch-be arch-diff --repo . --base main
Архитектурный дифф <base>..<head> · маршрут critical (…)

Новые связи
  + CMP-001 → CMP-004 (import) — в модели: НЕТ; задет инвариант AD-2
    основание: skeleton/intake/writer.py:2
  + CMP-001 → store:postgres://ledger-db:5432 (connect) — в модели: НЕТ
    основание: skeleton/intake/config.yaml:1

Новые узлы
  + store:postgres://ledger-db:5432 · … [datastore]

Контракты
  без изменений
NFR
  без изменений

Задетые инварианты
  ! AD-2 «Проводки только через Оркестратор»
    правило C-007 (no-direct-ledger-write, зубы не измерены)

Затронутые ADR: ADR-003

Предложения модели (принять: arch-be arch-diff accept <n…> --base <база>; …):
  1. model/CMP-001-intake.md: depends_on += CMP-004   ⚠ противоречит AD-2
  2. model/SYS-001-ledger-db.md: новая сущность SYS-001 …
```

(форма, не точный текст; на чистом рефакторинге внутри компонента вывод —
одна строка «Архитектурных изменений нет»)

## Принятие и отклонение предложений (K5, ADR-064)

Модель перестаёт отставать, потому что её поддержка — одно решение на
изменение, а не отдельная работа:

```
arch-be arch-diff accept 1 --base main          # предложение №1 → дельта
arch-be arch-diff reject 2 --base main --reason "шина legacy осознанно вне модели"
```

- **`accept <n…>`** оформляет принятые предложения дельтой
  `changes/<name>/DELTA.md` (имя — `--name` или `arch-diff-<head8>`; занято —
  суффикс `-2`…). Сама команда файлы `model/` **не правит**: модель меняется
  только через дельту — последующая правка покрыта ею для `delta guard`
  (пути файлов дельта несёт дословно). Предложение с ⚠ (противоречит
  инварианту AD) принимается, но конфликт фиксируется в дельте явно
  (секция «Конфликты с инвариантами»). При `[delta] sources = ["openspec"]`
  дельта НЕ пишется — команда подсказывает оформить change OpenSpec
  (правило 9, ADR-062), и решение не журналируется.
- **`reject <n> --reason "…"`** пишет отказ в журнал; причина обязательна.
  Повторно это ребро не предлагается, пока не изменились его основания
  (`файл:строка`). Отклонённое ребро, оставшееся в коде, — будущая находка
  гейта (K6).
- **Номера стабильны в сеансе**: решённые предложения исчезают из списка,
  номера остальных сохраняются — `accept 1` и `reject 2` по одному выводу
  работают в любом порядке. После влития дельты (ребро ушло в модель)
  нумерация пересчитывается — ссылайтесь на свежий вывод.

### Журнал решений

Решения (и принятия, и отказы) пишутся в
`.arch-handoff/arch-diff-decisions.json` — схема
`arch-be/arch-diff-decisions/v1`:

```json
{
  "schema": "arch-be/arch-diff-decisions/v1",
  "entries": [
    {
      "edge_id": "import:CMP-001->CMP-004",
      "decision": "accept",
      "reason": "",
      "grounds_hash": "…sha256 оснований файл:строка…",
      "decided_at": "2026-10-08T12:00:00+03:00",
      "source": "human",
      "delta": "arch-diff-65333294"
    }
  ]
}
```

Журнал append-only, действует последняя запись по ребру (last-wins);
предложение подавляется, пока `grounds_hash` записи совпадает с текущими
основаниями ребра — основания изменились, и ребро предлагается снова.
`arch-diff` читает журнал при каждом прогоне; битый журнал — громкая ошибка,
а не молчаливый сброс решений. Коммитить журнал или нет — решение команды
(как `teeth.json`).

Поле `source` — честный источник решения: переменная окружения
`ARCH_BE_ACTOR=human|agent`; без неё — `unknown` (угадывания нет; связывание
с подписью A3 и принуждение — ADR-060, не эта волна).

## Форматы вывода

| `--format` | Назначение |
|---|---|
| `md` (дефолт) | Сводка одного экрана; детали — сворачиваемые `<details>`-блоки. Для комментария MR/PR. |
| `mermaid` | `flowchart LR` «до/после»: добавленные рёбра — `==>`, удалённые и рёбра вне модели — `-.->` с меткой, новые узлы — классом `added`. |
| `json` | Машинный контракт `arch-be/arch-diff/v1` (поле `schema`); детерминирован: повторный прогон на тех же коммитах — байт-в-байт тот же JSON. |
| `sarif` | SARIF 2.1.0: рёбра вне модели, задетые инварианты и ломающие контракты — warnings с адресами `файл:строка` (площадки показывают их в интерфейсе PR). |

## Exit-коды и `--fail-on`

Команда информационная: **всегда `exit 0`**, кроме явных условий
`--fail-on` (тогда `exit 1`):

```
arch-be arch-diff --base origin/main \
  --fail-on undeclared-edge,breaking-contract,invariant-touched
```

| Условие | Срабатывает, когда |
|---|---|
| `undeclared-edge` | есть добавленное ребро, отсутствующее в модели |
| `breaking-contract` | контракт изменён ломающе или удалён |
| `invariant-touched` | изменение задевает инвариант AD |

Заявленные триггеры маршрута — `--trigger имя=true` (повторяемый; словарь —
как у `arch-be control score`: незнакомое имя — ошибка, а не завышение
маршрута).

## Доставка в PR: комментарий, который обновляется (K4)

`arch-be connect ci --provider gitlab|github|jenkins` рядом с джобой гейта
рендерит джобу `arch-diff`: она запускает `arch-be arch-diff --base
<целевая ветка> --format md` и публикует результат **одним комментарием**
MR/PR, обновляя его на каждом пуше:

- тело комментария начинается маркером `<!-- spine-arch-diff -->`;
- пайплайн ищет существующий комментарий по маркеру и делает **edit**
  (GitLab: `PUT …/notes/<id>`; GitHub: `PATCH …/issues/comments/<id>`),
  а не добавляет новый; маркера нет — комментарий создаётся;
- публикация — средствами пайплайна (`curl` + `jq` для GitLab/Jenkins,
  `gh api` для GitHub). **Бинарь `arch-be` сети не касается** (граница
  C-34): он только пишет `arch-diff.md`.

Настройка по площадкам:

| Площадка | Что рендерится | Токен для комментария |
|---|---|---|
| GitLab | джоба `spine-arch-diff` в `.gitlab-ci.yml` (на `merge_request_event`) | masked CI-переменная `GITLAB_TOKEN` (project access token, scope `api`; у `CI_JOB_TOKEN` прав на комментарии нет) |
| GitHub | job `arch-diff` в `.github/workflows/spine-gate.yml` (на `pull_request`) | встроенный `GITHUB_TOKEN` (в workflow объявлено `permissions: pull-requests: write`) |
| Jenkins | этап `Spine arch-diff` в `Jenkinsfile` (только PR-сборки multibranch) | credentialsId `arch-diff-mr-token` + переменные `ARCH_DIFF_PLATFORM` (`gitlab`\|`github`), `ARCH_DIFF_LIST_URL`, `ARCH_DIFF_ITEM_URL` (формы URL — в комментарии этапа, помечены `[ТРЕБУЕТ ПРОВЕРКИ]`) |
| Bitbucket DC | блок `connect ci --provider bitbucket` (ADR-059) | комментарий не нужен: вердикт и дифф доезжают через Code Insights (`--format bitbucket-insights`) — самообновляющийся отчёт |

Во всех трёх джобах дифф остаётся **информационным** (без `--fail-on`):
краснота MR/PR — зона ответственности джобы гейта (`spine-gate`). Хотите
красный дифф — добавьте `--fail-on …` в строку `arch-be arch-diff` шаблона
(блок перегенерируется `connect ci`, правки — вне маркеров либо после
перегенерации).

Прогон вне MR/PR (push ветки) комментарий не публикует: джобы GitLab/GitHub
ограничены событием MR/PR, этап Jenkins — `changeRequest()`; `arch-diff.md`
при этом остаётся артефактом сборки.

## Почему это честно

- Детерминизм (правило 10): повторный прогон на тех же коммитах даёт тот же
  результат; граф читается из git-снимков, рабочее дерево не меняется.
- Ложное «удалено/добавлено» от переименований исключено конструкцией
  (граф строится на уровне компонентов; детектор триггеров — `git diff` с
  rename detection).
- Разрешение импортов эвристическое (динамические импорты, экзотика Go —
  документированные пропуски): ложное отсутствие ребра возможно, ложное
  ребро — нет.
