# Проверка поставки Spine BE (для ИБ/ДИТ заказчика)

Как проверить, что поставляемое — это ровно то, что в репозитории, и что
внутри периметра не исполняется ничего лишнего. Контекст: модель угроз
(`docs/threat-model.md`, T5/T6), ADR-031, GEN-18 (provenance) — здесь тот
же стандарт применён к самому продукту, а не только к проектам заказчика.

## Что поставляется и чем это проверяется

| Артефакт | Чем проверяется |
|---|---|
| Исходники (репозиторий) | git-история, подписи коммитов (если включены), ADR-дисциплина |
| Бинарь `arch-be` | `SHA256SUMS.release` из CI-джобы supply-chain + сборка из исходников (ниже); для релизов по тегам `v*` — сводный `SHA256SUMS` на 8 бинарей (linux-x86_64/aarch64, macos-arm64, windows-x86_64 × core/full, workflow release.yml) |
| Зависимости Rust | `Cargo.lock` + `cargo audit` (CI-джоба audit, ежедневная база RUSTSEC) |
| Состав поставки (SBOM) | `sbom-core.cyclonedx.json` / `sbom-full.cyclonedx.json` (CycloneDX 1.6) — приложены к GitHub Release той же сборкой, что и бинари (B2); хэши SBOM — в том же `SHA256SUMS` |
| Вендоренный JS (`vendor/archify/`) | `SHA256SUMS` в каталоге вендора; целостность гейтится правилом BE-22 (`control check`) |
| Toolchain | `rust-toolchain.toml` (pinned stable), MSRV 1.85 (CI-джоба msrv) |

## Релиз выходит только с зелёного коммита (B1)

Первая джоба `.github/workflows/release.yml` (`CI зелёный для коммита тега`)
запрашивает у GitHub API check-runs коммита `github.sha` и требует, чтобы все
**обязательные** джобы `ci.yml` были завершены со статусом `success`. Сборка
бинарей (`build`) объявлена `needs: ci-green` — она не начинается, пока
проверка не пройдёт.

Поведение fail-closed (релиз **не** собирается), если:

- check-runs для коммита недоступны (ошибка API) — нет данных о статусе;
- незавершённые (`queued`/`in_progress`) джобы не дошли до конца за
  отведённое ожидание (30 минут);
- хотя бы одна обязательная джоба завершилась не `success`.

Список обязательных джобов задан в workflow явно и совпадает с `name:`
джобов `ci.yml` (fmt, clippy, test, core-build, hermetic, msrv, audit, deny,
supply-chain, dogfood, eval-suite). Ночные проверки (`nightly.yml`) релиз не
блокируют — они не входят в список.

**Приёмка (эмпирическая, только в CI):** тег `v*` на коммите с красной
обязательной джобой не создаёт GitHub Release. Локально это непроверяемо —
проверяются структура workflow и согласованность имён джобов.

## Защита тегов `v*` и подпись тега

Релиз триггерится тегом `v*`, поэтому первый рубеж — **кто может создавать
такие теги**. Настраивается средствами GitHub (Settings → Rules / Tag
protection rules): правило на `v*` ограничивает создание и удаление тегов
ролями владельца/администратора и (опционально) запрещает их перемещение.
Владелец репозитория — единственная учётная запись, чьи действия с тегами
ожидаемы.

Подпись тега (`git tag -s`) и проверка зелёного CI **не заменяют друг
друга**:

- подпись тега доказывает, *кем* создан тег, но не то, что помеченный коммит
  прошёл тесты и сенсоры; подписанный тег на красном коммите остаётся
  подписанным;
- подпись не обязательна для клиента: `git` примет и неподписанный тег, а
  проверка подписи требует настроенного `gpg.ssh`/trusted-keys у каждого, кто
  читает репозиторий;
- компрометация ключа подписи у владельца обесценивает подпись, тогда как
  проверка CI привязана к фактическому результату прогона на коммите.

Поэтому слои складываются: защита тегов (кто может тегировать) + проверка
зелёного CI (что было проверено) + provenance/подпись артефактов (из чего
собрано) — см. ниже.

## Сборка из исходников (рекомендуемый путь для периметра)

```bash
git clone <внутренний-зеркало-репо> && cd spine-bank
git checkout <тег/коммит поставки>
cargo build --release --locked          # pinned toolchain из rust-toolchain.toml
sha256sum target/release/arch-be        # сверка с SHA256SUMS поставки
```

Сборка воспроизводима на уровне исходников и lock-файла: одинаковые
входные (коммит, `Cargo.lock`, toolchain) дают функционально одинаковый
бинарь; побайтовая идентичность с CI-сборкой не гарантируется (пути,
временные метки), поэтому базовая доверенная процедура — сверка состава
(SBOM) и самостоятельная сборка, а не только хэш чужого бинаря.

## Работа со SBOM

`sbom-core.cyclonedx.json` / `sbom-full.cyclonedx.json` — перечень всех
crate-зависимостей с версиями и лицензиями. SBOM собирается в той же
матричной сборке, что и публикуемый бинарь (B2): тот же коммит и
`Cargo.lock`, а не отдельная джоба CI. `cargo-sbom` строит SBOM из
`Cargo.lock` (workspace-wide), поэтому граф зависимостей не зависит от ОС —
достаточно одной платформы на редакцию. `cargo-sbom` не различает фичи
сборки, поэтому `sbom-core` и `sbom-full` описывают один и тот же
lock-файл и могут совпадать по составу: раздельные артефакты привязывают
SBOM к той же матричной сборке, что и соответствующий бинарь, а не
утверждают разный граф зависимостей.

Типовые проверки ДИТ:

- соответствие внутреннему списку разрешённых лицензий (проверка:
  `jq -r '.components[].licenses[].expression' sbom-full.cyclonedx.json | sort -u`;
  снимок 2026-09-04: 298 компонентов, лицензии пермиссивные —
  MIT/Apache-2.0/BSD/ISC/Zlib/BSL-1.0/Unicode-3.0/Unlicense, плюс
  MPL-2.0 и CDLA-Permissive-2.0 (weak copyleft уровня файла — при
  внутреннем запрете copyleft смотреть компоненты точечно));
- сверка состава с предыдущей поставкой (diff по `components[]."bom-ref"`);
- сопоставление с внутренней базой уязвимостей (дополнение к RUSTSEC из
  `cargo audit`).

## Внешние рантаймы в контуре

- **node** — нужен только для Archify-контура диаграмм
  (`[archify].enabled = false` отключает целиком; doctor показывает
  версию node и путь CLI). Вендоренный код пиннут `vendor/archify/SHA256SUMS`
  (гейт BE-22); node сам — внешний бинарь, поставляется ИТ-контуром
  заказчика (рекомендуемая версия зафиксирована в выводе `arch-be doctor`).
- **MCP-серверы** — локальные stdio-процессы из конфигурации пользователя;
  публичные регистры (npx/uvx/pipx) запрещены продуктовыми пресетами
  (BE-08).

## Что заведомо НЕ закрыто (честный реестр)

- Подпись релизных артефактов (cosign/GPG) — следующий шаг; сейчас доверие
  = CI на внутреннем зеркале + хэши + сборка из исходников.
- Побайтовая воспроизводимость сборки (reproducible builds) — не
  настроена; компенсируется самостоятельной сборкой из исходников.
- SLSA-provenance CI — не формируется; артефакты supply-chain
  (SBOM + хэши) — первый уровень, см. реестр GAP в `docs/threat-model.md` §5.
- **Подпись тегов и branch/tag protection** — настраивается средствами
  GitHub владельцем репозитория; проверка зелёного CI в `release.yml`
  дополняет её, но не заменяет (см. раздел о защите тегов).
