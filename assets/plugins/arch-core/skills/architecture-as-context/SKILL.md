# Архитектура как контекст

Для флота агентов архитектура существует ровно в той мере, в какой она попала в их контекст или в проверки. Этот скилл переносит знание архитектора из документов и голов в **слои контекста**, которые агенты гарантированно читают, — и делает это экономно, потому что контекст ограничен, а лишние правила размывают важные.

Скилл не пишет за SDD-фреймворк proposal, spec или план. Он готовит то, что фреймворк должен получить **на вход** в каждой задаче.

## Модель слоёв

| Слой | Где живёт | Что туда класть | Кто владеет |
|---|---|---|---|
| **L0 Корпоративный** | корпоративный скилл или плагин (маркетплейс) | 5–15 инвариантов предприятия, запреты, правила эскалации | EA-практика |
| **L1 Доменный / платформенный** | скиллы домена, golden paths | эталонные архитектуры, разрешённые технологии, интеграционные паттерны, словарь домена | domain/solution-архитектор |
| **L2 Репозиторий** | `CLAUDE.md` / `AGENTS.md`, около одной страницы | назначение системы, границы модулей, индекс обязательных решений, команды проверки | команда + архитектор |
| **L3 Каталог / модуль** | вложенные `CLAUDE.md`, правила каталога | локальные правила модуля, контракты, запреты импорта | команда |
| **L4 Изменение** | конфиг и артефакты SDD-фреймворка | ограничения и NFR конкретного изменения | автор изменения, архитектор по уровню риска |

Принцип: **знание кладётся в самый нижний слой, где оно ещё полностью верно.** Правило одного модуля в корпоративном скилле — шум для всех остальных; корпоративный инвариант в одном CLAUDE.md — дыра во всех остальных репозиториях.

Плейбук Anthropic AI-Native SDLC рекомендует держать CLAUDE.md примерно в одну страницу, а детальные правила выносить в правила каталогов и скиллы. Эта модель слоёв — развёрнутая версия того же принципа.

## Процесс

### 1. Инвентаризация источников
Собери, что есть: стандарты, принципы, эталонные архитектуры, ADR, схемы интеграций, существующие CLAUDE.md/AGENTS.md, конфиги SDD-фреймворков в репозитории (`openspec/`, каталоги BMAD, планы superpowers, `intent/`). Если источники — длинные документы, не копируй их: извлекай утверждения.

### 2. Извлечение и классификация утверждений
Разбей знание на атомарные утверждения и присвой тип. Тип определяет форму и слой:

| Тип | Признак | Форма | Обязательно |
|---|---|---|---|
| **Инвариант** | нарушение недопустимо, можно проверить | «Всегда / никогда» + почему + проверка | связать с fitness function (`arch-fitness-functions`) |
| **Умолчание** | так делаем, если нет причины иначе | «По умолчанию X; отступай, если Y; при отступлении — Z» | явный критерий отступления |
| **Эвристика** | помогает суждению, не правило | «При выборе между A и B учитывай …» | пример применения |
| **Знание** | факт о ландшафте | короткое описание + ссылка | дата актуальности |

Утверждение, которое нельзя отнести ни к одному типу, обычно слишком размыто: переформулируй или выбрось. Слова «преимущественно», «по возможности», «обоснованно» без критерия — главный источник того, что агенты «соблюдают» стандарт формально.

### 3. Формулировка для агента
Используй `assets/constraint-card.md`. Правила хорошей формулировки:
- **Императив и конкретика**: «Публикуй события только через outbox-таблицу модуля» лучше «Обеспечивай надёжную доставку».
- **Почему** — одно предложение. Агент, который понимает причину, правильно обобщает на непредусмотренные случаи.
- **Пример и контрпример**, если правило неочевидно.
- **Эскалация**: что делать, если задача требует нарушения. Стандартная формула: «Остановись, опиши конфликт в design/proposal и предложи запрос на решение» — так нарушение превращается в решение, а не в тихий обход.
- **Ссылка на проверку**: какая команда или проверка подтвердит соблюдение.

### 4. Раскладка по слоям и бюджет
Для L2 используй шаблон `assets/claude-md-architecture-section.md`. Ориентир по бюджету: архитектурный раздел CLAUDE.md — 30–60 строк, индекс обязательных решений — одна строка на решение со ссылкой на ADR. Если не помещается — выноси в скилл с хорошим description (скиллы подгружаются только при необходимости) или в правила каталога. Шаблон корпоративного или доменного скилла-стандарта — `assets/standard-skill-template.md`.

Для L4 — точки встраивания в конкретные SDD-фреймворки описаны в `references/framework-injection.md`. Прочитай раздел нужного фреймворка, когда определишь, что используется в репозитории.

### 5. Проверка соблюдения
Контекст без проверки — гипотеза. Предложи (или проведи, если есть доступ к агенту) прогон: 3–5 типовых задач для этого репозитория, где правило должно сработать, включая одну задачу-ловушку, провоцирующую нарушение. Зафиксируй, соблюдал ли агент правило без подсказки. Если нет — переформулируй, перенеси в другой слой или добавь автоматическую проверку. Позже эти задачи становятся частью архитектурного эвал-сьюта.

### 6. Сопровождение
У каждого слоя — владелец и дата пересмотра. Противоречия между слоями разрешаются явно: нижний слой может **уточнять** верхний, но не **отменять** инвариант; отмена инварианта — только через решение (`arch-agent-binding-decisions`). Знания, полученные из инцидентов и раскопок решений, возвращай в контекст — так петля Maintain → Plan замыкается и на уровне архитектуры.

## Анти-паттерны

- **Копипаст стандарта** на десятки страниц в CLAUDE.md: съедает контекст и размывает важное.
- **Правила без «почему»**: агент соблюдает букву и нарушает дух в новых случаях.
- **Только запреты** без пути эскалации: агент молча обходит или останавливается без пользы.
- **Противоречивые слои** без владельцев.
- **Инварианты без проверок**: на скорости агентов нарушение обнаружится в проде.
- **Неактуальное знание**: устаревший факт о ландшафте хуже отсутствующего.

## Результат

По итогам работы выдай:
1. Таблицу утверждений: текст, тип, слой, проверка, владелец.
2. Готовые файлы: архитектурный раздел CLAUDE.md/AGENTS.md, карточки ограничений, при необходимости черновик скилла-стандарта и правки конфигурации SDD-фреймворка.
3. Список задач для проверки соблюдения.
4. Список инвариантов, которым нужна автоматическая проверка, — с предложением перейти в `arch-fitness-functions`.

Перед изменением существующих файлов команды (CLAUDE.md, конфиги фреймворков) покажи предлагаемый diff и получи согласие: эти файлы — общая собственность команды.

## Связка со Spine

- Слой L0 в Spine — корпоративный CONSTRAINTS-слой (`extends` с пинненной версией, corp-пресеты); L1 — доменные плагины banking/; L2 — `AGENTS.md` (генерирует `agents-md refresh`, проверяет `agentsmd_lint`); L4 — дельта `changes/<id>/DELTA.md` и OpenSpec change c NFR изменения.
- Классификация «инвариант / умолчание / эвристика»: инварианты — AD-блоки ARCHITECTURE-SPINE.md с механическим стражем (C-NNN); умолчания — правила с severity: warn; эвристики — скиллы. Что не проходит тест принадлежности спайна (могут ли двое разойтись?) — не инвариант.
- Бюджет контекста проверяется прогоном: hook-напоминания (self-usage guard) и `fitness_check` — это L4-механика соблюдения.
