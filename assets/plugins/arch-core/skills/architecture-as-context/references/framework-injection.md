# Точки встраивания архитектурного контекста в SDD-фреймворки

Форматы фреймворков меняются быстро. Прежде чем править конфигурацию, посмотри фактические файлы в репозитории и версию инструмента; при расхождении с этим описанием доверяй репозиторию и документации инструмента.

## Содержание
1. OpenSpec
2. superpowers
3. BMAD Method
4. Anthropic AI-Native SDLC
5. Без фреймворка

---

## 1. OpenSpec

**Как устроен.** `openspec/specs/<domain>/spec.md` — источник истины о текущем поведении (требования и сценарии). `openspec/changes/<name>/` — изменение: `proposal.md`, `design.md`, `tasks.md` и delta specs с разделами ADDED / MODIFIED / REMOVED. При архивации дельты сливаются в основные спеки, изменение уходит в `changes/archive/`.

**Куда встраивать архитектуру.**
- **Проектный контекст**: в новых версиях — `openspec/config.yaml` (общий контекст и правила для отдельных артефактов), в старых — `openspec/project.md`. Сюда — краткий архитектурный контекст и правила для `design.md`: например, «в design.md обязательно раздел "Архитектурные решения" с пометкой, затрагивает ли изменение обязательные ADR».
- **Архитектурные спеки как домен**: заведите домен вроде `openspec/specs/architecture/spec.md` с требованиями-инвариантами в форме сценариев («Когда модуль публикует событие, тогда оно записывается в outbox…»). Тогда любое изменение, затрагивающее инвариант, обязано содержать delta к этому домену — архитектурное изменение становится видимым в ревью.
- **design.md как точка архитектурного ревью**: для изменений уровня T2–T3 архитектор смотрит proposal и design до `apply`, а не код после.
- **Архивация** — момент проверить, что знания из design.md, ставшие долговременными, перенесены в ADR или контекст.

## 2. superpowers

**Как устроен.** Набор скиллов, задающих цикл: `brainstorming` (сократический дизайн, вопросы по одному, варианты с компромиссами) → `writing-plans` (план мелкими шагами) → `subagent-driven-development` или `executing-plans` (свежий сабагент на задачу, ревью сначала на соответствие спецификации, затем на качество кода) → `test-driven-development` → `finishing-a-development-branch`.

**Куда встраивать архитектуру.**
- **Brainstorming читает контекст проекта**: архитектурный раздел CLAUDE.md и доменные скиллы попадут в варианты, которые агент предлагает человеку. Добавьте правило: «при выборе варианта сверяйся с индексом обязательных решений; вариант, нарушающий решение, помечай и предлагай запрос на решение».
- **Ревью на соответствие спецификации** — естественное место для архитектурной проверки: добавьте в контекст ревьюера ссылки на обязательные ADR и fitness functions.
- **Собственный скилл архитектуры** рядом со скиллами superpowers: superpowers сам побуждает агента искать и применять подходящие скиллы, поэтому доменный скилл-стандарт с точным description будет подхвачен в нужный момент.
- Не переписывайте скиллы superpowers — дополняйте их своими.

## 3. BMAD Method

**Как устроен.** Агенты-персоны по фазам: Analyst (Analysis) → PM (Planning, PRD) → Architect (Solutioning, документ архитектуры) → Scrum Master готовит детальные story-файлы с полным контекстом → Dev реализует → QA/Test Architect. Треки Quick Flow, BMad Method, Enterprise (последний добавляет безопасность, DevOps и тестовую стратегию).

**Куда встраивать архитектуру.**
- **Агент Architect BMAD — не замена архитектору, а его исполнитель.** Корпоративные и доменные ограничения должны стать входом для его workflow создания архитектуры: положите их в документы, которые агент читает (контекст проекта, если используется, документ архитектуры, доменные скиллы).
- **Story-файлы SM** — главный канал доставки контекста Dev-агенту. Добавьте правило, чтобы SM включал в каждую story ссылки на затронутые обязательные решения и проверки.
- **Enterprise-трек** — точка подключения архитектора безопасности и платформы.
- Человек-архитектор фокусируется на приёмке документа архитектуры и на решениях с высокой ценой ошибки, а не на написании документа.

## 4. Anthropic AI-Native SDLC

**Как устроен.** Петля версионируемых Markdown-артефактов: Plan (`intent.md`) → Design (`spec.md`, генерируется с учётом организационных ограничений, переиспользуемые скиллы кодируют требования бренда, безопасности, UX как жёсткие требования генерации; владелец продукта подписывает) → Build (Claude Code в plan mode создаёт `plan.md`; CLAUDE.md хранит соглашения и архитектурное знание) → Test (непрерывные эвалы, сьюты из 20–50 реальных задач) → Deploy (многослойное AI-ревью diff против `plan.md` и стандартов безопасности, git-хуки, автоприёмка низкорисковых изменений, человек одобряет регулируемую, высокорисковую и ключевую архитектурную логику) → Maintain (мониторинговые агенты создают новый `intent.md`).

**Куда встраивать архитектуру.**
- **Скиллы как жёсткие требования генерации spec** — прямой канал для L0–L1: архитектурные стандарты оформляются скиллами наравне с безопасностью и UX.
- **CLAUDE.md** — L2, около одной страницы.
- **Проверка plan ↔ diff** в git-хуках — дополнить архитектурными fitness functions.
- **«Ключевая архитектурная логика»** требует человеческого одобрения — архитектор определяет, что именно к ней относится (через политику уровней риска).

## 5. Без фреймворка

Если SDD-фреймворка нет: начни с L2 (CLAUDE.md/AGENTS.md) и обязательных ADR, затем добавь правило для агента: «перед реализацией изменения, затрагивающего границы модулей, данные или внешние интеграции, опиши план и сверь его с индексом решений». Это минимальный аналог design-гейта, который не требует внедрения целого фреймворка.
