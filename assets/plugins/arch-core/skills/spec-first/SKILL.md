# Спека прежде кода

Один уточняющий раунд в начале дешевле трёх переделок в конце. Но раунд —
именно один: спека на полстраницы, не ТЗ на десять.

## Когда НЕ нужно

Задача однозначна, мала (< ~30 минут) и обратима → просто делай. Спека для
«поправь опечатку» — это карго-культ.

## Формат мини-спеки

```
ЦЕЛЬ: <одно предложение: что должно стать возможным/правдой>
НЕ-ЦЕЛИ: <что сознательно НЕ делаем в этой задаче — 2–4 пункта>
ОГРАНИЧЕНИЯ: <технологии, совместимость, что нельзя трогать, бюджет времени/токенов>
КРИТЕРИЙ ГОТОВНОСТИ: <проверяемое условие: команда/тест/сценарий, который
  покажет «готово» — фиксируется до работы, как в verify-first>
ОТКРЫТЫЕ ВОПРОСЫ: <максимум 3, только те, что меняют архитектуру решения>
```

## Протокол

1. **Сначала извлеки, потом спрашивай.** Заполни спеку из уже сказанного,
   контекста репозитория и `CODEBASE_MAP.md`. Вопросы — только про то, что
   реально развилка (два разных решения), а не то, что можно разумно
   предположить.
2. **Один раунд вопросов.** Покажи заполненную спеку с пометками
   `[предположение]` и до трёх вопросов. Ответов нет / «делай как считаешь» →
   предположения становятся решениями и фиксируются в спеке.
3. Спека подтверждена → она закон на время задачи:
   - копируется в начало сессионного журнала (`session-journal`);
   - её «НЕ-ЦЕЛИ» и «ОГРАНИЧЕНИЯ» — это будущие разделы «НЕ НАРУШАТЬ» в
     паспорте `task-handoff`;
   - для параллельных прогонов это тот самый SPEC из `parallel-experiments` —
     критерии сравнения вариантов берутся из «КРИТЕРИЯ ГОТОВНОСТИ».
4. **Дрейф скоупа.** Посреди работы всплыло «а ещё надо бы...» → это правка
   спеки, а не молчаливое расширение: одна строка пользователю
   («расширяю цель на X, ок?») или запись в журнал `СКОУП+: ... отложено`.
5. Финальный ответ сверяется с критерием готовности дословно: прогнал —
   показал результат. «Должно работать» запрещено (`verify-first`).

## Красные флаги

- Начал писать код, не сумев сформулировать критерий готовности одной
  проверяемой фразой.
- Больше трёх вопросов пользователю — значит, не сделал шаг 1.
- Спека переписывается второй раз за задачу — остановись, это уже другая
  задача: закрой текущую, начни новую со своим handoff.

## Связка со Spine

- Мини-спека этого скилла — вход маршрутизации: после уточняющего раунда прогони `significance_score` (триггеры видны из не-целей и ограничений) и оформи результат дельтой (`delta_propose`) для Standard/Critical — там критерии приёмки ДО реализации обязаны быть.
- Критерий готовности из спеки становится fitness-правилом (CONSTRAINTS) или критерием приёмки дельты — проверяемым, а не декларативным.
- Для кодовых харнессов спека уезжает в TASK.md пакета (`handoff_create`): цель/не-цели/ограничения/DoD — ровно секции задачи исполнителю.
