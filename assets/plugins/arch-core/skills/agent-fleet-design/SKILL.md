# Проектирование флотов агентов

Флот агентов — это распределённая система: у неё есть компоненты (агенты), интерфейсы (артефакты передачи), состояние (контекст, репозиторий), права, отказы и стоимость. Значит, к ней применимы инструменты архитектора. Этот скилл проектирует **систему производства**, а не продукт. Механику исполнения (например, `subagent-driven-development` или `dispatching-parallel-agents` в superpowers, роли BMAD, сабагенты и динамические workflows в Claude Code) он не переизобретает — он выбирает и настраивает её под задачу и риск.

## Процесс

### 1. Профиль нагрузки
Выясни (по одному вопросу):
- **Тип работы**: новая функциональность, миграция/модернизация, массовый рефакторинг, генерация тестов, разбор инцидентов, документация, исследование.
- **Объём и делимость**: сколько единиц работы, насколько они независимы.
- **Риск**: что сломается при ошибке, обратимость, регулируемые данные.
- **Верифицируемость**: есть ли тесты, насколько им можно доверять, есть ли эталон поведения.
- **Ресурсы**: сколько людей могут проверять результат, срок, бюджет.

Главное наблюдение, которое стоит проговорить: в агентной разработке ограничение почти всегда не в генерации, а в **верификации и слиянии**. Флот, который производит больше, чем люди и проверки способны принять, создаёт очередь непринятых изменений и давление на снижение качества ревью.

### 2. Выбор топологии
Подробное описание топологий, их сильных сторон и отказов — в `references/topologies.md`. Прочитай его и предложи 2 варианта с компромиссами и рекомендацией. Краткий ориентир:

| Ситуация | Топология |
|---|---|
| одна функция, высокая неопределённость | один агент + человек, затем план |
| функция из независимых задач | оркестратор → исполнители, свежий контекст на задачу, ревью между задачами |
| несколько функций параллельно | параллельные сессии в отдельных worktree, 2–3 на инженера на старте |
| миграция однотипных единиц | map-reduce: пилотная волна → шаблон → волны по модулям |
| высокая цена ошибки | пары исполнитель–критик, независимый проверяющий агент без доступа к рассуждениям исполнителя |
| сквозной процесс от идеи до кода | конвейер ролей (как в BMAD) с артефактами-контрактами между фазами |
| эксплуатация | фоновые событийные агенты: аномалия → разбор → новый intent |

### 3. Агентный закон Конвея
Структура флота отпечатывается в структуре системы: если агенты нарезаны по слоям (один делает API, другой БД), получится связанность по слоям; если по модулям — модульность. **Выравнивай границы агентов с границами модулей и bounded contexts.** Назначай агенту «владение» каталогами: исполнитель пишет только в свою зону, изменения чужих интерфейсов идут через запрос владельцу. Это же снижает конфликты слияния.

### 4. Границы контекста и артефакты передачи
- Каждый агент получает **минимально достаточный контекст**: свою задачу, релевантные спеки и решения, контракты соседей. Общий раздутый контекст снижает качество и растит стоимость.
- Передача работы — только через **артефакты-контракты** в репозитории (spec, plan, story, task, отчёт ревью) с определённой структурой. Устная передача между агентами в общем контексте — источник распространения ошибок.
- Определи **общие реестры**, которые должны видеть все исполнители: существующие утилиты и общие компоненты (иначе агенты параллельно напишут одно и то же), словарь домена, индекс решений.

### 5. Права и радиус поражения
Для каждой роли агента определи: какие инструменты разрешены, в каких каталогах можно писать, есть ли сеть, какие MCP-серверы и секреты доступны, может ли агент запускать миграции, пушить, создавать PR, мержить. Принцип наименьших привилегий; песочница по умолчанию; необратимые действия (миграции прода, удаление данных, изменения IAM) — только через человека. Отдельно — защита от prompt injection из недоверенных источников (тикеты, веб-страницы, логи): агент, читающий недоверенный ввод, не должен иметь широких прав на запись.

### 6. Точки контроля
Привяжи к уровням риска (см. `arch-drift-and-risk-review`): где проверка автоматическая, где AI-ревью, где человек. Для флота важно ставить человеческий контроль **рано** — на шаблоне в пилотной волне, на плане, на контракте, — а не на сотнях итоговых diff.

### 7. Режимы отказа
Пройди по списку и для каждого риска запиши смягчение:
- **Распространение ошибок**: ошибка в общем артефакте размножается по всем исполнителям → пилотная волна, ревью шаблона.
- **Отравление контекста**: устаревший или неверный факт в общем контексте → владелец и дата актуальности у контекста.
- **«Починка» тестов под код**: агент ослабляет проверки → запрет на изменение тестов и проверок без отдельного шага с одобрением.
- **Дублирование и расхождение**: параллельные агенты делают одно по-разному → реестр общих компонентов, владение зонами.
- **Конфликты слияния** → нарезка по модулям, частые небольшие слияния, порядок волн.
- **Дрейф от спецификации** → ревью на соответствие спеке до ревью качества; проверка plan ↔ diff.
- **Неконтролируемая стоимость** → лимиты на задачу и на волну, остановка при превышении.
- **Тихие неудачи**: агент сообщает об успехе без проверки → требование доказательства (вывод тестов, команды) в отчёте.

### 8. Экономика
Оцени три ресурса: **токены/вычисления**, **CI-ёмкость** и **минуты человеческого внимания**. Последний — самый дефицитный и самый недооценённый. Посчитай: сколько изменений произведёт флот, сколько из них потребует человека по политике рисков, сколько минут на каждое. Если сумма превышает доступное время людей — меняй топологию (больше автоматической верификации, крупнее единицы ревью, ранний контроль шаблона), а не сокращай ревью молча.

## Результат

Карточка топологии по `assets/fleet-card.md` и, при желании, диаграмма Mermaid. Если флот разворачивается в репозитории — предложи, какие артефакты и правила добавить (каталог для артефактов передачи, правила владения зонами в CLAUDE.md, ограничения прав в настройках агента), и покажи изменения перед записью.

## Разбор инцидента флота

Если пользователь пришёл с проблемой («агенты наломали дров»), веди разбор без поиска виноватых и без «модель плохая»: восстанови хронологию, затем причины по уровням — контекст, права, топология, верификация, экономика — и изменения в дизайне по каждому уровню. Результат разбора добавь в карточку флота как урок.

## Связка со Spine

- Топологии: оркестратор–исполнители = `handoff_create` + `harness_run` (MCP-handoff параллельно в worktree, ADR-001); пары исполнитель–критик = `rubric_evaluate` (независимый судья); фоновые событийные агенты = `subagent_run`/`ralph_run`.
- Права и песочницы: bash-sandbox (bwrap, ADR-038), fs-периметр (ADR-083), модель доверия command_succeeds (ADR-053). Точки человеческого контроля: significance Critical → решение A3 через `propose_options`.
- Экономика флота: журнал MCP-вызовов `.arch-handoff/mcp-calls.jsonl` + `arch-be digest` — измеряй токены/минуты внимания по данным, а не на глаз (см. harness-token-economics в плагине arch-ai-platform).
