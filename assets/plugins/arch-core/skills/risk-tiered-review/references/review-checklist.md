# Чек-лист архитектурного ревью изменения

Используй выборочно: для T1 — разделы 1–3; для T2 — 1–6; для T3 — всё. Не превращай чек-лист в формальность: фиксируй только реальные находки.

## 1. Соответствие намерению
- Изменение делает то, что описано в intent/proposal/spec, и не больше?
- Файлы вне плана: объяснены или это выход за рамки?
- Delta specs (OpenSpec) отражают изменение поведения?

## 2. Обязательные решения и границы
- Затронуты ли обязательные ADR? Соблюдены? Если нет — есть запрос на решение?
- Импорты через границы модулей, обращения к чужим данным, новые циклы.
- Публичные контракты (API, события, схемы): ломающие изменения, версионирование, совместимость.

## 3. Неявные решения
- Новые зависимости, кэши, ретраи, хранилища, паттерны (см. сигналы в `arch-agent-binding-decisions`).
- Дублирование существующих компонентов.

## 4. Данные
- Владение данными, миграции и их обратимость, порядок развёртывания (expand–contract).
- Персональные и регулируемые данные: где появились, логируются ли.
- Консистентность и транзакционные границы.

## 5. Отказы и эксплуатация
- Таймауты, ретраи с идемпотентностью, поведение при отказе зависимости.
- Наблюдаемость: логи, метрики, трассы для нового пути.
- Конфигурация и feature flags, план отката.

## 6. Проверки и тесты
- Тесты проверяют поведение, а не реализацию? Не ослаблены ли существующие (удаления, `skip`, расширенные допуски)?
- Изменены ли архитектурные проверки, исключения, базовые линии? Почему?

## 7. Безопасность (T3)
- Аутентификация, авторизация, скоупы, секреты.
- Обработка недоверенного ввода, включая ввод, который читают агенты.
- IaC: публичная доступность, IAM, шифрование.

## 8. Прослеживаемость (T3, регулируемые домены)
- Цепочка intent → spec → plan → diff → тесты/эвалы → одобрение версионирована?
- Именованный одобряющий и обоснование решения зафиксированы?
