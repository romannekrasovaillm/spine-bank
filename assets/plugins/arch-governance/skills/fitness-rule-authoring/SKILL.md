# Создание хороших архитектурных фитнес-правил

## Когда применять

- Формулируешь новое правило: CONSTRAINTS.yaml (C-NNN), поле Rule у инварианта AD-n в спайне, гейт handoff-пакета.
- Значимое решение (ADR) пишется без способа автоматической проверки — это намерение, а не решение.
- Ревью существующего набора правил (`arch-be trace check` показал AD без правила).
- Правило планируется включить на легаси или уже тонет в ложных срабатываниях.
- Governance на уровне ландшафта: стандарты по всем системам сразу, а не код одной системы.

## Анатомия: пять частей правила

Хорошее правило полезно, когда у него есть пять частей. Если одной нет — правило вырождается:

1. **Архитектурная характеристика + бизнес-причина** — что защищаем и почему это важно бизнесу. Без причины правило воспринимается как бюрократия. Причина произносится одним предложением и отвечает «зачем»; «так принято» и «best practice» — не причины.
2. **Объективная метрика** — число или проверяемый факт, который невозможно истолковать двояко.
3. **Порог** — без него правило превращается в пожелание: «покрытие тестами» — пожелание, «покрытие ≥ 80% для критичных модулей» — правило.
4. **Место и момент запуска** — где и когда проверяется.
5. **Реакция на нарушение** — заранее прописанная и автоматическая: блок слияния / предупреждение / тикет / алерт. Без реакции никто не замечает падения правила.

Эталон (все пять частей): «Чтобы домены можно было выпускать независимо, модули домена "Платежи" не импортируют классы домена "Кредиты"; проверяется ArchUnit на каждом PR; нарушение блокирует слияние».

## Классификация — выбирай осознанно

- **Атомарные / холистические** — одна характеристика / совокупное свойство системы.
- **По событию / непрерывные** — на PR, релиз, календарь / постоянно в проде.
- **Статические / динамические** — по структуре кода / по поведению в рантайме.
- **Ручные** — юридическая проверка, аудит безопасности тоже фитнес-функции, если есть чёткий критерий; автоматизировать стоит всё, что можно.
- **Временные** — срабатывают по календарю: напоминание обновить фреймворк через полгода, проверка, не истекло ли исключение.
- **Эмерджентные** — характеристика, важность которой обнаружилась в эксплуатации.
- **Орг-общие / домен-специфичные** — для всей организации / для одного домена.

## Уровни запуска

- **Коммит / PR** — быстрый статический анализ: зависимости, цикломатическая сложность, линтинг API-контрактов.
- **Пайплайн** — интеграционные и нагрузочные тесты, сканирование уязвимостей.
- **Прод** — мониторинг и chaos engineering (Chaos Monkey в Netflix — классический пример проверки устойчивости прямо в продакшене).

Сдвиг мышления: SLO фактически являются непрерывными холистическими фитнес-функциями; фитнес-правила пересекаются с observability, а не только с тестированием. Выбирай самое дешёвое место, где нарушение ловится достаточно рано.

## Связь с ADR — практичная эвристика

У каждого значимого архитектурного решения (ADR) должно быть хотя бы одно правило, проверяющее его соблюдение. Решение без проверки остаётся намерением: через год код может ему уже не соответствовать, хотя документ всё ещё висит в репозитории. Связка «ADR + фитнес-функция» превращает архитектурное управление из ревью-комитетов в автоматический контроль.

## Уровень предприятия (ландшафт)

Правила ландшафта проверяют соответствие стандартам по всем системам сразу: каждый сервис зарегистрирован в каталоге с владельцем; никто не начинает технологию со статусом «hold» в техрадаре; API соответствуют корпоративному стандарту; интеграции идут только через утверждённые шины; нет компонентов с истёкшим сроком поддержки; персональные данные хранятся в разрешённых контурах.

Инструменты другие: policy-as-code (OPA, Conftest), проверки IaC (Checkov и аналоги), линтеры OpenAPI (Spectral), скоркарты в портале разработчика (Backstage), запросы к архитектурному репозиторию или CMDB.

## Методика

### Фаза A — авторинг одного правила

1. **Зафиксируй характеристику и бизнес-причину.** Формула: «чтобы X (бизнес-цель), защищаем Y (характеристика)». Тест: причина произносится одним предложением и отвечает «зачем»; иначе правило не заводить.
2. **Подбери объективную метрику и порог.** Тест: результат проверки — число или факт без двоякого толкования. Помни закон Гудхарта: метрика, ставшая целью, перестаёт быть хорошей (80% покрытия спокойно сочетается с бесполезными тестами) — измеряй важное, а не легкоизмеримое.
3. **Определи место и момент запуска** (см. «Уровни запуска»). Критерий: самое дешёвое место, где нарушение ловится достаточно рано.
4. **Пропиши реакцию на нарушение** в самом правиле, а не решай в момент падения.
5. **Выбери тип по классификации**; всё автоматизируемое — автоматизируй; ручное оставляй только с чётким критерием.
6. **Определи область действия:** одна система или ландшафт (для ландшафта — секция выше).
7. **Сверь связь с решениями:** у значимого ADR ≥ 1 правило; в спайне поле Rule у AD-n — проверяемое; в CONSTRAINTS.yaml правило C-NNN имеет owner, verified_by и срок. В контуре харнесса связность «решение → правило» проверяет `arch-be trace check` (AD без правила и без `unverifiable` — error), набор правил прогоняется гейтом `arch-be control check . --constraints CONSTRAINTS.yaml`.

### Фаза B — внедрение набора

8. **Выбери 3–5 характеристик**, действительно критичных для системы или ландшафта, — не больше.
9. **Запусти в режиме предупреждения:** откалибруй пороги, убери ложные срабатывания (прогоны гейта `arch-be control check` / CI-уровня, где правило живёт).
10. **Легаси → ratchet («храповик»):** текущие нарушения фиксируются как базовая линия, правило запрещает только ухудшение — количество нарушений может только уменьшаться. Никогда не включай блокирующий режим на легаси без базовой линии: сборка упадёт сразу.
11. **Переведи в блокирующий режим** и выведи результаты на общий дашборд — состояние архитектуры видно всем, а не только архитектору.
12. **Заведи процесс исключений:** исключение оформляется явно — обоснование, владелец, срок действия; молчаливое отключение проверки запрещено.
13. **Периодически пересматривай правила:** архитектурные приоритеты меняются, устаревшее правило мешает так же, как отсутствующее.

## Чек-лист качества правила

- [ ] Все 5 частей записаны явно: характеристика+причина / метрика / порог / место и момент / реакция.
- [ ] Причина отвечает «зачем», а не «так принято».
- [ ] Метрика измеряет важное, а не только легкоизмеримое (Гудхарт).
- [ ] Порог дифференцирован по критичности систем: требования к платёжному фронту и к внутреннему отчётному инструменту не совпадают.
- [ ] У значимых ADR/AD есть ≥ 1 правило (`arch-be trace check` чист).
- [ ] Пороги откалиброваны в warning-режиме до блокировки.
- [ ] На легаси включён ratchet, а не блокирующий режим с нуля.
- [ ] Исключения явные: обоснование, владелец, срок.
- [ ] Результаты видны на общем дашборде.
- [ ] Правила стоят в календаре пересмотра.

## Антипаттерны

- **Слишком много правил сразу** → команды тонут в ложных срабатываниях, отключают проверки, ищут обходы. Признак: растёт число «отключено навсегда».
- **Измеряют лёгкое, а не важное** (закон Гудхарта). Признак: метрика зелёная, проблема жива.
- **Одинаковые пороги для систем разной критичности.** Признак: платёжный сервис и внутренний отчётный инструмент проходят одинаковый набор.
- **Блокирующий режим на легаси без базовой линии.** Признак: сборка падает сразу после включения.
- **Молчаливое отключение** вместо оформления исключения. Признак: закомментированные правила, skip-флаги без ссылок.
- **Правило без причины** → бюрократия. Признак: никто не может объяснить, зачем правило.
- **Правило без реакции.** Признак: красный статус висит неделями, никто не действует.
- **Правила не пересматриваются.** Признак: правило защищает характеристику, которая больше не приоритетна.

## Примеры

**Полное правило (5 частей):** «Чтобы домены можно было выпускать независимо, модули домена "Платежи" не импортируют классы домена "Кредиты"; проверяется ArchUnit на каждом PR; нарушение блокирует слияние».

**Ratchet на легаси (иллюстрация):** правило «нет циклических зависимостей» на легаси даёт 40 нарушений → базовая линия 40, правило запрещает только рост, счётчик только уменьшается; при нуле — можно переводить в полный блок.

**Временное правило:** напоминание обновить фреймворк через полгода; проверка «не истекло ли исключение» по календарю.
