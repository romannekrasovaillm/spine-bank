# Токен-экономика harness: как дизайн оркестрации задаёт цену задачи

Тезис: главный рычаг против «token maxing» (покупки качества растущим числом
токенов) — не цена токена и не выбор модели, а **harness**. В контролируемом
эксперименте (одни и те же 22 задачи, 6 моделей, меняется только слой
оркестрации) harness срезал blended cost/task на 41% ($0.21→$0.12), медианное
время — на 44% (48→27 с), токены/задачу — на 38% (14.2k→8.8k) при качестве на
уровне паритета (0.78→0.81). Экономия модельно-инвариантна (−33…−61% на каждой
модели), а прирост качества — функция силы модели (**harness leverage**, r=0.99).

## Биллинг задачи (модель для расчёта)

Задача = k-ходовый цикл. Вход разложим на управляемые harness'ом слагаемые:
`T_in = S(системный) + H(история) + G(схемы инструментов) + R(retrieval) + U(ход пользователя)`.
Наивный harness переигрывает весь транскрипт → вход растёт как **O(k²)**;
harness, который компактит историю, кэширует инвариантный префикс и выносит
тяжёлые tool-output, переводит в **≈O(k)**. Агентные нагрузки
input-доминантны (input:output ~100:1), а кэш читается по ~0.1× цены
(`p_eff = p_in·(1 − h·(1 − κ)), κ≈0.1`, h — доля кэш-чтений).

## Шаги

1. **Введи двузонный промпт.** Каждый промпт — физически: **байт-стабильный
   префикс** (полный каталог схем инструментов + стабильный системный промпт +
   append-only транскрипт), затем **volatile tail** (перестраивается каждый ход:
   время, список файлов, состояние плана, напоминания, кастомные инструкции).
   Разделение — правило корректности: всё, что меняется за ход, структурно
   запрещено в префиксе; логика cache-breakpoint отказывается ставить маркер на
   volatile-сообщении. Готово, когда на идентичном префиксе ~99% prompt-токенов
   обслуживаются как cache reads.

2. **Расставь cache breakpoints.** Ставь до 4 провайдерских брейкпоинтов: после
   каталога схем, после стабильного системного промпта и скользящий по двум
   новейшим durable-ходам. Защёлкни retention (напр. 1 час) на сессию, чтобы
   политика не менялась в середине прогона. Готово, когда cache hit rate
   измеряется на каждом ходе и является первой метрикой агента.

3. **Структурная, инкрементальная, cache-aware компакция.** При ~80% входного
   бюджета сворачивай старую историю в типизированный checkpoint из четырёх
   артефактов: durable memory (решения, ограничения, отвергнутые подходы),
   восьмисекционный execution summary под возобновление (текущее состояние,
   затронутые файлы, ошибки, следующие шаги), дословно сохранённые требования
   пользователя и ссылки на скиллы. Живой хвост из 4–12 последних сообщений
   (≤30% бюджета) всегда выживает дословно; каждый checkpoint сворачивает
   предыдущий (компакция инкрементальна); суммаризацию ведёт дешёвая модель,
   вне платящего цикла; пустой/деградировавший summary отменяет компакцию.
   Готово, когда история больше не переигрывается квадратично и нет
   деструктивной середины-обрезки.

4. **Выноси контекст, который модель не оплачивает (context offload).**
   - **Sub-agent как context firewall:** ребёнок ведёт широкое чтение/поиск в
     своём контексте и возвращает summary с жёстким капом (напр. 8 КБ), цитаты —
     в metadata-sidecar, который родитель не читает; делегирование капнуто по
     глубине и идемпотентно при ретраях.
   - **Progressive disclosure скиллов:** в промпте только таблица
     «имя+описание», полный документ лежит в песочнице и читается по вызову.
   - **Spill тяжёлых tool-output в файлы:** shell-вывод сверх порога — head/tail
     превью + полный вывод в файл (с баннером, запрещающим судить об успехе по
     превью); web-fetch — инлайн-фрагмент + спилл страницы; слишком большие
     чтения файлов отклоняются, а не молча обрезаются. Файловая система —
     неограниченная память, контекст держит указатели.
   - **Event-sourced состояние:** план/canvas проецируется один компактный
     рендер за ход, результаты plan-tool заменяются однострочным ack.
   Готово, когда удаление stale/bulky токенов одновременно режет счёт и чистит
   рабочий набор модели.

5. **Zero-token ожидания и durability.** Ожидание — это не цикл: при
   необходимости ответа человека/апрува/долгой фоновой задачи прогон
   **устойчиво приостанавливается при нулевой стоимости токенов** и
   возобновляется по ingress-событию (никакого polling-цикла). Каждое событие
   журналируется в write-ahead log до стриминга; упавший/вытесненный прогон
   возобновляется под generation fencing с точного следующего sequence number.
   Готово, когда краш не означает «перекупить 40 ходов заново».

6. **Failure-spend governance.** Классифицируй каждую ошибку в типизированный
   класс (rate limit, stall, timeout, malformed stream, outage, permanent) до
   решения; только whitelisted классы падают на следующего провайдера.
   Mid-stream-сбой = **discarded attempt**: частичный черновик очищается, и
   никакие side effects (tool execution, durable writes) не исходят из
   отброшенной попытки. Circuit breaker останавливает модель, трижды
   повторившую байт-идентичный падающий tool call (со steering: менять
   аргументы vs отступить). Обрезка вывода и output-length cap завершаются
   громко, типизированным состоянием. Капни цикл (напр. 50 итераций) и
   параллелизм инструментов (напр. 4). Готово, когда множитель ретраев/
   думлупов на формулу биллинга ограничен структурно.

7. **Model-agnostic floor.** Какую модель и через каких провайдеров звать, в
   каком порядке фолбэка — типизированный route plan, переданный данными; цикл
   никогда не ветвится по имени модели, а каждый провайдерский стрим
   нормализуется в один chunk-контракт. Нативный tool calling — единственный
   путь; schema hygiene для слабых моделей: инлайнить `$ref`, восстановлять
   double-encoded JSON-аргументы, вычищать внутренности фреймворка из ошибок
   валидации, дробить перегруженные схемы. Готово, когда структура держит
   floor независимо от драйвящей модели.

## Что измерять

`η$ = Q/C` (качество на доллар) и `CPM = Q·10⁶/τ` (завершений на млн токенов),
где `τ` — токены на завершённую задачу. В эксперименте η$ выросла на 82%,
CPM — с 54.9 до 92.0.

## Чего не делать

- Не позволять переменному за ход содержимому попадать в кэшируемый префикс —
  это убивает cache hit rate.
- Не обрезать историю деструктивно посередине: компакция должна быть
  структурной и инкрементальной.
- Не давать субагенту возвращать полный контекст — только капнутый summary.
- Не держать схемы всех инструментов в каждом вызове, если модель их не
  использует, — используй progressive disclosure.
- Не реализовывать ожидания polling-циклом и не считать краш «просто ретраем».
- Не пенять на модель за рост счёта: четыре из пяти входных слагаемых и ретраи
  задаёт код harness.

## Связка со Spine

- Церемония дороже пользы — измерено ArchBench: ×8 входных токенов против брифа. Правила скилла применимы к контуру Spine: кэшируемый префикс системного промпта, повторное использование прогона survey/recover по ревизии (не перегонять на каждом шаге), тяжёлые tool-output — в файлы (evidence), а не в контекст.
- Субагент как context firewall — механика Spine: `subagent_run` возвращает плотный отчёт, сырой лог остаётся вне родительского контекста; `ralph_run` переносит состояние файлами (handoff), не историей чата.
- Failure-spend governance: dead-end прогоны харнесса — таймаут тишины + убийство группы процессов (harness_run) — это и есть zero-token ожидание; budget прогона — рекомендованный таймаут маршрута (fast 1800с / standard 3600с / critical 7200с).
