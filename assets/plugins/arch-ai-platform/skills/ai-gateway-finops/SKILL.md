# AI-шлюз и FinOps

Связанные скиллы: `ai-platform-reference-architecture`, `llm-tco`;
наблюдаемость — набор agent-eval (`agent-observability-setup`).

## Функции шлюза (минимальный набор)
1. Единый API (OpenAI-совместимый) и виртуальные ключи на команду/приложение/агента.
2. Маршрутизация: алиасы моделей (`chat-default`, `code`, `cheap`) → конкретные
   модели; клиенты не знают провайдера.
3. Надёжность: ретраи, fallback на другую модель/провайдера, балансировка
   между репликами/регионами, таймауты.
4. Квоты и лимиты: RPM/TPM, бюджеты в деньгах на ключ/команду, жёсткие и мягкие пороги.
5. Учёт: usage и стоимость по ключу/команде/модели, экспорт в BI.
6. Политики: какие модели разрешены для каких данных; guardrails (вход/выход);
   логирование с маскированием.

Пример конфигурации LiteLLM Proxy — `references/litellm-config.md`.

## Рычаги снижения стоимости (по убыванию типичного эффекта)

| Рычаг | Эффект | Как |
|---|---|---|
| Prompt/prefix-кэш | вход дешевле в разы (у провайдеров кэш-чтение в ~4–10 раз дешевле) | стабильный префикс: системный промпт и инструменты в начале, без меток времени; кэш-брейкпоинты |
| Маршрутизация по сложности | 30–80% трафика на дешёвые модели | классификатор/правила; каскад «дешёвая → проверка → дорогая» |
| Ограничение контекста агентов | меньше входных токенов на шаг | обрезка выводов инструментов, компакция, суб-агенты |
| Batch API для офлайн-задач | ~50% скидки у провайдеров | ночные разметки, суммаризация |
| Ограничение thinking/выхода | меньше выходных токенов | бюджет рассуждений по типу задачи, лимит max_tokens |
| Семантический кэш | экономия на повторяющихся вопросах (FAQ) | только для детерминированных ответов без персональных данных; риск неверных попаданий |
| Self-hosted для массовых нагрузок | дешевле при высокой загрузке | `llm-tco` |

Оценить потенциал по реальным логам: доля кэш-чтения и токены по шагам —
`trace_analyzer.py` (набор agent-eval).

## Учёт затрат (chargeback/showback)
- Ключ на приложение/агента + метаданные (команда, проект, среда) в каждом запросе.
- Ежедневная выгрузка usage → витрина: стоимость по командам, моделям, сценариям; стоимость на успешную задачу (не только на токен).
- Бюджеты с алертами на 50/80/100%; аномалии (рост стоимости на сессию — признак зацикливания агента).
- Showback сначала (прозрачность), chargeback — когда учёт стабилен.

## Политики маршрутизации (шаблон)
- Конфиденциальные данные → только внутренние/одобренные модели (метка классификации в запросе или по ключу).
- Код и агенты → сильная модель; классификация/извлечение → малая; fallback на эквивалент другого провайдера.
- Каскад для массовых задач: малая модель + самопроверка/валидатор, эскалация при низкой уверенности.

## Связка со Spine

- Маршрутизация и каскады моделей — решения с последствиями: фиксируй ADR (каскад дешёвая→дорогая меняет UX-задержку — это NFR-компромисс, отражи p99 обеих веток).
- Лимиты/квоты на шлюзе — исполняемые правила: дублируй политику шлюза fitness-правилами конфигурации (must_contain по манифесту шлюза) — «заявлено в политике» обязано совпадать с «проверено в CI».
- FinOps-метрики (токены по командам, cache hit rate) — наблюдаемость: потребуй их в NFR платформы (verified_by), иначе оптимизация будет по ощущениям.
