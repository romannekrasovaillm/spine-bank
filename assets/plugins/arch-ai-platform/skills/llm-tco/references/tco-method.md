# Методика TCO для LLM

## Структура затрат
**API**: токены (вход без кэша, вход из кэша, выход) + запись в кэш (у части
провайдеров платная) + надбавки (длинный контекст, приоритетный доступ) −
скидки (batch API ~50%, объёмные контракты). Плюс затраты на шлюз и интеграцию.

**Собственный инференс**:
| Статья | On-prem | Аренда |
|---|---|---|
| Вычисления | amortization: capex / (срок × 12); срок 3–5 лет (моральное старение GPU ~2–3 поколения) | цена GPU-часа × 730 × число GPU (reserved дешевле on-demand) |
| Электричество | кВт на GPU с долей сервера (H100-узел ~10 кВт / 8 GPU ≈ 1.2–1.4 кВт) × PUE × тариф | включено |
| Размещение | стойка, охлаждение, сеть | включено |
| ПО и поддержка | лицензии (NVIDIA AI Enterprise и т.п.), поддержка вендора | частично |
| Персонал | SRE/MLOps на платформу | меньше, но не ноль |
| Хранилище и сеть | веса моделей, логи, межузловая сеть (InfiniBand/RoCE для TP/PP между узлами) | egress-трафик |

## Типовые ошибки
- Сравнение по пиковой пропускной способности GPU без SLA: при TTFT/TPOT-ограничениях
  реальная ёмкость в 2–5 раз ниже пиковой.
- Игнорирование пиков: парк сайзится по пику, а платится 24/7.
- Забытые фиксированные затраты: персонал, резервирование, тестовый контур.
- Сравнение с прайсом API без кэша, хотя у агентов доля кэш-чтения 60–90%.
- Сравнение моделей разного качества.
- Отсутствие порога пересмотра: цены API падают быстро (в разы за год для
  того же уровня качества), решение о закупке нужно пересматривать.

## Шаблон обоснования (для ADR/записки)
1. Контекст и нагрузка (объёмы, рост, профиль).
2. Варианты: API (2–3 модели), свой парк (1–2 конфигурации), гибрид.
3. Таблица TCO на 1 и 3 года + точка безубыточности + чувствительность (±50% нагрузки, ±30% цены).
4. Нефинансовые критерии: размещение данных, регуляторика, независимость, латентность, доступность моделей.
5. Решение, риски, условия пересмотра (например, «если загрузка < 30% два квартала подряд»).
