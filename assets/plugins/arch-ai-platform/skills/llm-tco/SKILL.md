# TCO: API против собственного инференса

Связанные скиллы: `llm-capacity-planning` (набор LLM serving — сколько GPU и
какая пропускная способность на GPU), `ai-gateway-finops` (снижение затрат
маршрутизацией и кэшем, учёт по командам), `ai-platform-reference-architecture`.

## Шаг 1. Данные

| Что | Откуда |
|---|---|
| Объём токенов в месяц (вход/выход) и доля кэша | логи шлюза/провайдера; оценка: пользователи × запросы × длины |
| Пик/среднее | профиль нагрузки по часам (для внутренних сервисов 3–5×) |
| Цены API | **актуальный прайс провайдера** (не по памяти); учесть скидки batch/кэша/объёма |
| Пропускная способность GPU при SLA | `capacity_plan.py` (вывод ток/с на реплику ÷ TP) или нагрузочный тест |
| Стоимость GPU: аренда за час или capex сервера на GPU | коммерческие предложения; capex с долей сервера, сети, хранилища |
| Электричество, PUE, размещение | инфраструктурная служба |
| Персонал (FTE) на эксплуатацию | обычно 1–3 FTE на платформу инференса, не на каждый GPU |

## Шаг 2. Расчёт

```bash
python scripts/tco_calc.py --in-mtok 3000 --out-mtok 400 --cache-hit 0.5 \
  --api "frontier:in=3,out=15,cache=0.3" --api "mini:in=0.3,out=1.2,cache=0.03" \
  --gpu-throughput "out=1800,in=25000" --gpu-hour 2.5 --ops-fte 1 --fte-year 120000
python scripts/tco_calc.py --rps 3 --in 4000 --out 500 --api "api:in=2,out=8" \
  --gpu-throughput "out=1500,in=20000" --gpu-capex 30000 --amort-years 4 --power-kw 1.2 --kwh 0.12 --ops-fte 2
```
Валюта — любая (`--currency RUB`), главное — единообразно.

## Шаг 3. Интерпретация

- **Сравнивай сопоставимое по качеству**: собственная open-weight модель против
  API-модели того же класса (подтвердить эвалами, набор agent-eval). Сравнение
  своей 30B-модели с frontier-API по цене без сравнения качества бессмысленно.
- **Загрузка решает**: стоимость своего инференса за токен падает обратно
  пропорционально загрузке парка; при средней загрузке < 20–30% API почти
  всегда дешевле. Пики и резервирование (N+1) съедают загрузку.
- **Фиксированные затраты** (персонал, минимум 2 узла для отказоустойчивости)
  доминируют на малых объёмах.
- **Нефинансовые факторы** часто решают раньше денег: требования к размещению
  данных и регуляторика, независимость от поставщика, задержки, доступность
  нужных моделей, сроки поставки GPU. Перечисляй их отдельно.
- **Гибрид** — частый оптимум: базовая нагрузка на своём парке с высокой
  загрузкой, пики и сложные задачи — в API (маршрутизация на шлюзе).

Структура затрат, типовые ошибки и шаблон обоснования — `references/tco-method.md`.

## Формат ответа

Таблица вариантов (в месяц, за 1M токенов, число GPU и загрузка), точка
безубыточности, чувствительность, допущения списком, нефинансовые факторы,
рекомендация (часто — гибрид с порогом пересмотра).

## Связка со Spine

- Скрипт tco_calc.py даёт числа; закрепляй решение ADR'ом с числами в Context (цены, загрузка, горизонт) и пересмотром при изменении ставок — TCO без даты пересмотра протухает.
- Стоимость владения — в модель: `nfr cost` (cost_per_instance_month, exit_cost по CMP) считает TCO и цену выхода по карточкам; стратегия выхода (exit_cost) обязательна для вендорских компонентов — цена ухода растёт каждый год бездействия.
- Точка безубыточности чувствительна к загрузке: зафиксируй измеренный профиль нагрузки (RPS, токены/запрос) в NFR-карточках, а не в голове.
