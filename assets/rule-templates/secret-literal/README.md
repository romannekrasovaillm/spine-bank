# Шаблон правила: секретов-литералов в исходниках нет

Кладёт в кейс `skeleton/rule_templates/secret-literal/` эталонную реализацию
сборки клиентской конфигурации и исполняемый тест, который сканирует её
ИСХОДНИК форматами креденшлов (AWS `AKIA…`, GitHub `ghp_/gho_/ghs_…`,
OpenAI `sk-…`, PEM-блок, присваивания `*_API_KEY`/`*_TOKEN`/`*_SECRET`/
`*_PASSWORD`).

## Что проверяется

Свойство архитектурного инварианта: **секрет не зашит в код**, а читается из
окружения или секрет-хранилища. Тест читает файл `reference_impl.py` и
утверждает, что ни один известный формат креденшла в нём не встречается;
отдельная проверка требует, чтобы файл содержал ожидаемый класс — иначе тест
прошёл бы на пустом файле вхолостую.

## Проверка зубов

`arch-be rules template verify --id secret-literal` подменяет
`reference_impl.py` нарушающей реализацией с двумя засеянными литералами
(AWS-ключ и GitHub-токен) — тест обязан упасть. Значения в фикстурах
валидны по форме, но нерабочие (пример-заглушка AWS).

## Как включить правило в кейс

```bash
arch-be rules template apply secret-literal --ad AD-17 --dir <кейс>
```

Команда кладёт файлы, пишет `.arch-handoff/rule-templates.lock` и печатает
фрагмент правила `command_succeeds` с `verified_by` — его вносит в
`CONSTRAINTS.yaml` архитектор дельтой (шаблон защищённые файлы не правит).

Проверка со скелета — только первый шаг: перенесите сканирование на реальный
модуль конфигурации проекта. То же свойство на уровне всего репозитория
проверяет составляющая гейта `secrets` (C3, `[gate.secrets]`).
