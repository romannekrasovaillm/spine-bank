# Контракт: адаптер платформы цифрового рубля

Внутренняя сторона стыка банка с платформой ЦР. Внешний протокол платформы
публично не раскрыт — `[ТРЕБУЕТ ПРОВЕРКИ]`; здесь зафиксировано то, что банк
обязан обеспечить независимо от его деталей, и граница допущения.

## Что обязан обеспечивать адаптер

| Обязанность | Требование |
|---|---|
| Единственная точка обмена | прямые вызовы платформы из других компонентов запрещены |
| Идемпотентность исходящих вызовов | идентификатор поручения банка — ключ операции для платформы; повтор не создаёт второй операции |
| Различение исходов | три различимых исхода: подтверждено, отклонено, не определено; «не определено» не сводится к отказам |
| Таймауты | конечные, с фиксацией в журнале до вызова |
| Нормализация | ответ платформы переводится во внутреннюю модель состояния независимо от формата |
| Ключи | только через криптоконтур; ключевой материал не выходит за его пределы |

## Граница допущения

Пока состав методов и форматы платформы не подтверждены, адаптер
проектируется как изолирующий слой: изменение протокола не должно выходить
за его границы. Ни один другой компонент не знает ни имён полей платформы, ни
её кодов ошибок.

## Что относится к внутреннему обмену (известно точно)

- Запрос поручения: идентификатор поручения банка, вид операции, сумма,
  идентификаторы кошельков, признак подтверждения клиентом.
- Ответ: состояние (подтверждено / отклонено / не определено), причина
  отклонения, идентификатор операции платформы, время платформы.
- Запрос состояния по идентификатору — основа разрешения `UNKNOWN`.
- Выписка за период — основа сверки.

## Открытые вопросы к оператору платформы

Состав методов и форматы `[ТРЕБУЕТ ПРОВЕРКИ]`; поведение платформы при
повторе с тем же идентификатором `[ТРЕБУЕТ ПРОВЕРКИ]`; глубина доступной
выписки и её задержка `[ТРЕБУЕТ ПРОВЕРКИ]`; коды отказа и их
классификация `[ТРЕБУЕТ ПРОВЕРКИ]`.
