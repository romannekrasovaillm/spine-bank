# Количественные NFR. Сервис цифрового рубля для физлиц

Числа — проект решения, а не измерение: они подлежат проверке на пилоте и
пересмотру по факту. Каждый NFR имеет способ проверки и привязан к цепочке
компонентов и интеграций модели.

| ID | Требование | Цель | Проверка |
|---|---|---|---|
| NFR-001 | Latency перевода C2C (ответ клиенту об исполнении/неопределённости) | p99 ≤ 3000 мс | гистограмма `cr_transfer_duration_seconds` |
| NFR-002 | Latency оплаты C2B по QR | p99 ≤ 3000 мс | гистограмма `cr_qr_payment_duration_seconds` |
| NFR-003 | Latency открытия кошелька ЦР | p99 ≤ 5000 мс | гистограмма `cr_wallet_open_duration_seconds` |
| NFR-004 | Доступность приёма поручений через каналы | ≥ 0,995 | `sum(rate(cr_gateway_requests_total{result!~"5xx"}[5m]))/sum(rate(...))` |
| NFR-005 | Доступность исполнения операций (включая внешние зависимости) | ≥ 0,980 | тот же расчёт по звену «шлюз → оркестратор → адаптер → ПЦР» |
| NFR-006 | Целевое время восстановления (RTO) | ≤ 15 мин | учения переключения, протокол в evidence |
| NFR-007 | Целевая точка восстановления (RPO) | ≤ 60 с | проверка по журналу операций после учения |
| NFR-008 | Пропускная способность приёма поручений | ≥ 2400 rps | нагрузочный прогон + метрика `cr_gateway_rps` |
| NFR-009 | Лаг сверки с платформой ЦР | ≤ 5 мин (p99) | метрика `cr_reconcile_lag_seconds` |
| NFR-010 | Хранение журнала операций и сведений об операциях | 5 лет | проверка политики хранения по реестру данных |

**Границы окна**: latency-цели включают внешнюю зависимость (платформа ЦР).
Если подтверждённое значение SLA платформы окажется ниже заложенного в
`INT-001`, цели `NFR-001`/`NFR-002` пересматриваются — это зафиксировано как
риск `RISK-002`, а не спрятано в допущение.

Latency-бюджеты hop'ов и доступности участков живут в модели (`model/INT-*`,
`model/CMP-*`) и сверяются детерминированно: `arch-be nfr budget`,
`arch-be nfr availability`, `arch-be nfr capacity`.
