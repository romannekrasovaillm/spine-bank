# Шаблон `append-only-journal`

Проверяемое свойство: **журнал принимает только новые записи** — строку
нельзя переписать или стереть, исправление оформляется компенсирующей записью
со ссылкой на исходную, порядок записей сохраняется, поэтому по журналу
восстанавливается вся история, а не только последнее состояние.

## Что положил `arch-be rules template apply`

| Файл | Роль |
|---|---|
| `test_append_only_journal.py` | свойства инварианта, читаются как спецификация |
| `fakes.py` | фейк журнала с операциями `append`/`read` (правки и удаления нет) |
| `reference_impl.py` | эталонная реализация: тесты зелёные из коробки |
| `java/` | та же проверка на JUnit 5 (`Subject.java` + `AppendOnlyJournalTest.java`) |

Нарушающая реализация в кейс не кладётся: она остаётся в шаблоне и нужна
проверке зубов (`arch-be rules template verify --dir .`), которая подменяет
`reference_impl.py` нарушающей версией и убеждается, что тест **падает**.

## Как перенести проверку на настоящий код

1. **Оставить** фейк и тесты: свойство не зависит от того, кто его соблюдает.
2. **Заменить** `reference_impl.py` на импорт настоящего журнала
   (`from app.ledger import Ledger`) — тогда тест проверяет ваш код.
3. **Переключить команду правила** в `CONSTRAINTS.yaml` со скелета на тест
   вашего кода (`python3 -m pytest -q tests/test_ledger_contract.py`).
   После этого проверка зубов помечается «адаптирован: проверьте вручную» —
   нарушающей реализации для вашего кода у харнесса нет.
4. **Оставить в реестре** `verified_by` у инварианта — правило остаётся
   звеном трассировки, но теперь оно проверяет поведение, а не текст.

## Чего шаблон не проверяет

- Что журнал append-only на уровне хранилища: шаблон проверяет поведение
  вызывающего кода, а не права доступа к таблице (это свойство вашей БД).
- Что компенсирующая запись действительно отменяет эффект исходной — шаблон
  проверяет, что связь `reverses` есть и порядок записей сохранён.
